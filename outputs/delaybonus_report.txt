  - Option construction, target_entity and victim_id population all UNCHANGED.

  The repaired predicate is never even consulted for the bonus, because the gate
  that encloses it never opens:

      communication_risk : only value observed = 0.0    >=0.55 in 0/2400

  ROOT CAUSE OF THE SECOND DEFECT
    rescue_planner.py:191-196 sources both signals via _signal_value(analysis, context,
    ("route_risk",) / ("communication_risk","comm_risk"), default=0.0), which does
    getattr(source, key, None). planning_coordinator.py:53-60 passes the SAME object as
    both analysis and context: a real AnalysisSnapshot (built at wildfire_model.py:1652)
    whose complete field list is
        ['timestamp','local_results','global_result','all_triggers','dashboard_summary']
    No route_risk. No communication_risk. No comm_risk. Neither GlobalAnalysisResult nor
    LocalAnalysisResult has them, and _snapshot_value does not descend into
    dashboard_summary. Both lookups return None -> default 0.0.

    The per-option max() fallback (rescue_planner.py:210-213) reads params keys
    "route_risk"/"communication_risk", which rescue_adaptation_generator never writes.

    The nearest real producer uses a DIFFERENT KEY NAME: the knowledge layer writes
    route_risk_score (firefighter_model.py:35,74,102-103,131,153,196; values assigned at
    wildfire_model.py:3083-3130) and managed/firefighter_state.py:29 writes
    route_risk_summary. Nothing anywhere writes a key literally named route_risk or
    communication_risk.

  IT IS NOT A MAGNITUDE PROBLEM - THE OPPOSITE
    Delay does not lose narrowly, nor by a lot. It TIES EXACTLY:
        utility gap (winner.score - best_delay.score): min=max=mean=0.000000
        EXACT TIES: 2400/2400 ; every option scores 0.0 ; all feasible
    And the bonus is not added to the score - rescue_planner.py:242 sorts by the tuple
        (_preference_adjustment(entry, signals), entry.score)
    so the bonus is the PRIMARY key and any strictly positive value beats any gap.
    Counterfactual measured on the same data - repaired predicate AND gate forced open:
        rescue_decision_delay_rescue wins 2400/2400 ; 2400/2400 selections flip.
    => the mechanism works the instant the signals are real. _DELAY_CANCEL_BONUS at
       0.75 vs 0.0001 would be indistinguishable, which is a further reason the brief
       was right to forbid tuning it.

  INCIDENTAL: today's winner, rescue_victim_handling_confirm_victim (2400/2400), wins
  only because max() over a total tie returns the FIRST element and it is the first
  option the generator emits. That is list order, not selection.

KNOWN RELATED ISSUES - STATUS (reported, NOT fixed, per the brief)
================================================================================
  1. Generic victim_id on delay options - CONFIRMED, and worse than "generic": it is
     the EMPTY STRING, for ALL 10 rescue options, not just delay.
     _entity_id (rescue_planner.py:375-382) looks for params["victim_id"] (never written
     by the generator - zero grep hits) then getattr(option,"victim") (AdaptationOption
     has no such field; the attr name is target_entity). Both miss -> "".
     Since "" is in _GENERIC_VICTIM_IDS (rescue_executor.py:16), a delay WOULD take the
     generic fallback at rescue_executor.py:528-533 and be refused whenever ANY
     firefighter anywhere is mid-rescue - the brief's concern is correct. Demonstrated
     in isolation: _active_physical_pairing(model,"","") -> ('ff_0','victim_9') while
     _active_physical_pairing(model,"victim_3","") -> None.
     HOW OFTEN DOES THE GENERIC PATH TRIGGER AFTER THIS FIX? Zero times - measured
     0/2400: the executor's delay branch is never entered because delay is never
     selected. The question becomes answerable only once the signal plumbing is fixed.
     Also note target_entity is "mission" at runtime (hardcoded wildfire_model.py:1722),
     itself a member of _GENERIC_VICTIM_IDS - so even routing target_entity into
     victim_id would still land on the generic branch.

  2. MAPE-K delay never issues a physical unassign - CONFIRMED, fully open.
     RescueExecutor.execute()'s delay path reaches only managed-abstract appliers
     (_apply_victim_state 552-592, _apply_firefighter_model 595-621,
     _apply_victim_runtime 624-654). The only physical mutator,
     execute_physical_command (:207 -> model.apply_physical_rescue_command :248), is
     unreachable from execute(). A successfully-applied delay CANNOT recall a
     firefighter already en route.
     Additional finding not in the brief: rescue_executor.py:94 gates the whole apply
     block on a truthy victim_id, so with victim_id=="" a delay would skip all three
     appliers yet still return {"applied": True} and log status="success".

  3. NEW - the blocker this work uncovered: route_risk / communication_risk are never
     plumbed to the rescue planner. This is what actually keeps delay dead. It is the
     necessary next step if delay/cancel is meant to function.

  4. NEW - systematic schema mismatch: 42 matching gates audited, 18 DEAD, 8 PARTIAL,

  5. NEW - UtilityEvaluation gives zero separation across all rescue options (every
