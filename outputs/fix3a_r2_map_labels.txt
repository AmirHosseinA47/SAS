SUMMARY
I found every consumer of a victim searcher's executed action label. The label leaves UAVExecutor in two ways. It is written to agent.execution_action in _commit_execution_direction (uav_executor.py:155) and to wind_state["last_action"] (uav_executor.py:2936, local_adaptation_generator.py:1808). It is also returned as result["action"] (uav_executor.py:498), which the dispatcher stores in latest_execution_result[...]["uav_results"] (decision_dispatcher.py:394, 400-401), and the probes read it from there.

Seven consumers change behaviour depending on the label:
1. The stay rule in _commit_execution_direction (uav_executor.py:164-171) is an equality test on "hold", "fire_flank_hold" and FIRE_WAIT_LABEL.
2. execute()'s second-gate exemption (uav_executor.py:444-460) uses equality on "rtb_waypoint", "yield_step_aside", "hold" and "victim_search_escape_bfs". It also has a substring test: the label contains "retarget_to_interior" AND self._last_escape_method is non-empty. That attribute is never reset when execute() starts, and the executor object persists across steps (decision_dispatcher.py:216-223), so the value can be left over from an earlier step.
3. The gate relabels its own input (uav_executor.py:2792, 2836). Any input containing "retarget" comes out as exactly "victim_search_wind_aware_retarget_to_interior".
4. _sync_wind_search_execution_state (uav_executor.py:2944-2955):
   - equality on "victim_search_wind_aware_sweep" clears force_sweep;
   - substring "hazard_retreat" sets force_interior_retarget, resets the corridor, and blacklists the 5x5 area around the searcher's POSITION for 15 steps.
5. _sync_wind_search_streaks (local_adaptation_generator.py:1751-1761) tests equality on "hold" for hold_streak and substring "wind_aware" for resetting wind_aware_hold_streak.
6. _movement_category_for_action (uav_executor.py:192-199) tests substrings: "hazard" or "escape" gives searcher_hazard_retreat; "wind_aware" or equality "search" gives searcher_coverage; equality "hold" gives searcher_hold; anything else gives searcher_move. This feeds the dashboard, the timeline and the explanation engine. Today FIRE_WAIT and FIRE_RETREAT are shown as "searcher_coverage / searching region".
7. Offline analyzers:
   - _fx3_p3_analyze tests equality on the WAIT/RETREAT constants (lines 26-27, 370), endswith("_fire_wait") (line 243), and YIELD_LABELS plus startswith("hold_escape") (lines 212-224);
   - _mf2_p3_analyze tests equality on "hold" and "fire_flank_hold", equality on "yield_step_aside" and "hold_escape", and substring "fire_flank";
   - _sd_analyze and _fx3_pockets count exact label strings;
   - the three probes (_sd_probe, _fx3_probe, _mf2_probe) and _ffr_harness only record labels; they do not classify them.

agents.py, serve_dashboard.py, wildfire_model.py, the execution log and the path context only display or pass labels through. None of them tests a searcher label. agents.py reads only the execution_stay and execution_yield flags and its own rtb_* labels.

What happens if a step the gate hands to the route keeps its ORIGINAL label (for example ..._sweep):
- execute() applies the gate a second time. The near-field retreat (uav_executor.py:2818-2838) replaces the route's step, which brings back the veto-against-planner livelock.
- A wait under that label is not a stay. It commits the stale selected_dir (uav_executor.py:2266), so the searcher moves blindly.
- If the original label is itself a gate output containing "hazard_retreat", every step blacklists the searcher's position and forces a retarget. The route target then changes each step, and a new target clears the latch (uav_executor.py:2195-2198).
- Analyzers cannot tell these steps apart from ordinary ones. rows_uav column 8 is identical, and only the fx3 "G" and "R" events would show the difference.

What happens with a new distinct SUFFIX (for example <origin>_fire_route):
- It does not contain "retarget_to_interior" (unless the origin does), so it is not exempt from the second gate. The exemption must be extended.
- The "_sweep" equality no longer matches, so force_sweep stays set. That keeps the searcher in the sweep branch (uav_executor.py:1406-1410, local_adaptation_generator.py:4062-4066). This must be decided deliberately.
- "hazard_retreat" is absent, so no blacklist fires. That is correct for the latch.
- The "wind_aware" substring is kept, so the streak reset and the dashboard coverage category are unchanged.
- An origin of "hold_escape" would be counted as YIELD by _fx3_p3_analyze.py:224. An origin containing "escape" would show on the dashboard as a hazard retreat.
- Per-origin wait labels ("<origin>_fire_wait") would break the stay equality (uav_executor.py:170), the fx3 clearance check (_fx3_p3_analyze.py:370) and test_fix3a. Only fire_waits() (_fx3_p3_analyze.py:243) would survive, because it uses endswith.

RECOMMENDATION. Make every relabel conditional on the new switch, so that with the switch at 0 the labels stay byte-identical. rows_uav is an identity field (_fx3_p3_analyze.py:101).
- (R1) Keep FIRE_WAIT_LABEL and FIRE_RETREAT_LABEL (uav_executor.py:2116-2117) as the single canonical labels for every no-path outcome, whatever the origin. The origin is still recoverable from the fx3 G event's in_label.
- (R2) Give every MOVING step the route owns this label: the pre-gate label plus a constant suffix "_fire_route". This covers latched fire-mode BFS steps (uav_executor.py:2239-2242) and every gate-handed step, including ones where the route is not latched.
  - Never build it from a label that starts with "hold" or contains "hazard_retreat".
  - Ignore prefer_bfs_action_label for route-owned steps, so the label never becomes victim_search_escape_bfs.
- (R3) Make these consumer changes:
  - In execute(), exempt route-owned steps by testing the label explicitly (endswith "_fire_route", or equality with the two FIRE constants), or with a per-call ownership flag. Do not rely on _last_escape_method, and reset it at execute() entry.
  - In _sync_wind_search_execution_state, change the sweep test to startswith("victim_search_wind_aware_sweep"), or document on purpose that force_sweep stays set.
  - In _movement_category_for_action, add a first clause for _fire_route / _fire_wait / _fire_retreat that returns a new fine category, and map that category in movement_explainability.py:17-24 (unknown categories currently fall through to searcher_move).
  - In _fx3_p3_analyze, change the test at line 370 to endswith, and add a count of endswith("_fire_route").
  - Send the hand-off through _attempt_pathfinding_toward_target so the fx3 "R" hook and the mf2 ROUTE hook see it (_fx3_probe.py:130-161, _mf2_probe.py:110-129).

A label-based check that part (a) holds: in the shipped arm, no searcher step within 6 of fire or smoke should carry "hazard_retreat" or "_hazard_escape".
