1. THE SILENT EXIT (report row 3) - RE-VERIFIED, HOLDS
================================================================================
EVIDENCE AT HEAD
  wildfire_model.py:5924-5929: step() calls sys.exit(0) when BATCH_SIZE == evaluation_timesteps_counter - 1,
  i.e. on the (BATCH_SIZE + 2)-th call; the model therefore runs BATCH_SIZE + 1 full steps.
  evaluate_scenarios.py:195 --batch-size defaults to 300 independently of --steps (:194, default 300);
  :266-271 catches only Exception, and SystemExit is not an Exception; stdout is redirected inside
  _run_seed, so nothing is printed and `raise SystemExit(main())` never runs - the process ends with the
  model's code 0.
  REPRODUCED here: `evaluate_scenarios.py --scenario D --n 2 --steps 6 --batch-size 3 --seeds 101,202`
  -> exit 0, header line only, no seed row, no summary (outputs/_mf1_item1_repro_head.txt).
  The same exposure exists in three more places: evaluate_extended_metrics.py:113-114 (same 300/300
  defaults), outputs/_ffr_harness.py:149 (params BATCH_SIZE hard 300: a --steps 360 run without
  --set BATCH_SIZE=360 exits 0 with no JSON), and serve_dashboard._start (:449, batch_size from the
  browser, steps up to 600: sys.exit inside a request thread silently kills that request, the browser
  step loop hangs).
  BATCH_SIZE has no other effect on a run: its only reader besides the exit test is the dashboard
  header's display (dashboard_state_builder.py:169, frozen at import to 300).
DESIGN (no switch - nothing that produced results changes)
  (a) ROOT CAUSE, model: step() no longer calls sys.exit. At the start of the over-limit call it prints
      MR1/MR2 exactly as today and raises BatchLimitReached (new, a RuntimeError subclass) whose
      message names BATCH_SIZE, the steps already run, and the remedy. At the END of the last allowed
      step (counter == BATCH_SIZE + 1) it sets self.running = False, which is mesa's own stop signal:
      main.py's ModularServer then ends the run cleanly instead of having its process exited.
  (b) ROOT CAUSE, runners: the batch always covers the run. evaluate_scenarios and
      evaluate_extended_metrics: --batch-size defaults to None -> effective max(300, --steps) (so every
      run of <= 300 steps is unchanged); an explicit --batch-size that cannot run --steps
      (--steps > --batch-size + 1) exits 2 with a message before any seed runs. Harness: params
      BATCH_SIZE = max(300, --steps) (unchanged for <= 300 steps; --set still overrides). Dashboard:
      BATCH_SIZE = max(batch_size, steps), and /step returns {"error": ...} instead of dying.
  (c) FAILURES CAN NO LONGER LOOK LIKE SUCCESS: evaluate_scenarios catches Exception AND SystemExit per
      seed, prints the ERROR row to stdout and stderr, and exits 1 if ANY seed failed (after printing
      the successful rows' summary, marked FAILED k/n). _run_seed checks after its loop that the model
      advanced exactly --steps steps (evaluation_timesteps_counter), and raises if not - so a model
      that silently stops stepping is a failed seed, not a short success. The harness gets the same
      step-count check (its uncaught exception already exits non-zero and writes no JSON).
  Unit tests (new): the model raises BatchLimitReached (not SystemExit) past the limit and sets
  running False at the limit; evaluate main -> 2 on an impossible --batch-size; -> 1 with an ERROR row
  when a seed raises; a run with no --batch-size advances exactly --steps steps.
PAPER: nothing reported so far is wrong because of it (every recorded 360-step run pinned BATCH_SIZE).
  From now on a 360-step evaluation needs no batch flag, and a runner that checks exit codes can no
  longer record an empty round as a success.
