5. THE KILL SWITCH AND THE SHIPPED DEFAULT
================================================================================
ROUTE_BLOCK_STALE_CLEAR, ordinal ladder, each rung a strict superset:

  0  off, byte-identical to f4e79d5 (G1)
  1  clear the unassigned, unbound, non-enclosed no-referent unit
  2  rung 1, plus release-then-clear a unit still bound to a terminal referent

Read at CALL TIME from the common_fixed_variables MODULE via
WildFireModel._route_block_stale_clear_mode(), never through the star import and
never at import time. The dead-input test builds the model FIRST and then
monkeypatches cfv, so a frozen read fails it. Clamping matches base_station_mode:
0/1/2 pass through, -5 -> 0, 99 -> 2, "bad" -> 1, None -> 1, and a MISSING
attribute -> 1 (pinned separately, since the junk rows reach only the except
branch and leave the getattr default free to drift). `--set
ROUTE_BLOCK_STALE_CLEAR=0` was verified end to end through apply_scenario_config
on all 23 control runs.

SHIPPED DEFAULT: 1. This is a deliberate, documented DEVIATION from the literal
decision rule in latchfix_part1.txt section 6.4, which said "ship 2 if the gate
passes and rung 2 shows no movement vs rung 1". That antecedent was literally
satisfied - but 6.4 conflated "rung 2 did the same thing as rung 1" with "rung 2
did anything at all", and what was measured is the second. The rule had no arm
for "the higher rung was never exercised". See latchfix_part1.txt section 6.5,
appended rather than rewritten, so the pre-measurement document is not
retroactively falsified.

  RUNG 2 NEVER FIRED. ff_route_blocks_stale_released_total is 0 on every one of
  the 34 sweep runs: all five cleared units had assigned=False, so rung 1 alone
  would have cleared all of them and rung 2 is indistinguishable from it on the
  entire measured population. Release accounting is therefore bit-identical -
  design invariant 9 held without needing its relaxation.

  STATED PLAINLY: rung 2's release path has UNIT-TEST evidence only. THAT IS WHY
  IT IS SHIPPED OFF. Shipping a strict superset whose extra branch never
  executed would add a never-executed code path to a codebase this campaign has
  spent nine rounds removing them from. Rung 2 stays in the tree, tested,
  because s606 m0 south shows the state it exists for (flagged -> route reopens
  -> relabelled "assigned") does occur in real runs. Anyone who wants that
  closure can set 2 and loses nothing on any run recorded here either: the
  measured behaviour of rungs 1 and 2 is identical across all 34 sweep runs.

  WHY THE SWITCH-2 EVIDENCE TRANSFERS TO THE SHIPPED RUNG. It is MEASURED, not
  argued - see 5.1 - and the code says the same thing. Rung 2 differs from rung 1 in
  exactly two places. (a) MEMBERSHIP: `stale` additionally admits route_blocked
  units that are still `assigned`. (b) THE CLEAR: a candidate for which `bound`
  is true is released and cleared at rung 2 and skipped at rung 1. Every path
  through (b) that does anything increments
  ff_route_blocks_stale_released_total, which is 0 on 34/34 runs, so (b) never
  fired; the only other outcomes are the two `continue`s (fire-enclosed, or a
  refused executor call), which `continue` identically at rung 1. And (a) alone
  has no side effect: the window it opens - `blocked` empty while `stale` is not
  - executes only the victim_cells build, which is a pure read (no write, no
  print, no RNG draw), and then either falls to a recovery loop over an empty
  `blocked` or reaches (b).
