PART 1, Q2 - CAN A QUEUED REMOVAL FAIL OR BE SKIPPED?
================================================================================

Five distinct paths exist. Only the first is of any real interest.

2.1  OUTER `except Exception: pass` (2222 / 2282-2283)  -- THE REAL MECHANISM
--------------------------------------------------------------------------------
The queue is emptied at 2224 BEFORE the loop runs. If anything inside the loop
raises past the inner handlers, the loop aborts and every entry not yet reached
is gone from the queue permanently.

Calls inside the loop that are NOT individually wrapped:
    2240  self._victim_id_from_agent(agent)
    2242  self._finalize_rescued_victim(vid, agent)
    2273  self._victim_id_from_agent(rescued_victim)
    2276  self._finalize_rescued_victim(vid, rescued_victim, firefighter_id=ff_id)
    2280  self._recycle_firefighter_after_exit(agent)

_finalize_rescued_victim (4206-4247) is the deep one: it reaches
_firefighter_id_for_victim, _enqueue_rescue_incident and _process_rescue_incidents,
which descend into the planner, the dispatcher and the physical rescue executor.
_recycle_firefighter_after_exit (2077-2115) calls _firefighter_id_from_marker and
_sync_firefighter_operational_knowledge unwrapped (only its grid.move_agent is
wrapped, 2094-2098).

On failure: nothing is logged, raised, counted or surfaced. 2283 is a bare
`pass`. `removed` is returned with whatever partial value it had.

BLAST RADIUS is bounded by list position, and the ordering fact from 1.3 bounds
it tightly: PathMarker entries are always ahead of Firefighter/Victim entries,
and the PathMarker branch is fully wrapped, so it cannot raise. Therefore the
only entries that an abort can lose are Firefighter/Victim entries at the tail.
Measured max queue length was 92, but the losable tail is at most
2 x (firefighters exiting this step) - measured 2 in every observed instance.

ASYMMETRY worth recording: the same helper called at 2285
(_try_dispatch_unresolved_confirmed_victims) sits OUTSIDE the try block. If it
raises there it propagates out of step() and crashes the run - loud. Called from
inside the loop via _recycle_firefighter_after_exit it is silenced. Identical
failure, opposite visibility, decided only by line position.

2.2  TYPE FALL-THROUGH (2227 / 2239 / 2258, no else)
--------------------------------------------------------------------------------
The if/elif/elif chain has no else. An agent of any other type would be dropped
from the queue with no removal, no count and no message. Not reachable today -
the two enqueue sites can only produce Firefighter, Victim and PathMarker.
MEASURED: 0 fall-throughs in 1,717 entries.

2.3  PATHMARKER SCHEDULE GUARD (2234)
--------------------------------------------------------------------------------
`if agent.unique_id in getattr(self.schedule, "_agents", {})` can skip
schedule.remove. Harmless (it only skips when already absent) and
MEASURED: 0 skips in 3,120 calls.

2.4  THE DEAD-FIREFIGHTER BRANCH (2259-2270) IS UNREACHABLE
--------------------------------------------------------------------------------
The only site that sets dead=True is wildfire_model.py:4139 in
_check_fire_casualties, and it (a) does not enqueue the firefighter and (b)
clears exiting/exit_target at 4141-4142:

    4139            ff_marker.dead = True
    4140            ff_marker.status = "dead"
    4141            ff_marker.exiting = False
    4142            ff_marker.exit_target = None

so a dead firefighter can never satisfy the SITE A condition
(`elif self.exiting and self.exit_target`). Firefighter.advance() also returns
immediately on dead (agents.py:457-458). And _check_fire_casualties runs LATER
in the post-move cycle than the removal stage, so a firefighter cannot be queued
and then killed before processing.
MEASURED: 0 dead-Firefighter entries in 1,717. Both grid.remove_agent and
schedule.remove at 2262/2266 are dead code.

2.5  QUEUE PERSISTENCE, GROWTH BOUND, IDEMPOTENCY
--------------------------------------------------------------------------------
DRAINED UNCONDITIONALLY: yes. 2223-2224 empties the queue on every call, and the
call happens every step (4565, unconditional). Entries cannot persist across a
step. Anything appended DURING the call lands in the fresh list and is handled
next step.

GROWTH BOUND: per step, at most 2 x (firefighters at exit) + (PathMarkers in the
schedule). An L-shaped rescue path is at most HEIGHT+WIDTH = 100 markers
(common_fixed_variables.py:20-21). Unbounded growth is not possible because the
drain is unconditional.
MEASURED: max queue length 92; leftover at run end 0 across all 13 runs.

IDEMPOTENCY:
  - same agent twice in one list: _clear_rescue_path dedups by id().
    MEASURED: 0 double-queues.
  - queued after already removed: grid.remove_agent is guarded by
    `pos is not None` and mesa sets pos=None on removal; schedule.remove raises
    KeyError which the inner handler swallows. So re-processing a removed agent
    is a silent no-op. Idempotent by swallow.
  - RE-QUEUE AFTER A DROP: because SITE A never clears self.exiting /
    self.exit_target, a firefighter that was not recycled is still sitting on its
    exit target next step, re-enters the same branch, and appends itself AND its
    victim again. Any 2.1-shaped drop therefore SELF-REPAIRS on the following
    step. This is the single most important behavioural fact in this report and
    it is confirmed empirically in 4.3.

2.6  THE COUNT IS WRONG (2286)
--------------------------------------------------------------------------------
`return removed` counts PathMarkers, Victims and (unreachable) dead
firefighters. It does NOT count `recycled`. A step that recycles a firefighter
and removes nothing reports 0.
MEASURED: 1,717 queued, 1,688 returned; the 29 recycled firefighters are
invisible to the only counter the mechanism has.

5.1  IF A DROP DID PERSIST - the four channels
--------------------------------------------------------------------------------
  scheduler step?  Yes, the agent keeps being dispatched. But Victim.step/advance
     (agents.py:368-372) and PathMarker.step/advance (1186-1190) are all `pass`.
     Cost is dispatch only; no state changes.

  grid cell?  No blocking. MultiGrid permits multiple occupants. Every
     get_cell_list_contents consumer in the tree type-tests for Fire or UAV only
     (agents.py:68, 287, 302, 633, 645; local_uav_monitor.py:85, 140;
     uav_executor.py:4392). A leaked Victim or PathMarker is invisible to pathing.

  counts in evaluate_scenarios / dashboard?  Not from marker presence.
     _build_evaluation (serve_dashboard.py:272-314) derives rescued/dead/
     unreachable/candidate from managed_victims state, firefighter_deaths from
     firefighter_marker_agents flags, and burnt_cells from Fire agents. A leaked
     marker on its own moves no number. What DOES move numbers is the
     un-run _finalize_rescued_victim - see 5.2.
     PathMarkers are not rendered by serve_dashboard at all; only main.py's mesa
     portrayal draws them (main.py:49-57).

  dispatched to / observed / interacted with?  YES - this is the live channel.
     _detect_victims_in_uav_radius (wildfire_model.py:953-1007) iterates
     victim_marker_agents and uses `marker.pos is None` (line 961) as its only
     "this victim is gone" test, plus terminal-status guards at 968-979. A victim
     whose removal was dropped AND whose finalize did not run keeps pos set and a
     non-terminal status, so it is re-detectable and re-dispatchable.

subsequently classified "unreachable".

HONEST SCOPE OF THIS EXPERIMENT: forcing _finalize_rescued_victim to raise
conflates two effects - (i) the rescue bookkeeping not happening, and (ii) the
queue entries after the raise being dropped. It is an upper bound on "the outer
handler swallows every exception on the finalize path", not a clean isolation of
the drop alone. It is reported as such.

5.3  IS THE DROP INERT?
--------------------------------------------------------------------------------
At current scale, YES - completely. 0 natural drops in 3,120 steps, and a forced
single drop moves none of the 13 evaluate_scenarios metrics, leaves no residue,
and leaves nothing pending. The inertness is not luck: it rests on the structural
property in 2.5 (SITE A never clears `exiting`, so the enqueue re-fires every
step) plus the ordering property in 2.1/1.3 (PathMarkers are always ahead of the
only entries that can raise).

The one shape that would NOT self-repair: a drop, followed by the firefighter
dying before it can re-queue (4139-4142 clears exiting/exit_target, so a dead
firefighter never re-enqueues). Its victim marker would then be permanently
leaked and permanently unfinalized. That compound requires an exception that was
never once observed.

PART 3 - VERDICT
================================================================================
                    (E) SILENCE ONLY

Drops do not occur. The mechanism would fail silently if they did, and the
silence is total.

WHAT THE ORIGINAL AUDIT GOT RIGHT
  "the failure is silent - nothing surfaces when a queued removal is dropped."
  Correct, and understated. Nothing surfaces; the only counter is both wrong and
  unread; both invariant checkers stay quiet; and under sustained failure the
  visible output blames geographic isolation instead.

WHAT THE ORIGINAL AUDIT GOT WRONG
  "Agents queued for removal are not always actually removed."
  Not demonstrated, and contradicted by measurement. 1,717 queue entries across
  13 canonical runs at 240 steps: 1,688 removed, 29 recycled, 0 dropped, 0 left
  pending, 0 exceptions on any unprotected path in 3,120 processor calls. The
  audit asserted an outcome ("are not always actually removed") from what is only
  a code smell (a broad `except Exception: pass` around a loop that empties its
  own queue first). The smell is real; the outcome is not.
  It also implies a fragile mechanism. The opposite is true: the mechanism is
  accidentally self-repairing, because agents.py SITE A never clears `exiting`,
  so a firefighter whose removal was dropped re-queues itself and its victim on
  the very next step. A forced single drop moved none of the 13 metrics.

WHY (E) AND NOT (B)
  (B) would fit the letter of "can occur but is inert". (E) is the more accurate
  label because the finding here IS the silence: the drop half did not survive
  measurement, whereas the silence half survived four independent checks and one
  fault injection. Recording this as (B) would preserve the audit's framing as
  though it had been substantiated. It was not.

WHY NOT (C)
  Not (C): the mechanism genuinely CAN drop - 2.1 is a real path with a real
  blast radius, demonstrated by injection. The audit's description of HOW removal
  works is not wrong, only its claim about what happens.

WHY NOT (D)
  No commit in this campaign touched _process_pending_agent_removals,
  _clear_rescue_path or agents.py SITE A. Nothing fixed it; it was never broken
  in the measured sense.

DISCLOSURE - IS IT WORTH ADDING ON ITS OWN MERITS?
--------------------------------------------------------------------------------
RECOMMENDATION: yes, narrowly - but scoped as a diagnostic, not as a behaviour
change. Scoped here only; NOT implemented, per protocol.

The case for it: this is a mechanism whose failure mode is a silent
misattribution. The persistent-fault run showed rescue_rate 50.0 -> 0.0 and
terminal_step 210 -> 64 while the log blamed "geographically_isolated". If this
ever fires in anger, the diagnosis cost is high and there is no breadcrumb.

Minimal scope, in preference order:
  1. Narrow the outer handler at 2222/2282: keep the loop going per-entry instead
     of aborting it (try/except INSIDE the for-loop), and print one line naming
     the agent type, id and exception. Turns a whole-queue abort into a
     single-entry loss AND makes it visible. This is the highest value item and
     the only one that changes behaviour.
  2. Fix the count at 2286 to include `recycled`, so pending_removals stops
     under-reporting by the number of firefighter recycles.
  3. Either consume `cleanup.pending_removals` somewhere real, or drop the
     explanation string at adaptation_manager.py:493 - today it is written and
     never read.
  4. Optional: add an `else:` to the 2227/2239/2258 chain that prints on an
     unexpected type. Zero occurrences measured; cheap insurance against a future
     enqueue site.

Explicitly NOT recommended: any change to the self-repair property in 2.5, or to
the removal ordering in 1.3. Both are load-bearing for the measured inertness.

7.1  WHAT WAS CHANGED
--------------------------------------------------------------------------------
(a) PER-ENTRY CONTAINMENT - wildfire_model.py _process_pending_agent_removals
    The single loop-wide `except Exception: pass` is replaced by a try/except
    around each queue entry. A failing entry is reported and skipped; every
    entry behind it is still processed. Branch bodies are unchanged.

(b) UNPROCESSED ENTRIES ARE PRESERVED (requested addition)
    The queue is still emptied before the loop, so an abort ABOVE the per-entry
    level would still discard the remainder. An outer handler now catches that
    case and calls _requeue_unprocessed_removals(pending[index:]) - `index` is
    advanced before the entry is processed, so the slice is exactly the entries
    the drain never reached. They stay queued and are drained next step.
    The outer handler own body is individually wrapped: it is the last handler,
    and an escape there would abort the whole step.

(c) FAILURES ARE REPORTED - new _report_pending_removal_failure
    Prints `[RemovalFailure] step=N agent=<Type>-<id> <ExcType>: <msg>` and
    increments pending_removal_failures_last_step / _total on the model.

(d) UNHANDLED TYPES ARE REPORTED - new `else:` on the type chain
    An agent that is not PathMarker/Victim/Firefighter is now reported and left
    untouched instead of silently vanishing from the queue.
    Verified: queueing a UAV prints
      [RemovalFailure] step=0 agent=UAV-2500 unhandled agent type
    and leaves it on the grid and in the schedule.

(e) THE COUNT IS FIXED - `return removed + recycled` (was `return removed`)
    Firefighter recycles are no longer invisible. Over the Part-2 sample this
    changes the reported total from 1,688 to 1,717 - i.e. from 98.3% of queue
    entries to 100%.

(f) THE DEAD EXPLANATION STRING IS NOW CONSUMED - adaptation_manager
    `cleanup` gains `pending_removal_failures`, `_collect_post_move_explanations`
    emits `pending_agent_removal_failures=N`, and - the part that actually
    reaches a human - `result["dashboard_summary"]` is set WHEN AND ONLY WHEN
    failures occurred. `dashboard_summary` is the one key of
    latest_post_move_cycle_result that explanation_engine._legacy_summaries
    (709-720) reads, so the previously-dead path now carries the one thing in
    the cleanup stage worth surfacing. Setting it only on failure is what keeps
    clean runs byte-identical.

7.7  WHAT THIS FIX DOES NOT DO
--------------------------------------------------------------------------------
  - It does not make drops less likely. Zero were ever observed; the fix is
    disclosure plus containment, not prevention.
  - It does not re-queue the FAILING entry, only the entries behind it.
    Deliberate: a deterministic exception would otherwise retry forever, and the
    self-heal in 2.5 already re-queues firefighter/victim pairs.
  - It does not touch the self-repair property (2.5) or the removal ordering
    (1.3). Both remain load-bearing for the measured inertness.
  - It does not change `if recycled > 0: _try_dispatch_unresolved_confirmed_victims()`
    at the end of the method, which remains outside the try - unchanged from
    pre-patch, so a failure there still propagates loudly as it always did.
