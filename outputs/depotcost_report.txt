1. WHAT WAS BUILT
================================================================================

1.1  The depot set
--------------------------------------------------------------------------------
BASE_STATION_DEPOTS, a bitmask over five anchors - NW 1, NE 2, SW 4, SE 8,
CENTRAL 16 - built in ASCENDING BIT ORDER so the set is ordered and
deterministic. 0 means "one depot at BASE_STATION_CORNER", the pre-round
behaviour and the shipped default.

The accessor RAISES outside 0..31 rather than falling back. base_station_corner()
silently maps anything outside 0..3 to NW, and the same habit here would have run
arm C as arm A with no error anywhere - the wave would have measured the wrong
thing and reported it as a result. That is this repo's recorded dead-input class
and it is not repeated.

model.base_station carries a "depots" tuple, per-depot berth tables and the
per-unit home index, with "origin" / "size" / "ranked" / "uav_berths" kept as
depot-0 ALIASES so every pre-existing reader - both renderers, the harness, the
eleven shipped geometry tests - works unchanged.

1.2  One berth per UAV PER DEPOT, and a latched target
--------------------------------------------------------------------------------
The single-depot design rests on an invariant stated twice in the source:
"distinct berths are what make the return leg deadlock-free". Giving every UAV a
berth in EVERY depot preserves it exactly - no two UAVs share a berth whichever
depot each picks - with no claim/release protocol.

The target is chosen ONCE at the trigger and latched. Re-running the argmin every
step would make a UAV equidistant from two depots flip its target each step, and
_rtb_direction would reverse with it. rtb_log gains target_depot / target_berth /
home_depot so a return leg is attributable to a depot.

The berth ranking stayed PER BLOCK. A single sort over the union interleaves the
depots: applied to NW+SE it gives uav_berths [(4,45) NW, (45,4) SE, (3,45) NW,
(3,46) NW], a 3/1 split that is an artifact of the (x,y) tie-break. Depot regions
are asserted pairwise disjoint, because the ranking sorts a list not a set.

1.3  base_station_contains is depot-scoped
--------------------------------------------------------------------------------
The docking fallback parks a UAV on any depot cell it has reached when its berth
is blocked. Against the UNION of two depots that would let a UAV dock - and at
mode 3 recharge and re-launch - inside a depot it was never flying to. The index
is threaded through; with one depot it is depot 0 and the union, i.e. unchanged.

1.4  The spawn split
--------------------------------------------------------------------------------
BASE_STATION_SPAWN_SPLIT: 0 all at depot 0 (default), 1 alternate, 2
partition-nearest. Split 2 homes each SEARCHER at the depot nearest its own
crosswind lane centroid. NW and SE fall in opposite halves of both lane axes, so
the correct assignment FLIPS between east and south wind and no wind-blind index
rule can be right for both - measured, and pinned by a test.

Two refactors, both single definitions rather than copies:
  _crosswind_band      split out of _searcher_crosswind_lane
  _uav_role_for_index  split out of _assign_uav_roles
_assign_depot_homes lives outside _build_base_station because the shipped
geometry tests bind that method onto a stand-in exposing only HEIGHT, WIDTH and
NUM_AGENTS.

1.5  The route_blocked gate could not run on an armed arm at all
--------------------------------------------------------------------------------
outputs/_rblatch_campaign2.py took only --scenario / --wind / --steps / --seeds /
--tag. Without --set the only way to gate a non-default configuration was to edit
the shipped default, which this round is forbidden to do, so the gate was
unreachable for arms A-D. Part 2 adds a --set passthrough there and in
_ffr_rbgate.sh. Proven inert in 3.3.

5. A DEFECT IN THE SHIPPED FEATURE - REPORTED, NOT FIXED
================================================================================
Recorded here as a defect in the feature rather than as a note about this round,
per ruling R5. Mode 0 means nobody is exposed today. ANY FUTURE ROUND THAT FLIPS
THE MODE INHERITS IT.

MECHANISM, two independent parts, either fix alone would prevent it:
  (a) agents._rtb_direction CANNOT SIDESTEP ON A PURE-AXIS APPROACH. When dx == 0
      the corresponding direction is None, so `secondary` is None, the swap puts
      None in `primary`, and the function falls through and returns the ORIGINAL
      BLOCKED DIRECTION. The UAV retries the refused move forever.
  (b) THE DOCKING FALLBACK FIRES ON A TRANSIENT BLOCK. It requires only that the
      berth be occupied AT THAT INSTANT - including by a UAV merely passing
      through it - and it permanently parks the returning UAV on another unit's
      berth.

FULL TRACE, dcB east/half/808, this round's own wave:
  step 203  UAV 2501 TRANSITS (3,46) on its way to its own berth (3,45). mesa
            advances agents in order, so 2502 evaluates docking in the same step,
            finds its berth (3,46) momentarily occupied, and the fallback parks it
            permanently on (4,45) - UAV 2500's berth.
  step 203+ UAV 2500 reaches (4,44), one cell short of (4,45), dx = 0. The
            sidestep has nothing to swap to. It retries the blocked move for 38
            steps and ends the run with 35.4 battery in hand.
So the fallback that exists to guarantee ONE UAV's return terminates is what
permanently blocks ANOTHER, and a one-step transit is enough to trigger it.

WHY THIS MATTERS MORE THAN THE PREVIOUS ROUND THOUGHT. That round reported its
five non-arriving mode-2 legs as "still flying home, none failed". They were
permanently deadlocked, all five the same UAV at the same cell for 34-66 steps
with 37-42 battery. It has now reproduced AT MODE 3, prospectively, in an arm
nobody predicted it in.

TEST GAP, closed: tests/test_base_station.py:273 covered only (10,48) -> (4,45),
where dx and dy are BOTH non-zero and a secondary direction exists. The pure-axis
case - the only one where the swap has nothing to swap to - is now pinned by
test_stall_sidestep_cannot_fire_on_a_pure_axis_approach, which asserts the
CURRENT BROKEN behaviour so a fix flips it visibly and is labelled as such.

NOT FIXED HERE because a fix changes mode-2 behaviour and would confound the
placement comparison this round exists to make. It is a separate round with its
own gate.

A SECOND, SMALLER LATENT DEFECT, found by review and unreached by any arm here:
the mechanism-1 planner waypoint publishes the UAV's HOME berth
(local_adaptation_generator.py:2004), not the latched target. At one depot the
two are the same value. With two depots and BASE_STATION_RETURN_MECHANISM=1 a UAV
would be steered to a berth the docking logic is not scoped to, and the trip could
not terminate. All four arms here use mechanism 2.

6. WHAT WENT WRONG OPERATIONALLY
================================================================================
Recorded because one of the two causes is still unknown and a reader should not
assume both are closed.

  CHAIN 1 died during stage 2 with no diagnostic, no traceback and no marker,
  after launching 8 of 13 runs. Its launched runs survived as orphans and kept
  writing correctly; the remaining 5 never started, and the gate and the test
  suite never started at all. CAUSE STILL UNKNOWN. It is NOT the bug below:
  chain 1 had the same bare `wait` but no heartbeat, so its `wait` had nothing to
  block on and would have returned correctly. TWO FAILURES, TWO CAUSES, ONE OPEN.

  CHAIN 2 stalled at the gate stage, and that one is understood - it was the
  heartbeat added to chain 2 to make a silent death detectable:
      heartbeat &                                    # never exits
      bash _dc_rbgate.sh A & bash _dc_rbgate.sh B &
      wait                                           # waits for A, B AND the heartbeat
  Bare `wait` waits for EVERY background job of the shell. Arms A and B finished
  at 11:59:17 and 12:01:07; `wait` blocked on the heartbeat, so the next stage
  never started. Reproduced in miniature: bare wait hangs, `wait "$A" "$B"`
  proceeds. Chain 3 targets every wait at explicit PIDs and completed.

  NO DATA WAS LOST OR CORRUPTED BY EITHER. The pool skips any run whose output
  exists and is non-empty, so both restarts were resumes. Checked explicitly for
  the CR-in-filename failure mode this campaign has hit before: zero files in
  outputs/ carry a control character in the name, and the gate path uses no queue
  file at all - seeds are literal argv.

  ONE PROCESS ERROR OF MINE. I ran a mutation test (deliberately breaking the
  centroid axes to prove a new test had assertion power) IN THE LIVE TREE while
  the wave was reading it. No contamination - the only dcD file predated the
  window by ten hours and _assign_depot_homes early-returns for every arm with
  one depot, so dcA/dcB/dcC cannot reach that line - and every run's spawn homes
  were verified post hoc. It was still careless; mutation testing belongs in a
  worktree.
