    def _move_toward(self, target):
        tx, ty = target
        cx, cy = self.pos
        dx, dy = tx - cx, ty - cy
        if abs(dx) >= abs(dy):
            nx = cx + (1 if dx > 0 else -1 if dx < 0 else 0)
            ny = cy
        else:
            nx = cx
            ny = cy + (1 if dy > 0 else -1 if dy < 0 else 0)
        preferred = (nx, ny)
        dist_before = abs(cx - tx) + abs(cy - ty)

        scored: list[dict[str, object]] = []
        for cell in self._neighbor_cells():
            if self._cell_contains_active_fire(cell):
                continue
            dist_after = abs(cell[0] - tx) + abs(cell[1] - ty)
            scored.append(
                {
                    "cell": cell,
                    "dist_after": dist_after,
                    "improving": dist_after < dist_before,
                    "maintaining": dist_after == dist_before,
                    "adjacent_fire": self._cell_adjacent_to_fire(cell),
                    "smoke": self._cell_has_active_smoke(cell),
                    "preferred": cell == preferred,
                    "risk": self._firefighter_cell_risk(cell),
                }
            )

        if not scored:
            self._mark_route_blocked()
            return

        chosen: tuple[int, int] | None = None
        chosen_tier = 4
        tier_pools = [
            [
                item for item in scored
                if item["improving"] and not item["adjacent_fire"] and not item["smoke"]
            ],
            [
                item for item in scored
                if item["maintaining"] and not item["adjacent_fire"] and not item["smoke"]
            ],
            [
                item for item in scored
                if not item["adjacent_fire"] and not item["smoke"]
            ],
        ]
        for tier_idx, pool in enumerate(tier_pools, start=1):
            if pool:
                chosen_item = min(
                    pool,
                    key=lambda item: (item["dist_after"], 0 if item["preferred"] else 1),
                )
                chosen = chosen_item["cell"]
                chosen_tier = tier_idx
                break
        if chosen is None:
            chosen_item = min(
                scored,
                key=lambda item: (
                    item["risk"],
                    item["dist_after"],
                    0 if item["preferred"] else 1,
                ),
            )
            chosen = chosen_item["cell"]
            chosen_tier = 4

        self._last_move_risk = int(chosen_item["risk"])

        if str(getattr(self, "status", "") or "").strip().lower() == "route_blocked":

5. NEW TRIGGER CONDITION - OPTION A vs OPTION B
================================================================================

OPTION A - relaxed neighbour test.
  "Trigger when every non-burning neighbour fails to reduce distance to target."

  Correctness: FAILS the brief's own acceptance criterion ("does not
  false-trigger on a firefighter that's making slow-but-real progress around an
  obstacle"). Manhattan distance is a local gradient, and going around ANY
  obstacle means walking the gradient sideways or backwards for several steps.
  A fire front lying across the approach is exactly that obstacle. Option A
  fires on every step of a legal, successful detour. It is the textbook local-
  minimum failure: "not descending the gradient" and "stuck" are different
  properties, and the flag's name, its documented meaning ("no safe route") and
  every consumer listed in section 4 mean the second one.
  The probe rerun in section 1 already contains an instance: row 4
  (neighbours_on_fire=3) has exactly one non-burning neighbour, it increases
  Manhattan distance 24 -> 25, and the unit is in no danger of being stuck.
  Option A would raise route_blocked there. Under the section-4 latch, that one
  false positive permanently retires the unit.
  Loosening it to "improve OR maintain" does not rescue it: a concave front
  still forces strictly-backwards steps.

  Cost: cheapest possible - the four values are already computed in `scored`
  (`improving` / `maintaining` are literally there). Essentially free.

  Timeliness: poor. It cannot fire until the unit is already jammed against the
  fire, because while open ground remains ahead the gradient still descends.
  It buys almost no lead time over the current condition - which is the exact
  failure the brief is trying to fix.

OPTION B - live BFS to the current target, active fire impassable.
  "Trigger when no fire-free path exists from the unit's cell to its target."

  Correctness: this IS the property the flag claims and the consumers assume.
    - No false positives on detours: if ANY fire-free path exists, however long
      or convoluted, BFS finds it and the flag stays clear. Slow-but-real
      progress is, by construction, never flagged.
    - True positives are exactly "genuinely stuck": encircled, or the target cut
      off behind a closed front. That is also precisely the condition under
      which the replacement pathway's answer - unassign and send a DIFFERENT
      unit, which may approach from the other side of the front - is the correct
      answer. A local gradient test cannot distinguish "I am stuck" from "nobody
      can get there", and the replacement decision needs the global fact.
    - It strictly dominates the current condition on the cases that matter: if
      all four neighbours burn and the target is not one of them, BFS returns
      None too.

  Timeliness: this is the decisive advantage. Connectivity is a GLOBAL property,
  so it can go false while the unit is 20 cells from any fire and in no local
  danger at all - the moment the corridor closes, not the moment the unit is
  being burned. That is the only way to get a signal with real lead time, and it
  is the thing the brief is asking for. The investigation's own seed 303/east
  case (route measurably unreachable at steps 138, 139, 140 with route_blocked
  never set) is precisely an Option B true positive that Option A would also
  have missed at 138.

  Cost: a 4-neighbour BFS over 50x50 = 2500 cells, plus one _fire_cells() scan
  of the schedule to build the impassable set.
    - Call frequency here IS higher than the death investigation's per-step
      dispatch checks, as the brief notes: _move_toward ran 1685 times across the
      18 runs (~94/run) versus 57 dispatches. Upper bound is NUM_FIREFIGHTERS x
      steps = 2 x 240 = 480 calls/run for scenario D.
    - But the comparison that matters is against what advance() ALREADY does per
      step: _fire_cells() is an O(all schedule agents) scan (~2500 Fire agents)
      and advance() already calls it on the survival-retreat, idle-retreat and
      moving-to-victim paths, and _needs_immediate_survival_retreat() calls it
      again. One more such scan plus a bounded BFS is the same order as work
      already being done every step.
    - I am not asserting this - the BEFORE campaign (outputs/_rb_campaign.py)
      instruments _fire_cells and BFS separately with perf_counter and the
      measured per-run cost is reported in Part 3 against a ~6-7 min/run
      baseline. If it is not negligible, that is reported rather than assumed.

DECISION: **OPTION B.**
  Option A is rejected on correctness, not on cost: it fires on exactly the case
  the brief names as the false positive to avoid, it does so on the very first
  constructed scenario in the existing probe, and given the section-4 latch each
  false positive is permanent. Option B is the only one of the two whose
  trigger condition matches the meaning the flag's consumers already depend on,
  and the only one that can fire before the unit is already in the fire.

  BFS details, matching outputs/_ffdeath_probe._bfs_path_len exactly (validated
  in the firefighter-death investigation; not reinvented):
    - 4-neighbour, in-bounds via the same grid bounds test;
    - impassable = cells containing an actively burning Fire agent
      (self._fire_cells(), one scan, then set membership - NOT
      _cell_contains_active_fire per cell, which would do a grid content lookup
      per visited cell);
    - the TARGET cell is reachable even if it is itself burning (the dst test
      precedes the blocked test). Deliberate: a victim's cell can transiently
      burn, and treating that as "no route" would hand a doomed victim to a
      replacement unit for no gain;
    - the SOURCE cell is not tested for fire - BFS starts there regardless. That
      is what makes the standing-in-fire case answerable at all (section 6).

6. THE STANDING-IN-FIRE GUARD
================================================================================

WHY DOES IT EXIST? Best understanding, stated before deciding:
  The guard is a second, independent veto layered on top of the trigger, and the
  only case it vetoes is "the unit is standing in active fire". A unit in that
  state is killed later in the SAME step, by _check_fire_casualties, which the
  post-move cycle runs at src_extension/adaptation_manager.py:170. The most
  plausible intent is therefore de-duplication and tidiness:
    (a) _check_fire_casualties already runs its own replacement - it issues
        unassign(reason="firefighter_fire_casualty", reset_victim_pending=True)
        at wildfire_model.py:4050-4060 and the casualty incident path re-pairs.
        Marking route_blocked first would produce a second, competing
        replacement attempt for the same victim in the same step.
    (b) it avoids emitting a route_blocked WARNING alert (alert_manager:151/222)
        for a unit that is about to emit a firefighter_dead CRITICAL one step
        later, and avoids leaving "route_blocked" as a dying unit's status.
  I found no comment, test or commit message stating the intent, so this is
  inference from the surrounding code, not documented fact.

WHY IT IS WRONG ANYWAY:
  - Both concerns are already handled elsewhere. The duplicate-replacement worry
    is covered by _blocked_replacement_attempted (one attempt per (ff,victim)),
    by _rescue_incident_seen_keys, and by the fact that once the unit is
    unassigned the casualty path's own unassign finds no active pairing and is a
    no-op. The status-tidiness worry is covered by _check_fire_casualties
    overwriting status to "dead" at :4061 regardless.
  - The ordering actually favours firing. route_blocked is processed
    SYNCHRONOUSLY inside schedule.step() (_on_firefighter_route_blocked calls
    _process_rescue_incidents itself), whereas the casualty replacement happens
    later, in the post-move cycle. Marking it gets the replacement dispatched one
    phase EARLIER in the same step. The brief's own suggested rationale -
    "replacement logic could then act on it a step earlier for whichever unit is
    dispatched next" - is correct and is a real, mechanical gain, not a
    hypothetical one.
  - Setting route_blocked also EXCLUDES the dying unit from being selected as its
    own replacement (:2389 and :3330 both filter route_blocked), which is
    strictly desirable.
  - And it is the single most informative moment in the whole signal: it is the
    only time the system knows, before the death, that this unit is finished.
    Suppressing it there is suppressing the one sample that matters.

DECISION: **REMOVE THE GUARD** (i.e. invert its purpose, per the brief's third
option: mark route_blocked immediately in this case).
  Concretely, `_mark_route_blocked` keeps only its idempotence check
  (do nothing if already route_blocked) and drops the
  `if not self._cell_contains_active_fire(own cell)` veto.

  Note this is a clean separation of concerns rather than a loosening: after the
  change the TRIGGER decides when to raise the flag, and _mark_route_blocked
  just raises it. If the unit is standing in fire but still has a live path, the
  new trigger simply does not fire and the flag is not raised - the guard was
  never what protected that case.

  Residual risk accepted and named: if a unit standing in fire survives (its
  cell's Fire burns out before _check_fire_casualties runs in the same step), it
  will have been marked route_blocked and unassigned. Under the section-4 latch
  it would then be permanently retired. Measured in Part 3.

  Narrowing was considered and rejected: "suppress only when the unit has no
  victim" is redundant, because _on_firefighter_route_blocked already returns
  early when rescued_victim is None.

agents.py only.

  D1. Add a helper `_path_exists_avoiding_fire(self, src, dst, fire_cells)` -
      the _ffdeath_probe BFS, returning bool. Uses grid.out_of_bounds for the
      bounds test and set membership for the impassable test; dst reachable even
      if burning; early-out when src == dst.

  D2. In `_move_toward(target)`, before building `scored`, compute
          route_blocked_now = (not self.exiting) and not path_exists(pos, target)
      using one self._fire_cells() call.

  D3. Trigger:  `if not scored or route_blocked_now: self._mark_route_blocked()`
      - `not scored` is KEPT unchanged, so every currently-firing case still
        fires, on every call site, exactly as today. (The two conditions are not
        strictly nested: if the target IS one of the four burning neighbours,
        scored is empty but BFS reports reachable.) No existing behaviour is
        removed.
      - `not scored` keeps its `return` (the unit genuinely has nowhere to step).
        `route_blocked_now` does NOT stop the unit - it raises the flag and then
        falls through to the normal tier selection and move. Halting movement
        would be a retreat-behaviour change, which is explicitly out of scope.

  D4. Suppress the status auto-clear at the tail of _move_toward when
      route_blocked_now is true, otherwise the flag would be set and cleared
      within the same call. When route_blocked_now is false the tail clears the
      flag exactly as today - this is the intended hysteresis: blocked while the
      route is gone, clear on the first step taken with a live route.

  D5. `_mark_route_blocked`: drop the standing-in-fire veto, keep idempotence.

SCOPING THE NEW TRIGGER TO THE APPROACH PHASE (`not self.exiting`)
  Deliberate, and stated here rather than discovered later:
    - Site 2 (moving to victim) and site 1 (survival fall-through) are the
      approach phase. The new trigger applies there. Site 2 becomes reachable
      for the first time - that is the entire point of the change.
    - Site 3 (exiting with victim) keeps ONLY the existing `not scored`
      condition, byte-identical behaviour to today. Reason: section 4's second
      finding - for a unit carrying a victim, the replacement pathway's response
      (unassign, drop the victim, dispatch someone else) is the wrong response,
      and would additionally break rescue finalisation. The correct handling of a
      blocked EXITING unit is a retreat/exit-routing question, and both retreat
      logic and standby/release posture are explicitly out of scope for this
      round. Making the flag fire more often on that path would change rescue
      outcomes through a pathway nobody has designed.
  If Part 3 shows the approach-phase signal is sound and the consumer latch is
  fixed, extending to the exiting path is a well-defined follow-up.

INTERACTION WITH THE THREE CALL SITES - explicit answer to the Part 2 question
  site 472 survival fall-through : trigger ALREADY reachable; now also fires on
                                   the no-path case. Intended. This is the path
                                   where units die, and it currently only fires
                                   when the unit is already boxed in.
  site 521 moving to victim      : trigger CURRENTLY UNREACHABLE; becomes
                                   reachable. INTENDED, and the primary purpose
                                   of the change - it is the only site that can
                                   fire while the unit is still far from fire and
                                   therefore the only source of lead time.
  site 556 exiting with victim   : UNCHANGED. Already reachable today (contra the
                                   brief); scoped out of the new trigger by the
                                   `not self.exiting` guard for the reasons above.

WHAT IS NOT CHANGED
  - _survival_move, _assigned_one_step_retreat, the idle-retreat state machine,
    the tier pools and the chosen-cell selection: untouched.
  - rescue_planner.py and all dispatch/pairing logic: untouched.
  - Every consumer in section 4: untouched. The two consumer findings above are
    reported, not fixed.

A. COST QUESTION IS ALREADY ANSWERED BY EXISTING CODE ON THE HOT PATH
   wildfire_model.py:3685 already contains `_safe_path_reachable_cells` -
   "4-connected BFS; active fire cells are impassable, burnt cells are not" -
   i.e. exactly the Option B primitive. It is called from
   `_update_unreachable_victims` (:3741), which model.step() runs
   UNCONDITIONALLY on EVERY step (wildfire_model.py:4487), together with
   `_active_burning_cells()` (:3669), an O(all schedule agents) scan identical
   in cost to `_fire_cells()`.

   So a full-grid multi-source fire-impassable BFS plus a full fire-cell scan is
   already paid once per step, unconditionally, today. Option B adds at most
   NUM_FIREFIGHTERS such units of work per step (2 in scenario D), and its BFS
   early-exits on reaching the target rather than flooding the whole grid.
   The measured perf_counter split from the campaign is reported in Part 3, but
   the design question "is a BFS per _move_toward call affordable at this call
   frequency" is settled: the codebase already does strictly more than this every
   step, on a path that runs even when no firefighter is moving.

   This also settles a secondary question - Option B is not a new concept being
   introduced into the model. "Safe-path reachability with active fire
   impassable" is already the codebase's own definition of reachable, used to
   decide whether a VICTIM is unreachable. Option B simply applies the same
   definition to the firefighter's own route. Option A would introduce a second,
   inconsistent notion of blocked.

   This confirms the static analysis in section 4: every consumer behaves
   sensibly on the firing itself, and the single thing that is wrong is that
   nothing ever clears the flag once the replacement pathway has removed the
   unit's target. It is a genuine latch, it is a consumer-side defect
   (wildfire_model.py:3454 explicitly preserves route_blocked through unassign),
   and per the brief it is REPORTED, not fixed in this round.

   Design consequence, and the reason Option A is now doubly rejected: under this
   latch every false positive is permanent and costs a whole firefighter for the
   rest of the run. A trigger that fires on "no neighbour improves my Manhattan
   distance" would retire units during ordinary detours. With only 2 firefighters
   in scenario D, two false positives retire the entire fleet.
