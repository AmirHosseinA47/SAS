================================================================================
FIREFIGHTER DEATHS UNDER DISPATCH PRESSURE - DIAGNOSIS
Manhattan-only pairing: does "available" != "reachable" actually kill people?
Read-only investigation. No production code changed.
================================================================================

VERDICT
-------
  (C) NOT SUPPORTED.

  The code defect is REAL and confirmed exactly as characterised
  (select_rescue_assignment sorts on Manhattan distance ONLY; "available"
  contains no reachability test of any kind). But it is NOT what is killing
  firefighters.

  Over 18 instrumented runs (scenario D: wind east x13 seeds, wind south
  x5 seeds, 240 steps each), 57 dispatch decisions and 16 firefighter deaths:

    * dispatches issued with NO live path to the victim
      (BFS, active fire impassable, evaluated AT DISPATCH TIME) : 1 / 57  (1.8%)
    * deaths in category (a) - dispatched into an already-blocked
      or already-partially-blocked corridor                     : 0 / 16  (0%)
    * deaths in category (b) - correct dispatch, fire spread in  : 2 / 16  (12.5%)
    * deaths in category (c) - something else                    : 14 / 16 (87.5%)

  The single no-path dispatch (seed 333/east, step 42) did not produce a
  death; that firefighter survived it.

  WHAT IS ACTUALLY DRIVING THE DEATHS (category (c)):
  Firefighters are being killed while IDLE and UNASSIGNED, pinned against the
  grid boundary, not while walking into a victim.

    * 14 / 16 deaths occurred when the firefighter had no target_pos, i.e. was
      not en route to anybody. Only 2 / 16 died within 2 steps of last being
      observed en route.
    * 12 / 16 deaths occurred on a grid-boundary cell (x in {0,49} or
      y in {0,49}).
    * median gap between "last step observed en route" and "died" = 40 steps;
      several are 100-200 steps. One firefighter (seed 909/east) died having
      never received an assign dispatch at all.

  The mechanism is: a firefighter finishes (or loses) a rescue at the map
  edge, goes to standby there, and the wind-driven fire front eventually
  sweeps to that edge. The idle-retreat logic (_survival_move /
  _idle_needs_survival_move) then has nowhere left to retreat to - it is
  already against the wall - so it holds and burns. This is a standby-posture
  / no-safe-harbour problem, not a pairing problem. Fixing pairing would not
  have saved any of these 14.

  There is exactly ONE death in the whole sample with any pairing signal at
  all (seed 101/east dispatch at step 16; see step 7 below). One of sixteen.

SEPARATE FINDING - route_blocked (see Part 3 / Part 10)
-------------------------------------------------------
  route_blocked is a near-dead signal, and its guard suppresses it in exactly
  the lethal case. Confirmed both by construction and empirically:
    - 3 firings across 18 runs / 1685 _move_toward calls (0.18%).
    - 0 firings in either 5-seed batch; all 3 came from one 8-seed batch.
    - _mark_route_blocked was reached only 5 times total, and 2 of those 5
      were suppressed by its own guard because the firefighter was already
      standing in fire.
  This is a real defect worth fixing on its own merits (Part 10).

PART 1 - RE-VERIFYING THE MECHANISM CLAIM
================================================================================

1. select_rescue_assignment - IS IT MANHATTAN ONLY?
---------------------------------------------------
  YES. Manhattan distance only. Route safety appears nowhere - not as a hard
  filter, not as a penalty, not as a tiebreaker. The tiebreaker is the
  firefighter ID string.

  src_extension/planning/rescue_planner.py:515-636. The scoring/sorting logic
  in full (:619-626):

        best_ff: str | None = None
        best_dist: int | None = None
        for ff_s, ff_pos in available:
            dist = _manhattan_distance(victim_pos, ff_pos)
            if best_dist is None or dist < best_dist or (dist == best_dist and ff_s < str(best_ff)):
                best_ff = ff_s
                best_dist = dist

  and _manhattan_distance is exactly what it says:

        def _manhattan_distance(a, b):
            return abs(int(a[0]) - int(b[0])) + abs(int(a[1]) - int(b[1]))

  The victim side is not scored at all - victims are sorted by ID string and
  needy[0] is taken (:558-565):

        needy.sort(key=lambda item: item[0])
        ...
        chosen_vid, victim_pos = needy[0]

  The whole function is otherwise filtering (which victims need rescue, which
  firefighters are available) and packaging the RescueDecision. The planner
  receives a read-only `snapshot` dict; it has no reference to the model, the
  grid, or the fire agents, so it could not evaluate a route even if it wanted
  to. That is an architectural fact worth carrying into Part 3.

2. THE "AVAILABLE" DEFINITION - EVERY CONDITION
------------------------------------------------
  Two layers, both quoted in full. Neither contains any reachability test.

  Layer 1 - the planner's own filter, rescue_planner.py:577-591:

        for ff_id, entry in firefighters.items():
            ff_s = str(ff_id or "").strip()
            if not ff_s or not isinstance(entry, dict):
                continue
            if bool(entry.get("dead", False)):
                continue
            if bool(entry.get("assigned", False)):
                continue
            if bool(entry.get("route_blocked", False)):
                continue
            if not bool(entry.get("available", True)):
                continue
            pos = entry.get("position")
            if pos is None or len(pos) < 2:
                continue
            available.append((ff_s, (int(pos[0]), int(pos[1]))))

  Layer 2 - what feeds entry["available"],
  wildfire_model.py:2385-2397 (_firefighter_available_for_dispatch):

        def _firefighter_available_for_dispatch(self, ff_marker: Any) -> bool:
            if getattr(ff_marker, "dead", False):
                return False
            status = str(getattr(ff_marker, "status", "") or "").strip().lower()
            if status in ("dead", "route_blocked"):
                return False
            if getattr(ff_marker, "assigned", False):
                return False
            if getattr(ff_marker, "exiting", False):
                return False
            if getattr(ff_marker, "rescue_completed", False):
                return False
            return getattr(ff_marker, "pos", None) is not None

  Full set of conditions for "available": not dead; status not in
  {dead, route_blocked}; not assigned; not exiting; not rescue_completed;
  has a grid position.

  CONFIRMED: reachability is absent. There is no path check anywhere between
  the availability filter and the commit. The decision returned by
  select_rescue_assignment goes straight to RescueExecutor, which applies it;
  no downstream stage re-validates that the chosen firefighter can actually
  get there. The characterisation in the brief is accurate.

3. DOES route_blocked EVER GET SET? (the second suspect)
---------------------------------------------------------
  The suspicion was "any non-fire neighbour exists" is enough to prevent it.
  That is very nearly right, and the truth is slightly worse.

  There is exactly ONE call site, agents.py:961, inside _move_toward:

        scored: list[dict[str, object]] = []
        for cell in self._neighbor_cells():
            if self._cell_contains_active_fire(cell):
                continue
            ... scored.append(...)

        if not scored:
            self._mark_route_blocked()
            return

  _neighbor_cells() is the 4-cell von Neumann neighbourhood, in-bounds only,
  NOT including the firefighter's own cell (agents.py:674-682). So `scored`
  is empty iff EVERY in-bounds von Neumann neighbour is simultaneously
  burning. Confirmed: one non-fire neighbour is enough to suppress it.

  And then the setter itself has a further guard, agents.py:914-921:

        def _mark_route_blocked(self) -> None:
            if not self._cell_contains_active_fire((int(self.pos[0]), int(self.pos[1]))):
                if str(getattr(self, "status", "") or "").strip().lower() != "route_blocked":
                    self.status = "route_blocked"
                    ...

  i.e. a firefighter that is surrounded on all four sides AND standing in
  fire - the case that is about to kill it - is explicitly NOT marked
  route_blocked.

  There is also a structural reason the ordinary approach path can never
  reach it. advance() (agents.py:455-...) calls _move_toward from three
  places. Two of them (the normal "moving to victim" branch, :520, and the
  "exiting with victim" branch, :554) are only reached when
  _needs_immediate_survival_retreat() returned False, and that predicate
  returns True whenever _cell_adjacent_to_fire(cell) - which is true whenever
  any von Neumann neighbour is burning. So on those two paths at least one
  neighbour is guaranteed non-burning, `scored` is guaranteed non-empty, and
  route_blocked is UNREACHABLE by construction. The only path that can reach
  it is the third: survival retreat was needed, _survival_move() failed to
  move the unit, and it fell through to _move_toward at :470.

  EMPIRICAL CONFIRMATION (constructed scenario, not reading alone).
  outputs/_route_blocked_probe.py builds a real WildFireModel, parks one
  firefighter at (25,25) with target (25,40), ignites 0/1/2/3/4 of its von
  Neumann neighbours, and calls advance() once:

    neighbours_on_fire=0    burning_nb=0 self_on_fire=False -> status=assigned       moved_to=(25, 26)
    neighbours_on_fire=1    burning_nb=1 self_on_fire=False -> status=assigned       moved_to=(24, 25)
    neighbours_on_fire=2    burning_nb=2 self_on_fire=False -> status=assigned       moved_to=(25, 26)
    neighbours_on_fire=3    burning_nb=3 self_on_fire=False -> status=assigned       moved_to=(25, 24)
    neighbours_on_fire=4    burning_nb=4 self_on_fire=False -> status=route_blocked  moved_to=(25, 25)
    all-4 + standing IN fire burning_nb=4 self_on_fire=True  -> status=assigned       moved_to=(25, 25)

  Exactly as derived: fires only at 4-of-4, and is suppressed by its own
  guard in the 4-of-4 + standing-in-fire case.

  EMPIRICAL FREQUENCY IN REAL RUNS (18 runs, scenario D, east+south):
    _move_toward calls                        1685
    ... with >=1 burning neighbour              31   (1.8%)
    ... with ALL neighbours burning               5   (0.30%)
    _mark_route_blocked actually called          5
    route_blocked actually SET                   3   (0.18% of moves)
    suppressed by the standing-in-fire guard     2   (40% of the calls)
  Zero firings in the D/east 5-seed batch and zero in the D/south 5-seed
  batch; all 3 came from the D/east 8-seed batch.

  So: not literally never, but ~0.2% of moves, and it misses exactly the case
  it most needs to catch. The blocked-route feedback loop is effectively
  absent, as suspected.

PART 3 - SCOPING

9. THE PRIMARY MECHANISM IS NOT SUPPORTED - HEADLINE
------------------------------------------------------
  Do not scope a reachability-aware-pairing fix as the firefighter-death fix.
  It is not one. On this sample it would address at most 1 of 16 deaths, and
  it would leave the actual mechanism - idle units overrun against the map
  boundary - entirely untouched.

  That said, the two ARE separable problems and the honest reading is:

  (i) The pairing defect is real, cheap to fix, and worth fixing as a
      correctness matter (it produced 1 no-path dispatch in 57 and 1
      passed-over-safer-alternative in 57). It is a small win, and it should
      be described and measured as a small win, not as the death fix. It may
      also matter much more in scenarios with more firefighters - 49% of
      dispatches here had a pool of exactly one unit, so scenario D
      structurally cannot exercise the defect. If someone wants to know
      whether pairing matters at all, the right next measurement is scenario
      A or C (3 firefighters) or an explicit high-firefighter override, NOT a
      fix attempt.

  (ii) The thing that would actually reduce firefighter deaths is a standby /
      release posture change: where does a firefighter go when it has no
      assignment, and does it keep enough clearance from an advancing front
      to survive 200 steps of standing there? 14/16 deaths, 12/16 on the
      boundary. That is a different investigation and should be scoped as
      one, not folded into this.

  Neither is a "fire spread into an already-committed route" problem, so the
  predictive-routing concern the brief raised as the hard case does not
  really arise: only 2 of 16 deaths were en-route at all.

8. IF THE PAIRING FIX IS PURSUED ANYWAY - APPROACH AND HOOK POINT
-------------------------------------------------------------------
  Named only, per instruction. No implementation code here.

  HOOK POINT. Not inside the availability filter. The planner
  (rescue_planner.py) receives a read-only snapshot dict and holds no
  reference to the model, grid or fire agents, so it cannot compute a path
  itself - this is a deliberate managed/managing separation (see
  docs/02_managed_vs_managing.md) and should not be broken. The right shape
  is:
    - the MODEL side, where the snapshot is built
      (wildfire_model.get_rescue_operational_snapshot, :2467-2492), adds a
      precomputed reachability field per firefighter entry alongside the
      existing "available" / "route_blocked" keys - the same place
      _firefighter_available_for_dispatch is already called;
    - the PLANNER consumes it in select_rescue_assignment as a SEPARATE
      TIEBREAKER on top of the existing Manhattan sort at :619-626, not as a
      redefinition of "available".

  WHY A TIEBREAKER, NOT A HARD FILTER / NOT A REDEFINITION OF "available".
  Three reasons:
    - Redefining "available" would change what the `if not available:` branch
      at :592-616 does - that branch already decides between "delay" and
      "mark_unreachable", and feeding it a shrunken pool would silently
      convert reachability failures into unreachable-victim markings. That is
      a behaviour change well outside the stated defect, and this campaign has
      already been burned by exactly that class of side effect.
    - "available" is also consumed by the dashboard, the knowledge model and
      adaptation_manager; it is a fleet-status concept, not a per-victim one.
      Reachability is per (firefighter, victim) pair and does not belong on it.
    - A hard filter makes a no-path situation produce no assignment at all.
      Given the measured pool sizes (49% of dispatches have exactly one
      candidate), a hard filter would mostly just convert "dispatch that
      probably works out" into "delay", which is a rescue-rate regression
      risk with no measured death benefit.
  The conservative shape is: keep Manhattan as the primary key, add
  "has a live path" (and optionally the detour) as a secondary key, so the
  sort only changes when two units are otherwise tied or when one is
  genuinely unroutable and another is not.

  COST. Negligible, measured. A 4-neighbour BFS on the 50x50 grid is ~2500
  cells worst case. This investigation ran a BFS every step for every en-route
  firefighter - several thousand BFS calls per run - on top of the simulation,
  with no observable change in run time; the simulation itself dominates by
  orders of magnitude. Dispatches are rare (57 across 18 runs of 240 steps,
  i.e. ~3 per run). Computing the fire-cell set once per snapshot build and
  running one BFS per candidate firefighter at dispatch time is free at this
  scale. Cost is not an argument against this fix; effect size is.

10. route_blocked - REPORTED SEPARATELY AS REQUIRED
-----------------------------------------------------
  Independent of the pairing verdict, this is a genuine defect.

  What is wrong, precisely:
    (i) The trigger is far too strict. route_blocked is set only when ALL
        in-bounds von Neumann neighbours are burning simultaneously
        (agents.py:958-961). Measured: 0.30% of _move_toward calls reach that
        state; 0.18% actually set the flag.
    (ii) On the two ordinary approach paths (advance() :520 and :554) it is
        UNREACHABLE by construction, because reaching those branches requires
        _needs_immediate_survival_retreat() == False, which requires
        not _cell_adjacent_to_fire(), which guarantees a non-burning
        neighbour exists. Only the fall-through at :470 (survival retreat
        was needed but _survival_move() could not move) can ever set it.
    (iii) Worst of all, _mark_route_blocked's own guard (agents.py:915)
        suppresses the flag when the firefighter is standing IN fire - which
        is the step immediately before wildfire_model.py:4060 kills it.
        Measured: 2 of the 5 calls in 18 runs were suppressed this way.

  Consequence: once a firefighter is committed to an approach, the system has
  no working feedback that the route has gone bad. The planner's
  `if bool(entry.get("route_blocked", False)): continue` filter
  (rescue_planner.py:583), the replacement-after-blocked reason path
  (:596-599), the alert_manager route_blocked alert, and the
  adaptation_manager / rescue_executor status handling for "route_blocked"
  are all effectively dead code in practice. There is a whole replacement
  pathway wired up behind a signal that fires 3 times in 18 runs.

  Note the interaction with the pairing question: this campaign's suspicion
  was that route_blocked never firing is what lets bad dispatches stand. The
  data says the dispatches were not bad. But the reverse still holds - the
  signal being dead means the system also cannot react to the 2 category-(b)
  deaths, where the route WAS clear at dispatch and closed afterwards. In
  seed 303/east the route to the target was measurably unreachable at steps
  138, 139 and 140 and route_blocked was never set; in seed 606 and 333 it
  did fire, and both firefighters died anyway a few steps later. So even when
  it fires it fires too late to matter. A meaningful fix here is a threshold
  change (e.g. "no non-adjacent-to-fire neighbour improves my distance", or
  a live-path check against the target) plus removal of the standing-in-fire
  suppression - but that is a separate scoping exercise and, on this
  evidence, should also not be sold as the death fix.
