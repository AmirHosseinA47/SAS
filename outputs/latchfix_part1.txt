3. THE FIX CANNOT STRAND A UNIT DIFFERENTLY  (Part 1, item 3)
================================================================================

70e1b33 was exactly this shape - a unit correctly released but left permanently
undispatchable - so this section is the one that decides whether the fix ships.
Three adversarial passes were run against the design; two found a real gap, and
the design below is the amended one.

--------------------------------------------------------------------------------
3.1  WHAT "RE-ENTERS THE DISPATCH POOL" REQUIRES - enumerated, not assumed
--------------------------------------------------------------------------------
_firefighter_available_for_dispatch (:2967-2978) requires, in order:
    not dead                       - the unassign does not touch it; the pass
                                     already filters it at :2544
    status not in (dead, route_blocked)   <- THE ONE THE FIX CHANGES
    not assigned                   - nulled by the unassign at :4266
    not exiting                    - nulled at :4269
    not rescue_completed           - NOT tested by the pass's eligibility loop;
                                     the fix must add it
    pos is not None                - filtered at :2550
and the planner (rescue_planner.py:588-592) additionally drops on the snapshot's
`route_blocked` and `available` keys, both derived from the same two facts.

So after `status = "available"` + `_sync_firefighter_operational_knowledge`, an
unassigned latched unit satisfies EVERY condition. Verified against the shipped
test that already asserts precisely this for the D6 site:
tests/test_phantom_rescue_release.py:590-595 asserts
`ff_b.status == "available"` and `model._firefighter_available_for_dispatch(ff_b)
is True` after the same clear. The new branch will assert the same thing plus
the snapshot key.

WHY "available" IS THE RIGHT LABEL AND NOT SOMETHING ELSE: it is exactly what the
agent's own clear computes for an unassigned unit (agents.py:1816), and the only
status that maps through the else arm at :3946-3954 to availability "available" /
route_state "idle" / route_blocked False. "en_route"/"assigned" would recreate
the reported-busy divergence 70e1b33's docstring names; "dead"/"off_grid" are
impossible - `dead=True` is written at exactly one site (:4885) always paired
with status "dead" at :4886, and `off_grid` is written together with pos=None at
:2287-2295, so route_blocked and off_grid cannot coexist.

WHERE THE WRITE MUST GO: the MARKER, never managed_firefighters. 70e1b33's commit
message calls the managed-state guard at :4279-4288 "provably inert" precisely
because the unconditional _sync_firefighter_operational_knowledge at :4324
re-derives every reported field from the marker
(_derive_firefighter_operational_fields, :3874). Anything written elsewhere is
erased. Write status, then sync, per unit - matching :2588 -> :2594 and
:3563 -> :3564.

--------------------------------------------------------------------------------
3.2  THE GAP TWO INDEPENDENT ATTACKS FOUND - and the amendment
--------------------------------------------------------------------------------
The pass's eligibility loop filters `if getattr(ff_marker, "assigned", False):
continue` at :2546. A branch that iterates the resulting `blocked` list
INHERITS that filter - and the second-block latch is exactly the shape that
KEEPS assigned=True:

  step N     FF_A assigned to V. Route closes. First raise: attempt_key (A,V)
             is new, so :3335 records it and the unassign fires. Ordinary latch.
  step N+m   the pass clears FF_A on a path to SOME victim cell, then
             :2599-2600 kicks _try_dispatch_unresolved_confirmed_victims. V has
             no visible claimant (_find_active_firefighter_for_victim needs
             `assigned` AND skips route_blocked), so V is re-dispatched - and the
             planner picks by Manhattan, so FF_A can be sent straight back onto
             the still-blocked V route.
  step N+m+1 FF_A blocks again on V. attempt_key (A,V) is ALREADY in
             _blocked_replacement_attempted -> :3333 returns BEFORE the unassign.
             FF_A now holds status="route_blocked", assigned=True,
             target_pos=Vcell, rescued_victim=V.
  step N+p   V is marked UNREACHABLE. Neither unreachable route releases FF_A
             (section 2.2). All victims terminal.
  step N+p   the pass runs. FF_A was rejected at :2546 on assigned=True, so it is
             not in `blocked`, and a branch iterating `blocked` never sees it.

  Variant A (no path ever reopens): FF_A ends route_blocked + assigned, bound to
            a cancelled victim, refused by all four gates.
  Variant B (a path reopens): agents.py:1816 writes status="assigned" because
            assigned is True. FF_A is then STILL undispatchable - now at :2973
            on `assigned` instead of :2971 on status - and INVISIBLE to any gate
            that counts `status == "route_blocked"`. A silent stranding.
            VICTIM_TERMINAL_STATUSES at agents.py:645 is ("dead","rescued") and
            does NOT contain "unreachable", so the unit keeps chasing the
            cancelled victim's live cell and can even carry it out.

AMENDMENT, and it is the reason the branch does NOT reuse `blocked`:
  - build a SEPARATE candidate list `stale` in the same loop, with the same
    filters MINUS `assigned`, PLUS `rescue_completed`;
  - for a candidate that is still bound, release it FIRST through the audited
    executor path with metadata={} - NOT reset_victim_pending, which would
    relabel the terminal victim back to "confirmed" at :4306-4308/:4316 - and
    only then set status="available".
This is safe by the branch's own trigger: `_any_victim_needs_rescue()` is already
False, so any referent still bound is terminal by construction and the release
cannot steal a live claim. It is put behind rung 2 of the ladder (section 4) so
it is separately measurable and separately killable, because it is a shape the
34-run sweep never produced.

`exiting` stays filtered in BOTH lists: an exiting route_blocked unit keeps a
live clear (agents.py:1198 -> :1816, with route_blocked_now pinned False at
:1740-1744), so it is not stranded and must not be touched.

3.3  WHAT WAS ATTACKED AND HELD
--------------------------------------------------------------------------------
  70e1b33's CORNER TRAP cannot reach the branch - three independent blocks:
    (a) a carrying unit is never a candidate. `rescued_victim` non-None is
        written at exactly one site (:4174) whose block also sets assigned=True
        (:4172), and after pickup agents.py:1141 sets exiting=True, which both
        lists filter.
    (b) even if it were, the carried victim keeps a grid position -
        agents.py:1197-1203 moves it with the carrier every step - so
        `_victim_needs_rescue` is True, `victim_cells` is NON-empty, and the

    (c) the distance-zero false positive has no analogue: the branch performs
        ZERO reachability tests. 70e1b33's bug was a false POSITIVE from a path
        test; there is no path test here.
  ENCLOSURE SEMANTICS are identical over the reachable domain. _neighbor_cells
    (agents.py:1316-1322) is 4-connected and in-bounds-filtered, so it is empty
    only on a 1x1 grid - the `bool(neighbors) and` divergence between

--------------------------------------------------------------------------------
3.4  THE SAFETY ARGUMENT, CORRECTED - "monotone victims" is FALSE
--------------------------------------------------------------------------------
The diagnosis (section 8.3) justifies safety by claiming _any_victim_needs_rescue
is monotone. IT IS NOT, and the fix must not be defended by it:

  :4306-4308  the reset_victim_pending arm of the unassign sets
              victim_state.status = "confirmed" guarded only against
              ("dead","rescued") - so "unreachable" IS resurrected;
  :4316       writes victim_marker.status = "confirmed" with NO guard at all;
  :4874-4885  the casualty unassign carries reset_victim_pending and is not
              gated on _victim_needs_rescue.

THE LOAD-BEARING FACT IS A DIFFERENT ONE, and it must be what the comment cites
and what a test pins:

  mark_unreachable also sets state.cancelled = True (:4335) and
  state.unreachable = True (:4339). reset_victim_pending resets NEITHER.
  get_rescue_operational_snapshot exports both (:3038-3043), and
  rescue_planner.py:556-558 drops any victim carrying either from `needy`.
  Only :4217 (assign) and :4414 (finalize) ever clear those flags, and both need
  the dispatch that cannot happen.

So no dispatch can follow the branch - because two booleans are never reset, not
because victim status is monotone. If a later round makes reset_victim_pending
clear cancelled/unreachable, this branch would silently become a source of
zero-path-evidence dispatches. A test must pin it (section 5, case 10).

3.5  HOW RE-ENTRY WILL BE VERIFIED - ASSERTED, NOT INFERRED (gate item 5)
--------------------------------------------------------------------------------
Three independent assertions, all mechanical:

  (i)  UNIT TEST, at the moment of the clear: for every cleared unit assert
       status == "available", assigned is False, rescued_victim is None,
       target_pos is None, _firefighter_available_for_dispatch(...) is True, and
       get_rescue_operational_snapshot()["firefighters"][ff]["route_blocked"] is
       False and ["available"] is True. Both rungs, including the bound case.
  (ii) IN-RUN INSTRUMENT, outputs/_lf_assert.py (new, read-only): wrap the clear
       and record, for every cleared unit and every subsequent step, the tuple
       (status, assigned, exiting, dead, pos, _firefighter_available_for_dispatch,
       _any_victim_needs_rescue). Assert at end of run that each released unit is
       in exactly one of: dispatchable; dead; off-grid; or available-with-no-work
       (i.e. _any_victim_needs_rescue False for every step after the clear).
       Fail the run loudly otherwise. This is the "account for it" requirement.
  (iii) WHOLE-SAMPLE SCAN over ff_steps in every _ffr_ artifact of both fix arms:
       no unit ends alive, on-grid, not fire-enclosed, with a terminal referent
       and _firefighter_available_for_dispatch False - which, per section 3.2
       Variant B, means checking `assigned` as well as `status`, not status alone.

4. THE KILL SWITCH  (Part 1, item 4)
================================================================================

--------------------------------------------------------------------------------
4.1  ROUTE_BLOCK_STALE_CLEAR - an ordinal ladder, 0 / 1 / 2
--------------------------------------------------------------------------------
  0  OFF. Kill switch. Provably byte-identical to f4e79d5, stdout included.
  1  Clear a route_blocked flag on a unit that is alive, on the grid, not
     exiting, not rescue_completed, NOT fire-enclosed, UNASSIGNED and unbound,
     when no victim needs rescue. This is the entire MEASURED population -
     all six latched units in the 34-run sweep and both baseline-arm latches.
  2  Rung 1, plus: a unit still assigned/bound to a terminal referent is first
     released through the audited executor unassign, then cleared. Section 3.2.

A ladder, not a bool, for the reason BASE_STATION_MODE documents for itself at
common_fixed_variables.py:167-175: each level is a strict superset of the one
below, so a level-N vs level-(N-1) comparison attributes exactly one increment.
Numeric for the reason base_station_corner gives at agents.py:585 - `--set`
never has to carry a string.

PROPOSED DEFAULT: 2, contingent on measurement.  [OUTCOME: 1. See 6.5.] Rung 2 is a strict superset with
the same trigger and the same guards, and it is the only rung that closes the
Variant B silent stranding. But rung 2 acts on a shape the sweep never produced,
so section 6.4 states the decision rule that can drop the default to 1 or 0.
This is the base-station round's discipline: ship the default the measurement
supports, not the one the design prefers.

--------------------------------------------------------------------------------
4.2  READ AT CALL TIME - the dead-input rule
--------------------------------------------------------------------------------
wildfire_model.py has ZERO `cfv.` uses today (verified) and line 18 is
`from common_fixed_variables import *`. It becomes two lines, mirroring
agents.py:9-10:

    import common_fixed_variables as cfv
    from common_fixed_variables import *

and the accessor is a staticmethod placed next to the guard it is read beside,
after _firefighter_fire_enclosed (3615-3630):

    @staticmethod
    def _route_block_stale_clear_mode() -> int:
        """0 kill switch / 1 unassigned only / 2 also bound. Read at CALL TIME."""
        try:
            return max(0, min(2, int(getattr(cfv, "ROUTE_BLOCK_STALE_CLEAR", 2))))
        except (TypeError, ValueError):
            return 2
    [AS SHIPPED both 2s are 1, the shipped default - see 6.5. The clamp of an
     out-of-RANGE number is unchanged: -5 -> 0, 99 -> 2.]

WHY cfv AND NOT THE STAR-IMPORTED NAME, specifically for this file:
apply_scenario_config (src_extension/adaptation/local_adaptation_generator.py:
270-273, verified) sets the attribute on BOTH modules -

    def apply_scenario_config(cfv_module: Any, wf_module: Any, **values: Any) -> None:
        for key, value in values.items():
            setattr(cfv_module, key, value)
            setattr(wf_module, key, value)

- so a bare global read WOULD in fact see a harness `--set` override here. But
the tests set only cfv (test_base_station.py:26,
test_victim_searcher_hazard_retreat.py:63), and any future caller that passes one
module makes the star-imported name dead. Reading cfv is the only form correct
under both, and it is the house pattern (agents.py:561,
src_extension/execution/uav_executor.py:2099). A module-level read would freeze at
import and make the switch silently inert - the dead-input defect this repo has
already hit nine times.

END-TO-END OVERRIDE PATH, verified: outputs/_ffr_harness.py parses every
`--set KEY=VALUE` into `params` and calls `apply_scenario_config(cfv, wf,
**params)` before the model is built, and `_parse_value` parses "0"/"1"/"2" as
int. So `--set ROUTE_BLOCK_STALE_CLEAR=0` reaches the accessor on every call.

6.5  DEVIATION FROM 6.4 - RECORDED AFTER THE MEASUREMENT  [APPENDED 2026-09-08]

unbound, so rung 2's release branch was never entered. 6.4 had no arm for "the
higher rung was never exercised", and its ship-2 clause reads as though absence
of movement were positive evidence of safety. Absence of EXECUTION is not.

THE DECISION: ship 1. Rung 1 is the lowest rung that covers the entire measured
population, and shipping 2 would add a code path with no in-run evidence to a
codebase this campaign has spent nine rounds removing dead and never-executed
inputs from. Rung 2 stays in the tree with its tests, one --set away.

This is consistent with 4.1's own closing sentence - "ship the default the
measurement supports, not the one the design prefers" - which is the principle
6.4 tried and failed to encode.

DISCHARGING 6.4's SHIP-1 OBLIGATION. 6.4 required that, if 1 ships, "the
Variant B shape is then reported as a known-open residual with its measured
count". Done, in outputs/latchfix_report.txt section 7: the state occurred once
across the 34-run sweep (seed 606 D/south mode 0, flagged step 198, route
reopened, relabelled "assigned"), and zero units were left in it at end of run
across all 34 sweep runs and all 23 harness runs.

WHAT THE RULE SHOULD HAVE SAID, for the next round that writes one:
  ship the lowest rung whose behaviour was actually exercised by the
  measurement; a higher rung that never executed is not validated by the
  measurement that failed to reach it.

7. WHAT THIS DESIGN DOES NOT DO
================================================================================
  - It does not touch the hazard-standoff oscillation (diagnosis 4.4). Out of
    scope by instruction, and in the family that measured worse in four rounds.
  - It does not add a path test to the replacement planner. That is the defect
    that put a unit on a reachable_at_assign=false route on seed 202 at step 237
    and it is real, but it changes DISPATCH while victims are live. Own round.
  - It does not scope route_blocked to its (unit, target) pair. That is the
    structural fix for the category; see 2.3.
  - It does not defer the `unreachable` marking while a live but route_blocked
    firefighter exists. That would change when victims are declared terminal and
    is the only thing that could move seed 202's outcome. Own round, and it must
    be measured against the overcorrection metric.
