1.3  CLASSIFICATION -> (a), the dead-input class, seventh instance
--------------------------------------------------------------------------------
(a) applies. The scorer reads inputs that are permanently absent. This is the
same class as _DELAY_CANCEL_BONUS, sop.mission_mode, the role-assignment
string/dict mismatch, should_return_to_normal, belief_gap_regions and
_belief_gap_critical - but broader than any of them: it is not one dead key, it
is the ENTIRE utility vector, 9 of 9.

Explicitly NOT (b): the nine terms are not gated. They are unconditionally
computed and unconditionally appended to raw_terms. They are zero because their
inputs are absent, not because a condition failed to fire.

Explicitly NOT (c): the planner is NOT correctly declining worthless options.
For 0.0 to be a correct verdict the scorer would have to have looked at the
options' value and found none. It never looks: the data on which value would be
judged is never presented to it. And the winner does not win a comparison - it
wins because it is the only option that trips two hardcoded constants. A scorer
that read real inputs and returned 0.0 would be correct; this one is not
reading.

Was a producer ever written and then removed? No.
    git log -S'"fire_contribution"' --all
returns exactly ONE commit - a4a01b4 "Add core project files and update README",
the 2nd of 43, the bulk import - which introduced utility_evaluation.py and its
tests in the same commit. The nine keys appear in the repo in exactly two
places: the scorer reading them, and six test files hand-constructing synthetic
options that carry them. There is no enrichment or adapter layer anywhere
between generation and scoring, and no half-built one to finish. The layer was
never wired, not un-wired.

1.4  IS THE 0.0 UNIFORM ACROSS ALL 22?
--------------------------------------------------------------------------------
For the nine weighted terms, YES - uniform, one cause. Measured: all 22
non-baseline options produce EXACTLY the same nine terms, every value 0.0, and
produce NO additional terms. None of the four conditional terms ever fires for
any of them. Verified across all 68,640 non-baseline scorings.

Two precision points, because "uniform" would otherwise overstate it:

  (i) The generator and scorer vocabularies are not strictly disjoint. Cost_switch
      is partially LIVE-wired: `_compute_switching_cost` (:295-320) reads
      role_switch_count and role_stability_timer, which the role family DOES emit
      (global_adaptation_generator.py:129-130). They arrive as literal None, so
      safe_float() maps them to 0.0. So 8 of the 9 terms are dead-KEY; Cost_switch
      is dead-VALUE. Measured: policy_switching_cost = 0.0 on all 71,760.

  (ii) There are three near-miss key mismatches where the generator computes the
       right idea under the wrong name, all measured inert:
         search_mode_required (generator) vs search_mode (scorer :801-803)
           -> is_search False on all 71,760, so the g_ir recovery boost never fires
         option_type "role_assignment" vs the scorer's test `"role" in ot and
           "change" in ot` (:849-858)
           -> role_reassignment False on all 71,760, so the role-switching cost
              never applies to role-assignment options
         target_regions PLURAL (generator :516/:626/:648) vs target_region
           SINGULAR (global_mission_planner.py:251)
           -> the region branch never fires. This generalizes the
              belief_gap_regions finding: SIX region-shaped keys are generated
              (target_regions, critical_regions, priority_regions,
              candidate_regions, uncertainty_regions, candidate_zones) and NOT ONE
              is read.

So: one cause for the tie, but the scope estimate must account for a second,
serially-blocking mismatch downstream (Part 2), not just this one.

2.1  DESIGN
--------------------------------------------------------------------------------
Arming is applied by wrapping `GlobalAdaptationSpaceGenerator.generate` and
mutating the target option's parameters dict after generation - the same
technique that settled belief_gap_regions and _belief_gap_critical. Five modes,
each the full 13-run canonical sample, each compared seed-matched against the
unpatched control:

  arm_lo          NEGATIVE CONTROL. fire_contribution=0.01 on the fire-front
                  coverage option. The score must move off 0.0 (proving the arm
                  reaches the scorer) yet stay below the ~0.153-0.255 baseline,
                  so selection must NOT change.
  arm_hi          fire_contribution=0.9 on the same option. Score must beat the

  arm_role_dict   the same PLUS uav_assignments as a proper dict in the LIVE role

  arm_role_dict_gen  the same but in the GENERATOR vocabulary ("fire_tracking").

2.4  THE HEADLINE
--------------------------------------------------------------------------------
The armed run is NOT byte-identical - but the arm that works is not the one that
fixes scoring.

  * Fixing scoring alone (arm_hi) makes the planner SELECT the option and changes
    NOTHING ELSE: 13/13 byte-identical outcomes. This is exactly the
    _DELAY_CANCEL_BONUS pattern the round anticipated - a correct fix landing on a
    second dead gate downstream.
  * The second gate is `_uav_assignments_from_params`
    (global_mission_planner.py:233-241). arm_role_str isolates it: the option is
    selected 3107/3120 times, but `assigned_role` is a bare STRING and
    `_string_dict` returns {} for anything that is not a dict, so the
    MissionDecision is empty and outcomes are 13/13 byte-identical.
  * Only when BOTH gates are bypassed (arm_role_dict) do outcomes move - in
    13/13 runs, on eval, agent positions, stdout and role signature.

So scoring is NOT the sole blocker, but it is also not pointless: it is the first
of exactly two serial blockers on the role path, and both are small.

TWO FURTHER MEASURED FACTS THAT BEAR DIRECTLY ON THE MAINTAINER'S NEXT WORK:

  (A) THE FIRE IS UNTOUCHABLE FROM THIS LAYER. burnt_cells is 16053 in every
      single mode, and the fire-map hash is identical in 13/13 runs for EVERY
      arm including the strongest one. Maximal global role reassignment,
      sustained for 239 of 240 steps, changes rescue outcomes and firefighter
      deaths but does not perturb the fire by one cell. Whatever the global
      layer can currently express, none of it reaches fire behaviour.

  (B) THE ROLE VOCABULARY BREAK IS REAL AND COSTLY. arm_role_dict (live
      vocabulary "fire_tracker") vs arm_role_dict_gen (generator vocabulary
      "fire_tracking") differ in 13/13 runs, and the generator's vocabulary is
      strictly worse (22 rescued vs 25, 10 firefighter deaths vs 8, 7
      never-detected vs 3). Writing the generator's own role words into the model
      produces roles that nothing downstream recognises. So even after fixing
      both gates above, a third fix - the vocabulary - is required before the
      path does something intended rather than merely something different.

3.1  BLOCKER ENUMERATION: "option generated" -> "option changes agent behaviour"

Each blocker below survived an adversarial refutation pass (18 of 36 candidate

B1. THE NINE UTILITY KEYS HAVE NO PRODUCER            [plumbing]
    src_extension/adaptation/global_adaptation_generator.py (all 4 families:
    :127 role, :291 task, :482 coverage, :615 resource) vs
    src_extension/planning/utility_evaluation.py:812-820
    Evidence: 0 of 9 present in 71,760 measured scorings; 37-key parameter union
    has EMPTY intersection with the nine; git -S shows no producer ever existed.
    Frozen/shared: no. AdaptationOption.parameters is a plain dict[str, Any].
    Test lock: NONE. Every global-utility test hand-writes the nine keys into
    synthetic options, so a generator that started emitting them breaks nothing.
    (tests/test_adaptation_integration.py:63-66 does assert absence of certain
    keys on generated options - it must be checked, but it asserts a different
    key set.)

B2. pfloat's SILENT 0.0 DEFAULT HIDES B1              [plumbing]
    src_extension/planning/utility_evaluation.py:793-797
    A missing key is indistinguishable from a genuine zero. This is why the
    failure is silent and survived to now. Not independently blocking, but it is
    the reason B1 is invisible without instrumentation.
    Frozen/shared: no.  Test lock: none.

B3. assigned_role IS A STRING; THE PLANNER ONLY ACCEPTS A DICT   [plumbing]
    src_extension/planning/global_mission_planner.py:233-241 (`_string_dict`
    returns {} for non-dicts) vs global_adaptation_generator.py:147
    (`parameters={**base_parameters, "assigned_role": role}` over the string list
    at :134-140).
    Evidence: MEASURED. arm_role_str selects the option 3107/3120 times and
    produces an empty MissionDecision, 13/13 byte-identical. This is the second
    serial gate, and it is the one that makes a scoring-only fix inert.
    Frozen/shared: no - module-private helper, one caller.
    Test lock: none found.

B4. ROLE VOCABULARY MISMATCH                          [design gap]
    global_adaptation_generator.py:134-140 emits fire_tracking, victim_search,
    victim_confirmation, victim_tracking, communication_relay.
    wildfire_model.py:656-662 uses fire_tracker and victim_searcher - two live
    roles, zero spelling overlap, and the local path generator compares with
    exact equality.
    Evidence: MEASURED. arm_role_dict vs arm_role_dict_gen differ 13/13, and the
    generator vocabulary performs strictly worse.
    Design gap, not plumbing: three of the five generator roles
    (victim_confirmation, victim_tracking, communication_relay) have NO runtime
    counterpart at all. Somebody must decide what they mean before they can be
    mapped.
    Test lock: tests/test_uav_sector_assignment.py has two of the eight existing
    baseline failures and is role-dependent - in the blast radius.

B5. SIX REGION-SHAPED KEYS ARE GENERATED, NONE IS READ   [plumbing]

    list); global_mission_planner.py:251 reads target_region SINGULAR. Same for
    critical_regions, priority_regions, candidate_regions, uncertainty_regions,
    candidate_zones - none has a reader.
    Frozen/shared: MissionDecision.task_assignments is dict[str, str], so a list
    of regions cannot survive the trip even after the key is fixed.
    Test lock: tests/test_global_adaptation.py:62 asserts the plural on the
    generator side (`option.parameters["target_regions"] == ["r1"]`).

3.2  QUESTION 7 - COULD FIRE-FIGHTING ASSIGNMENTS REACH A FIREFIGHTER TODAY?
--------------------------------------------------------------------------------
FROM THE GLOBAL LAYER: NO. Not by a broken path - the destination does not exist.

The trace, mechanically extracted from agents.py:379-1178 (the whole Firefighter
class). A Firefighter reads exactly SEVEN model attributes:

    model.HEIGHT, model.WIDTH        grid dimensions
    model.grid, model.schedule       to enumerate Fire agents and read geometry
    model._agents_pending_removal    bookkeeping
    model._rescue_path_clear_requested }  OUTBOUND - the firefighter WRITES these
    model._on_firefighter_route_blocked}  (agents.py:546), they are signals out,
                                          not orders in

Its behaviour is otherwise driven entirely by its own instance fields:
target_pos, exiting, exit_target, rescued_victim, assigned, status, dead. Two
tuning constants (IDLE_RETREAT_SAFETY_BUFFER=3, IDLE_RETREAT_MAX_CELLS=6,
agents.py:375-376) are module globals, so not even those are retunable at runtime.

NONE of the seven is written by the global adaptation layer. GlobalExecutor
(global_executor.py:40-105) writes exactly four sinks - uav_resource_model,
managed_uav_states, shared_operational_picture.mission_mode, and
pending_global_commands - and a Firefighter reads none of them. MissionDecision
has no firefighter-directed field. The managed mirrors
(managed/firefighter_state.py, knowledge/firefighter_model.py,
monitoring/firefighter_monitor.py) are read-only: managed_firefighters is written
only by wildfire_model itself and read only by the dashboard
(dashboard_state_builder.py:257), and FirefighterOperationalState has fields for
availability / assignment_state / route_state / rescue_progress - none for a
region, sector or geometry.

Four breaks, in depth order. Fixing any one alone changes nothing:
  1. MissionDecision has no firefighter field  - the order cannot be EXPRESSED
  2. GlobalExecutor has no firefighter sink    - it cannot be CARRIED
  3. Firefighter reads no src_extension state  - it cannot be RECEIVED
  4. target_pos is a single cell               - "region"/"sector" has NO
                                                 REPRESENTATION anywhere

THERE IS, HOWEVER, A LIVE MANAGING-SYSTEM -> FIREFIGHTER PATH - in the RESCUE
lane, and it must not be overlooked, because it changes the shape of the work:

    rescue_planner.select_rescue_assignment (PLANNING, rescue_planner.py:523)
      <- called by wildfire_model.py:2904 (_handle_rescue_incident) and :4023
         (_dispatch_firefighter_to_victim)
      -> RescueExecutor.apply_physical_pairing_decision (rescue_executor.py:307)
      -> execute_physical_command (:400) -> model.apply_physical_rescue_command
      -> wildfire_model.py:3498-3503:
             ff_marker.assigned = True
             ff_marker.target_pos = victim_cell
             ff_marker.rescued_victim = victim_marker
             ff_marker.status = "en_route"

This really moves real firefighters, and the pairing POLICY genuinely lives in
the planning layer. But for the maintainer's purpose it has three
disqualifying properties:
  - It is the RESCUE scope, not the global one. It is never reached from the
    adaptation-space / option / utility pipeline; no option, trigger or
    MissionDecision touches it.
  - It is INVERTED: wildfire_model initiates on a physics event (victim
    confirmed, route blocked, casualty, rescue complete) and pulls an answer from
    the planner. The planner cannot push an intent of its own.
  - It is VICTIM-GATED. PhysicalRescueCommand (wildfire_model.py:82-88) is frozen
    as (action, victim_id, firefighter_id, reason, metadata); all four actions
    are assign / unassign / mark_unreachable / finalize_rescue; the assign branch
    returns False if no victim_marker resolves (:3477-3478); and target_pos is
    set to the victim's own cell. There is no vocabulary for "defend this
    region", "hold this sector", or "move to this cell".

PLAIN ANSWER: fire-fighting assignments - target regions to defend, fire-front
sectors, coordinated positioning - CANNOT reach a Firefighter today by any path,
global or rescue. Given the current structures, such behaviour would have to be
hardcoded at agent level. Making it plannable instead means designing and
building the missing channel end to end: a command vocabulary that can express a
region, a decision field that can carry it, an executor sink that can apply it,
and firefighter behaviour that consults it. None of those four exists.
