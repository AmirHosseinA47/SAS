VERDICT ON THE ORIGINAL AUDIT ITEM: CONFIRMED, with one correction.

The defect is real and still present at HEAD 9dfdb07. The original
description is accurate about the summary block. It is OVERSTATED on one
point: it says "The masking is invisible in the output - nothing indicates
how many runs contributed to the statistic." That is true of the SUMMARY
BLOCK only. The same file already discloses per-run termination twice, in
the per-seed lines (terminal=- / all_terminal=False) and in the CSV block
(empty terminal_step cell, all_terminal=False). The defect is therefore
narrower than described: it is confined to the aggregate line, where a
reader who does not hand-count the seed lines above gets no signal.

That narrowing matters for impact (section 3) and it does not excuse the
defect: the summary block is precisely the part that gets copied into
comparison tables.

1a. IS THE None-FILTERING STILL PRESENT?  YES.

    Line 274: "if r.get(key) is not None". This is a generic filter applied
    to every key in METRIC_KEYS, not a terminal_step special case. The
    "elif key == terminal_step" branch at 280-283 is DEAD CODE with
    respect to the filtering: "present = [float(v) for v in nums]" is an
    identity copy of an already-filtered, already-float list, and
    re-running _mean_std on it returns exactly the values computed at 275.
    The branch's only real effect is the "%.1f" format instead of "%.2f".
    Whoever wrote that branch appears to have intended to handle the None
    case there and instead duplicated work the generic filter had already
    done.

1b. IS THE CONTRIBUTING-RUN COUNT REPORTED ANYWHERE IN THE OUTPUT?  NO.

    The header at line 272 prints len(rows) - the number of seeds that
    ran to completion without raising. It is NOT the number of runs that
    contributed to any given metric. A seed that ran fine but never reached
    a terminal state is counted in that header and silently excluded from
    the terminal_step mean. The header word "successful" refers to "did not
    throw", not "did terminate".

    Concretely, from committed outputs/fix12_D_north.txt:

        Summary (mean +/- std) over 5 successful run(s):
          ...
          terminal_step: 210.0 +/- 0.0
          steps_run: 240.00 +/- 0.00

    "210.0 +/- 0.0" is computed over 3 runs. Two runs (seeds 404, 505)
    never terminated. The line reads as a perfectly reproducible
    termination step across the whole batch; it is a 3-of-5 figure, and the
    "+/- 0.0" is real zero variance across those 3, which makes it look
    MORE trustworthy than it is. This is exactly the shape the original
    audit described.

1c. WHAT DOES terminal_step == None ACTUALLY MEAN?

    Verified against how it is SET, not just how it is consumed.

    evaluate_scenarios.py:114-132 (the producer):

        terminal_step = None
        step = 0
        ...
            for _ in range(steps):
                model.step()
                step += 1
                if terminal_step is None:
                    panel = model.get_dashboard_state()
                    mission = panel.get("mission_status", {}) or {}
                    if mission.get("all_victims_terminal"):
                        terminal_step = step

    It is a latch: first step at which the dashboard reports
    all_victims_terminal. It is never reset and never set from any other
    path. It is passed through _build_evaluation
    (serve_dashboard.py:272, 311) verbatim: "terminal_step": terminal_step.

    all_victims_terminal is built in
    src_extension/dashboard/dashboard_state_builder.py:95-153:

        all_terminal = bool(managed)
        for _, state in managed.items():
            ...
            if status not in _TERMINAL_VICTIM and not bool(getattr(state, "rescued", False)):
                all_terminal = False
        ...
        "all_victims_terminal": all_terminal and len(managed) > 0,

    So terminal_step is None means, unambiguously: at no step within the
    --steps budget did every managed victim hold a terminal status
    (rescued / dead / unreachable). It is "never terminated within the step
    budget". There is no second meaning - not "model crashed", not "no
    victims", not "field missing". The "len(managed) > 0" guard means a
    zero-victim model would also yield None, but no committed run has
    total_victims == 0.

    Cross-check: steps_run in the same summary is 240.00 +/- 0.00 for every
    affected file, i.e. every run consumed the full budget. Confirms the
    "budget exhausted" reading.


================================================================
2. SIBLING DEFECTS IN THE SAME REPORTING PATH
================================================================

2a. Is terminal_step the only field that can be None?  YES, empirically and
    by construction.

    By construction: _build_evaluation (serve_dashboard.py:304-314) returns
    every other METRIC_KEYS field as an unconditionally-computed int or
    float. terminal_step is the only pass-through of a nullable argument.

    Empirically: parsed every CSV block in every committed outputs/*.txt -
    687 run rows across 170 files. Count of empty cells per column,
    excluding the free-text unreachable_causes:

        terminal_step          54
        (every other column)    0

    54/687 = 7.9% of all committed runs never terminated. So the generic
    None filter at line 274 fires on exactly one field today.

2b. THE FILTER IS STILL A LATENT TRAP FOR THE OTHER TWELVE.

    "r.get(key)" - note .get, not [] - means a key that is MISSING from a
    row is dropped just as silently as a None. If a future field were added
    to METRIC_KEYS but not to _build_evaluation, its summary line would
    quietly average over whichever rows happened to have it. Nothing warns.
    Same defect class, not yet triggered.

2c. A METRIC WITH ZERO CONTRIBUTORS VANISHES ENTIRELY (line 276-277).

    If every run is non-terminal, nums == [], _mean_std returns
    (None, None), and "if mean is None: continue" DROPS THE LINE. The
    summary then contains no terminal_step row at all, with no note. A
    diffing reader would see a missing line, not a stated "no data".
    Not triggered in committed data (0 of 170 blocks have all runs
    non-terminal - the worst is 2 of 5) but it is live.

2d. "+/- 0.0" IS AMBIGUOUS AT n=1 (_mean_std lines 140-141).

    "if len(values) == 1: return values[0], 0.0" returns a std of 0.0 for a
    single sample. That is not zero variance, it is no variance
    information. Combined with 2c this means the audit's literal example -
    "216.0 +/- 0.0" over 1 of 5 runs - would print a fabricated-looking
    confidence interval. No committed block hits n=1 for terminal_step
    (minimum observed is n=3), but the code will do it.

2e. THE TERMINATION RATE IS NEVER SUMMARIZED AT ALL.

    all_terminal is produced per-run by _build_evaluation and printed on
    each seed line and in the CSV, but it is NOT in METRIC_KEYS. So the
    single number that would make the masking self-evident - how many of N
    runs terminated - appears nowhere in the summary block. This is the
    actual missing signal, more than the absent n= suffix.

2f. THE HEADER COUNT EXCLUDES CRASHED SEEDS SILENTLY-ISH.

    Line 239-245: a seed that raises prints an ERROR line and is continue'd
    out of rows. The header then says "over K successful run(s)" where
    K < N. The top-of-file banner says N=<requested>. The discrepancy is
    recoverable by comparing two lines but is not called out. Lower
    severity than the rest - the word "successful" and the printed ERROR
    line do disclose it. Reporting for completeness, not proposing a change.

2g. evaluate_extended_metrics.py - RELATED FILE, NOT DEFECTIVE ON THIS AXIS.

    It computes terminal_step per run (lines 45-64, 85) but never
    aggregates it. Its summary block (lines 148-151) averages only
    tracker_smoke_total, tracker_fire_total, firefighter_deaths, rescued,
    dead - all never-None - and uses no None filter at all
    ("nums = [float(r[key]) for r in random_rows]"). _fmt_ms prints "n/a"
    on an empty list, which is the correct behaviour and is what
    evaluate_scenarios.py should have done at 2c. It does not print the
    size of random_rows next to the means; the seed list is printed at the
    top, so the count is recoverable. Minor, out of the stated blast radius.

PART 2 - DESIGN
================================================================

5. CHOSEN FIX: OPTION C (report both), implemented as a strict superset of
   Option A. Option B is REJECTED.

WHY NOT OPTION B (impute step_budget for non-terminal runs)

    Option B changes what the printed number MEANS. fix12_D_north.txt would
    go from 210.0 to 222.0 with no change to a single simulation outcome.
    This branch carries ~15 committed matrix baselines that later rounds
    compare against seed-matched; 30 committed summary blocks would become
    silently non-comparable with any newly-generated file, and the
    non-comparability would be invisible - both files would show a
    plausible three-digit number under the same label. That is precisely
    the failure mode this campaign has caught by hand five times already
    (stale baselines across HEADs in the idleretreat and standby rounds;
    the CSV-flag encoding mismatch in the lane-clamp round). Introducing a
    sixth instance deliberately, in the reporting layer, to fix a
    disclosure bug, is a bad trade.

    Option B also destroys information: once imputed, the mean cannot
    distinguish "terminated at 240" from "never terminated", because the
    budget is a legal terminal_step value (outputs/_delaybonus_gate_post_
    Dwest.txt has a real terminal_step=239). _summarize_fix13.py gets away
    with it only because it states the convention in its own header and its
    own consumers know it.

WHY NOT OPTION A ALONE (disclose n only)

    A "(n=4/5)" suffix fixes the stated defect and nothing else. It leaves
    2c (metric vanishes at n=0), 2d ("+/- 0.0" at n=1) and 2e (termination
    rate never summarized) in place. 2e is the one that actually makes the
    masking legible at a glance, and it costs one line.

OPTION C AS SPECIFIED

    C1. terminal_step line ALWAYS carries its contributing count:
            terminal_step: 210.0 +/- 0.0 (n=3/5)
        Always, including n=5/5, so that absence of a suffix is never
        load-bearing and the gate "the count is visible wherever
        terminal_step is reported" holds unconditionally.

    C2. Every OTHER metric line carries the suffix ONLY when n < total.
        Today this never fires (section 2a proves terminal_step is the only
        nullable field across 687 committed rows), so 12 of 13 summary
        lines stay byte-identical to every committed baseline. It is a
        guard against 2b: if a future field is missing or None, it
        announces itself instead of quietly averaging a subset.

    C3. n == 0 no longer vanishes (fixes 2c). Instead of continue:
            terminal_step: n/a (n=0/5)
        Matches the "n/a" convention already used by
        evaluate_extended_metrics.py:_fmt_ms and the nan convention in
        _lane_matrix_summarize.py.

    C4. One new summary line, always printed, giving the termination rate
        directly (fixes 2e):
            non_terminal_runs: 2/5 (never reached all-victims-terminal within steps=240)
        This is the number a reader actually wants and it is currently
        nowhere in the summary block.

    C5. Remove the dead "elif key == terminal_step" recomputation
        (2a / lines 280-283) while preserving its only real effect, the
        "%.1f" format. Pure cleanup, zero output change.

    NOT DOING: 2d ("+/- 0.0" at n=1). Changing _mean_std's single-sample
    return would alter printed values in committed baselines for EVERY
    metric on any 1-seed run, which is the Option B trap again. With C1 and
    C4 in place, an n=1 line reads "216.0 +/- 0.0 (n=1/5)" and the reader
    can see the std is meaningless. Disclosure solves it without touching a
    value. Documented here so it is a decision, not an oversight.

    NOT DOING: any change to evaluate_extended_metrics.py. Section 2g shows
    it does not aggregate terminal_step and already handles empty sets
    correctly. Out of blast radius.

VALUE-PRESERVATION GUARANTEE

    No printed NUMBER changes. Every mean and std keeps its current value
    and current format. The changes are: (a) a suffix appended to the
    terminal_step line, (b) a suffix appended to other lines only in a case
    that cannot occur today, (c) a line that currently disappears now
    printing "n/a", (d) one added line. Seed-matched comparison against all
    ~15 committed matrix baselines remains valid on every existing figure.

CSV: NOT CHANGED. Deliberate.

    The CSV already encodes this per row - terminal_step is empty and
    all_terminal is False for non-terminal runs (verified: 54 empty
    terminal_step cells across 687 committed rows, and all_terminal is
    already a column). Adding a column would buy nothing and would carry
    real risk: outputs/_summarize_fix13.py:52 reads the LAST CSV field
    positionally -

        for tok in (parts[len(cols) - 1] if len(parts) >= len(cols) else "").split(";"):

    - to recover unreachable_causes. Appending a column to fieldnames would
    silently redirect that read to the new column and break the
    never_detected victim extraction that _summarize_fix13.py and
    _summarize_fix14.py both depend on. Checked before proposing, per the
    brief. Not adding a column avoids the issue entirely.

DOWNSTREAM PARSER COMPATIBILITY, CHECKED IN ADVANCE

    Only one committed script parses the summary metric lines:
        outputs/_summarize_fix9.py:62
        re.search(r"^  %s: ([0-9.]+) \+/- ([0-9.]+)" % key, text, re.M)
    It is anchored at the start and NOT at the end, so a trailing
    " (n=4/5)" is ignored and the captured groups are unchanged. Verified
    by inspection; will be verified by execution in Part 4.

    The new non_terminal_runs line: _summarize_fix9.py only searches for
    named keys, so an extra line is invisible to it. _summarize_fix13.py
    and _summarize_fix14.py only consume lines after the "seed,rescued,"
    header whose first character is a digit; the new line begins with two
    spaces and is skipped. No committed script matches on
    "Summary (mean +/- std) over" (grepped: zero hits outside
    evaluate_scenarios.py itself).

    Nothing under tests/ imports or parses evaluate_scenarios.py output.
    Only tests/_run_scenario_a_coverage_validation.py references the
    module name, and it is a helper script, not a test.


6. CONFIRMING THE FIX CANNOT CHANGE A SIMULATION OUTCOME

Argument: every edit is inside main()'s summary block
(evaluate_scenarios.py:268-300), which executes after the seed loop has
finished and every model has been stepped and discarded. It reads rows and
writes stdout. It touches no RNG, no module-level global, no import order,
no cfv/wf/am state. _run_seed, _scenario_params, _build_evaluation and the
WildFireModel construction path are untouched. No file under agents.py,
wildfire_model.py or src_extension/ is opened.

An argument is not the standard this campaign has used. The verification
will be executional, matching the standard set in the lane-clamp and
dispatchreach rounds:

    V1. A control run was captured BEFORE any source edit, at HEAD 9dfdb07:
            python evaluate_scenarios.py --scenario D --wind north --n 5 \
              --steps 240 --seeds 101,202,303,404,505 --csv
        (chosen because D/north is the historically non-terminal-heavy
        combo; launched during Part 1, output held in the session
        scratchpad, not committed.)

    V2. After the edit, the same command is re-run and the two outputs are
        compared with an exact byte diff after stripping ONLY the summary
        block. The banner line, all five per-seed lines, every "causes:"
        line, the full CSV block (header plus all data rows) and the
        REPRODUCE line must be byte-identical. Any difference in those
