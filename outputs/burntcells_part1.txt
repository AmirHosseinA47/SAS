VERDICT IN ONE PARAGRAPH
  The item is REAL, but both of its halves invert, and it names the wrong
  population. There are two distinct states that this codebase itself
  conflates. `burnt` (fuel exhausted) is provably the SAFEST ground in the
  model, and treating it as ordinary passable ground is CORRECT - that half of
  the audit is closed as verdict (C), and the "prefer burnt cells for retreat"
  inversion is separately closed as verdict (D), inert, because burnt ground is
  essentially never adjacent to a firefighter in danger. But
  `has_burned and not burnt` - which BOTH renderers paint the identical
  charcoal #2b2b2b, i.e. what a human operator actually sees as "charred" - is
  the MOST DANGEROUS ground in the model: 96% of such cells re-ignite, they
  carry a ~15x elevated per-step death rate, and three of the six remaining
  firefighter deaths are precisely this ground igniting under a stationary
  unit. That is verdict (A), REAL DEFECT, ACTIONABLE - but scoped narrowly to
  the HAZARD MODEL, because the Fire-level semantics AND the shared charcoal
  rendering both turn out to be specified and test-locked (section 2.4). The
  actionable gap is that nothing carries the specified re-ignition risk into
  firefighter movement or scoring.

CAN A CELL LEAVE `burnt`? NO. It is an absorbing state, triple-guarded:
  (i)   probability_of_fire() short-circuits to 0                 agents.py:54
  (ii)  step() returns before probability_of_fire is even called  agents.py:91-95
  (iii) advance() re-pins burning=False, bypassing the normal
        "self.burning = self.next_burning_state" commit           agents.py:122-124
  MEASURED: 0 burnt -> burning transitions over a full 240-step run
  (outputs/_bc_reignite.py). The absorbing property is not merely argued, it is
  observed.

THE CRITICAL DISTINCTION THIS INVESTIGATION TURNS ON
  `next_burning_state` is computed from probability_of_fire(), which reads the
  cell's BURNING NEIGHBOURS (agents.py:64-79). It does NOT read the cell's own
  fuel. So a cell that is currently burning stops burning whenever its
  neighbours stop sustaining it - with fuel still in the tank. That produces a
  third, unnamed state:

    burning   : is_burning() == True                  -> LETHAL
    burnt     : has_burned and fuel <= 0              -> PERMANENTLY SAFE
    "scorched": has_burned and fuel > 0 and not burning
                -> ORDINARY IGNITABLE GROUND, and empirically far worse

  This report calls the third state "scorched". The codebase has no name for
  it, which is the root of the whole defect.

1.3  PHYSICAL SEMANTICS OF A BURNT CELL
----------------------------------------
SMOKE - still emitting, briefly, then clears FASTER than a live cell.
  Smoke needs SMOKE_PRE_DISPELLING_COUNTER=2 burning ticks to activate, while
  burnt needs >= FUEL_BOTTOM_LIMIT=7, so smoke is always already active at the
  moment a cell turns burnt, with its dispelling counter at 3. The burnt branch
  then drains it every step (see the throttle note above), clearing on step 4.
  A burnt cell can never START new smoke: smoke_step(False) cannot enter the
  activation branch (agents.py:159-166).

HAZARD TO AN AGENT STANDING ON IT - NONE. This is the load-bearing fact.
  wildfire_model.py:4139-4140 is the ONLY site in the live tree that marks a
  firefighter dead, and wildfire_model.py:4045 the only one for a victim. Both
  live inside _check_fire_casualties (wildfire_model.py:4013), whose fire_cells
  set is built from is_burning() alone (:4016-4028). `burnt = True` forces
  `burning = False` in the same block, so a burnt cell can NEVER enter that
  set. There is no health, HP, exposure, inhalation, or injury mechanic
  anywhere; UAVs have no harm mechanic at all.
  NARROWING: residual smoke on a freshly-burnt cell is a real but NON-LETHAL
  hazard - it triggers _needs_immediate_survival_retreat, adds +10 risk, and
  fails _cell_meets_required_idle_safety, for about 4 steps.

FIREBREAK - YES, above a measured critical width of exactly 3.
  probability_of_fire sums over a Moore radius-3 neighbourhood with NO
  line-of-sight or occlusion test, so burnt cells never shield anything
  geometrically; they stop fire only by ceasing to be fuel. Measured directly
  (outputs/_bc_firebreak.py), probability of ignition for the first unburnt
  cell beyond a burnt band:
        width 0 -> 1.0000   crosses
        width 1 -> 0.9298   crosses
        width 2 -> 0.9111   crosses
        width 3 -> 0.0000   BLOCKED
        width 4 -> 0.0000   BLOCKED
        width 5 -> 0.0000   BLOCKED
  Because burnt is absorbing, a band this wide is a PERMANENT firebreak. The
  critical width is 3 because distance_rate is euclidean**-2 for d <= 3 and 0
  beyond (common_fixed_variables.py:156-161).

UAV OBSERVATION - cannot represent burnt-ness at all.
  UAV.surrounding_states() (agents.py:294-306) encodes every observed cell as
  a single bit, int(agent.is_burning() is True). A burnt cell, a scorched cell
  and virgin green ground all produce the identical value 0 - as does an
  out-of-grid cell, which wildfire_model.py:2406-2409 pads with 0 as well.
  This is a sensor-level limitation, not a scoring omission.

WHERE THE MODEL SIMPLY HAS NO OPINION
  * No agent may prefer, avoid, or reason about burnt ground.
  * No notion of future fire risk, predicted spread, or time-to-arrival
    anywhere in any agent's scoring. Every hazard term is present-tense.
  * No concept that an already-ignited cell with fuel left differs from virgin
    fuel - the omission this whole report turns on.
  * No victim survival mechanic beyond binary "cell is burning now".

PART 2 - IS THE CURRENT BEHAVIOR ACTUALLY WRONG?
================================================================================

2.1  FIREFIGHTERS
------------------
For `burnt` ground: treating it as ordinary passable ground is CORRECT, and the
audit's premise is simply false. Burnt ground cannot ignite (measured: 0
transitions) and cannot kill (it can never enter the casualty set). It is the
only tile type in the model with a guaranteed-zero future hazard. MEASURED:
firefighters stood on burnt ground for 759 steps across the 13 runs and died
there zero times.

The inversion - "the real defect is that retreat does not PREFER burnt cells" -
is mechanically well-founded but EMPIRICALLY INERT. The mechanism is real:
`dist` in _pick_improving_retreat measures distance to currently-burning cells,
and burnt ground lies behind the front, so maximising `dist` steers a retreating
unit out of the black and into unburnt fuel. But it never gets the chance to
matter, for a physical reason:

  A cell burns for 21-30 model steps (fuel 7-10, BURNING_RATE 1, one tick per
  FIRE_SPREAD_SPEED=3 steps) while the front keeps advancing. The burning
  annulus is therefore several cells thick, and the black always sits well
  behind the flame. Reaching it means crossing live fire, which is the thing
  that kills.

  MEASURED over the six runs containing a death (outputs/_bc_gap.py), across
  215 firefighter-steps with active fire within 2 cells:
      no burnt cell existed anywhere on the grid ......  36 steps
      mean distance to the nearest burnt cell .........  7.1 cells
      a burnt cell adjacent (d <= 1), i.e. reachable ...  6 steps  (2.8%)

  And the direct answer to the question this round was asked:
      deaths with >= 1 safe BURNT neighbour at ANY point
      in the unit's entire life ....................... 0 of 6

  A "prefer burnt cells in retreat" change would have had ZERO opportunities to
  act on any of the six remaining deaths. Same shape as the dispatch-
  reachability closure: real, unarguable, and without measurable consequence at
  current scale.

For `has_burned and not burnt` ground: this is where the defect is.

  MEASURED (outputs/_bc_reignite.py, 240 steps, five seeds):

    seed/wind    scorched     re-ignited    rate    re-ignition   burnt->
                 (distinct)   (distinct)            events        burning
    101/east         1509         1449      96.0%       3985         0
    202/east         1121         1048      93.5%       2874         0
    303/east         2012         1952      97.0%       5036         0
    101/south        2199         2140      97.3%       5490         0
    404/south        2259         2206      97.7%       5741         0
    ---------------------------------------------------------------------
    TOTAL            9100         8795      96.6%      23126         0

  So "charred-looking" ground re-ignites ~96% of the time (range 93.5-97.7%
  across five seeds), about 2.5 times per cell, while the burnt population
  re-ignited exactly ZERO times in the same runs. Yet _firefighter_cell_risk
  scores a scorched cell identically to virgin green ground, and both renderers
  paint it identically to permanently-safe burnt ground.

  PER-STEP DEATH RATE BY GROUND TYPE, 13 runs, 5316 firefighter-steps alive:
      on BURNT ground .............. 759 steps,  0 deaths  ( 0.00% )
      on SCORCHED ("charred") ...... 179 steps,  3 deaths  ( 1.68% )
      all ground ................... 5316 steps, 6 deaths  ( 0.11% )
  Scorched ground carries a ~15x elevated per-step death rate, and it is the
  ground the UI paints the same colour as the safest ground in the model.

  ALL SIX DEATHS are "died in place": the unit's last living step and its death
  step are the same cell. Three of the six are the charred cell igniting under a
  stationary unit:
      east/half  seed 404  ff_unit_0  stood on [31,38] charred at s28,30,31,32,
                                      died there s33
      east/def   seed 101  ff_unit_0  stood on [41,41] charred at s36,38-41,
                                      died there s42
      east/def   seed 202  ff_unit_0  stood on [34,49] charred at s222-224,
                                      died there s225

  In each of the three the unit walked in from genuinely safe ground:
      seed 404 (e/h) : 4 truly-green free neighbours at s26; entered s28
      seed 101 (e/d) : 3 truly-green free neighbours at s35; entered s36
      seed 202 (e/d) : stepped at s219 into a cell with ZERO free neighbours
  and was then enclosed by active fire before it died.

  HONEST LIMIT ON THIS ATTRIBUTION. At the moment of death all three were
  already surrounded by burning cells, so a scorched-cell penalty would have had
  to act during the APPROACH (roughly s26-s36), not at the death step. That the
  penalty would in fact have saved them is a hypothesis, not a measured result;
  it needs an A/B experiment. The sample is also small - 6 deaths over 13 runs.
  What IS measured and not in doubt: the re-ignition rate (96%), the rate
  enrichment (~15x), and that 3 of 6 deaths occurred on ground the UI renders as
  charred.

2.2  UAVs / FIRE TRACKERS
--------------------------
A burnt cell has no remaining fire-tracking information value, and nothing in
the stack distinguishes it. Targeting draws candidates ENTIRELY from the belief
fire_probability_map at a fixed 0.3 threshold
(local_adaptation_generator.py:3065-3092 _classify_fire_cells), then filters
smoke, scores a lateral/upwind flank, and splits north/south. No ground-truth
cell state is consulted at any stage. Burnt-ness is not a term, not a filter,
not a penalty, and no belief layer stores it. The only way dead ground loses
attractiveness is generic and indirect: a UAV overflies it, emits a negative
observation, and update_no_fire_observation (fire_runtime_model.py:130) halves
the probability; apply_time_decay (:209) bleeds all probabilities down with age.
The model cannot distinguish "cold because it never burned" from "cold because
it is permanently over."

  MEASURED, 13 runs, 3,316,022 cell-observations (UAV x cell x step, radius 8):
      on BURNT ground ............  613,751   (18.51%)
      on SCORCHED ground .........  373,347   (11.26%)
      on ACTIVELY BURNING ground .  252,165   ( 7.60%)
      on unburnt / green ground .. 2,076,759  (62.63%)

  So 18.5% of all observation effort lands on ground that is permanently over,
  against 7.6% on live fire. That is the one place the audit's concern has real
  mass - but it is the INVERTED form: the problem is not that burnt cells are
  treated as safe, it is that they are not deprioritized as observation targets.
  Note this is bounded and self-correcting: one overflight collapses the belief,
  so trackers are not repeatedly drawn back. The cost is a wasted visit, not
  persistent waste, and no measured mission outcome is attributed to it.

2.3  VICTIM SEARCHERS AND VICTIMS
----------------------------------
Burnt-ness is entirely absent from the victim subsystem, and correctly so.
Victims are placed on a deterministic ring computed from NUM_VICTIMS geometry
with no fire-state check (wildfire_model.py:508-555), and they never move. Their
mortality (wildfire_model.py:4045) keys strictly on is_burning(); there is no
health, injury, or graded-survival concept - the Victim class has three fields
and no-op step/advance.

A LIVE VICTIM CAN NEVER STAND ON A BURNT CELL. Reaching `burnt` requires
passing through `burning`, and any victim present during that passage is killed
in the same step. So the question "does a burnt cell affect victim detection or
survival" is vacuous by construction, not merely unmodelled. Dead victim markers
do persist on burnt ground, since only rescued victims are removed. Searcher
scoring uses distance-to-active-fire, wind, interior margin and coverage, and
never mentions burnt-ness. NO DEFECT HERE.

2.5  VERDICT
================================================================================

The audit item names one population but describes two. Split it:

(C) NOT A DEFECT - `burnt` cells (has_burned and fuel <= 0).
    Treating them as ordinary passable ground is CORRECT for this model, and
    the original framing is mistaken. They are absorbing (0 re-ignitions
    measured), cannot enter the casualty set, are the only ground with a
    guaranteed-zero future hazard, and form permanent firebreaks above a
    measured critical width of 3. Firefighters occupied them for 759 steps and
    died there 0 times. CLOSE THIS HALF.

(D) INERT - the inversion, "burnt cells should be PREFERRED as retreat targets".
    Mechanically real: retreat ranks by distance to currently-burning cells, and
    the black lies behind the front, so the ranking steers units out of it. But
    burnt ground is adjacent in only 2.8% of danger-steps, sits 7.1 cells away
    on average, and was available in 0 of 6 deaths. A preference change would
    have had no opportunity to act. Quantified as inert; same disposition as the
    dispatch-reachability closure.

(A) REAL DEFECT, ACTIONABLE - `has_burned and not burnt` cells: the ground both
    renderers paint charcoal #2b2b2b, i.e. what an operator sees as "charred".
    ONE defect (A1, the hazard model) plus ONE deliberate design choice I am
    flagging but NOT calling a defect (A2, the shared rendering):

    A1. HAZARD MODEL. A cell that has already ignited and retains fuel
        re-ignites 96% of the time, yet _firefighter_cell_risk
        (agents.py:665-673) scores it identically to virgin ground, and no
        predicate anywhere distinguishes it. Per-step death rate on this ground
        is ~15x baseline; 3 of the 6 remaining firefighter deaths are this
        ground igniting under a stationary unit. The signal is already present
        on the agent object (has_burned and fuel) and is simply never read.

    A2. RENDERING - NOT A DEFECT, A DELIBERATE CHOICE I AM QUESTIONING.
        main.py:77 and serve_dashboard.py:63 both colour on
        "is_burnt() OR has_burned", merging the safest ground in the model with
        the most dangerous into one indistinguishable charcoal. At step 60 the
        scorched population is 1.73x the burnt population, so early in a run the
        charcoal region is MAJORITY not-safe.
        CRITICAL CORRECTION: this is NOT an oversight. It is specified and
        locked by an existing test - see section 2.4. Changing it means changing
        a documented behaviour and updating that test, which is a design
        argument, not a bug fix. I am flagging the operator-facing consequence
        only; the call is the maintainer's.
        Note serve_dashboard.py:133 propagates the same merge into the "spared
        vegetation" muting pass. dashboard_state_builder.py:296-301 already
        publishes the two counts separately, so if a third colour were wanted
        the data is on hand.

FIX SCOPE - NOT IMPLEMENTED, AWAITING GO-AHEAD, per this chain's protocol.
  A1 would add a re-ignition risk term keyed on (has_burned and not burnt and
     fuel > 0) to _firefighter_cell_risk, and would need an A/B run on this
     13-run sample plus the 10 extra seeds to show it actually moves
     firefighter_deaths. The attribution above is suggestive, not proven, and
     the change must be justified by measured deaths, not by the 96% figure
     alone. Risk to watch: the scar rim already accumulates +100 (fire-adjacent)
     and +10 (smoke); adding more penalty there could push units further into
     unburnt fuel and make things worse. That is exactly why it needs the A/B.
  A2 is a display-only change and carries no simulation risk: give
     has_burned-and-still-fuelled its own colour, distinct from burnt.
  A1 and A2 are independent and can be taken separately or in either order.
