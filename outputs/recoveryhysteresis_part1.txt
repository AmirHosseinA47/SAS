6. IS DELETION ACTUALLY RIGHT? BOTH SIDES.
================================================================================

6.1  THE CASE AGAINST DELETING - BUILT AS STRONGLY AS THE EVIDENCE ALLOWS
--------------------------------------------------------------------------------
(a) THE CAPABILITY GAP IS REAL. The fail-safe mode machine is provably
    memoryless. safety_checker.py:67-72 declares
    `def classify_mode(self, reasons, current_mode: str = "normal") -> str:`
    and its FIRST STATEMENT is `_ = current_mode`. The live caller threads the
    previous mode in (mode_manager.py:71-74) and it is thrown away. The system
    has ZERO exit hysteresis: one clean analysis cycle would drop it straight
    out of a protective mode. That IS a genuine design weakness, and this dead
    block is the only artifact in the repo that names it.

(b) DELETING REMOVES SCAFFOLDING. The three blocking-reason frozensets encode
    real domain judgement about which hazards should prevent recovery from
    which mode. Someone implementing hysteresis properly would have to
    re-derive that.

(c) "LEAVE IT BUT DOCUMENT IT" IS EXPLICITLY ACCEPTABLE per the brief and
    costs nothing in risk.

6.2  WHY THE CASE AGAINST DOES NOT HOLD
--------------------------------------------------------------------------------
(a) IT IS AIMED AT THE WRONG GAP. should_return_to_normal gates ONLY the exit to
    NORMAL. The instability actually measured is info<->safety_first: 178
    transitions across 13 runs, with transitions_to_normal EMPTY in every single
    run. A fully wired, fully plumbed gate would damp NONE of the observed
    chattering, because reasons are never empty. It is evidence of a gap the
    system is not currently suffering from.

(b) NO SPEC TO DIVERGE FROM. The repo's entire doc set is 8 markdown files
    (README.md, docs/01-04, src_extension/{ARCHITECTURE_BOUNDARIES,
    MANAGING_SYSTEM_OVERVIEW,README_extension_structure}.md). A sweep for
    hysteresis|dwell|debounce|stable.recovery|return.to.normal|recovery across
