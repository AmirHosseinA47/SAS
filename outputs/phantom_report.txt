THE DEFECT, as diagnosed in Part 1
  The executor permits one victim to hold two firefighter claimants, and the
  route_blocked replacement pathway depends on that: a unit blocked twice on the
  same victim keeps its task (the incident handler returns early for a repeated
  pair) and is invisible to _find_active_firefighter_for_victim, so a
  replacement is dispatched. Whichever arrives first rescues. Nothing released
  the other: it walked to a stale target_pos, started exiting against empty
  ground, "completed" a rescue that was not counted, and drew a rescue absence
  it had not earned. The victim_dead recall had the same hole from the same
  lookup and left a route_blocked unit bound to a corpse.

1. WHAT WAS IMPLEMENTED
================================================================================
1.1  One helper, WildFireModel._release_other_claimants(victim_id,
     victim_marker, keep_ff_id, reason) -> list[str], next to
     _find_active_firefighter_for_victim. For every firefighter still bound to
     the victim (rescued_victim identity or id match; NOT gated on `assigned`
     or on status, so route_blocked claimants are included):
       skip  dead units                      (the casualty sweep owns them)
       skip  units with rescue_completed     (a unit that finished its own exit
                                              this step; the drain finishes it)
       skip  the unit named by keep_ff_id ONLY while it is exiting and no bound
             unit has rescue_completed        (D4, section 3)
       unassign through the executor, metadata {} (no reset_victim_pending: the
             victim is terminal, that flag relabels the marker "confirmed")
       then the label (D2): status en_route/assigned -> "available" and a
             knowledge re-sync; status route_blocked -> left for the
             revalidation pass, except when no victim needs rescue any more and
             the unit is not fire-enclosed, in which case "available" (D6)
       print "[Rescue Released] FF-x released from victim_y reason=..."
       bump ff_claims_released_total and ff_claims_released_by_reason (D8)
     Each unit is wrapped in try/except with a visible "[Rescue Release
     Failed]" line, because _process_rescue_incidents swallows exceptions; the
     relabel runs in its own guard so a relabel failure is reported as such and
     the release is still counted (D5).

1.2  Call sites in _handle_rescue_incident:
       rescue_complete, after a successful finalize_rescue: keep = the
         completing unit, reason "released_after_rescue_complete"; the release
         runs BEFORE _activate_post_rescue_coverage_for_searchers (as designed).
       rescue_complete, already-rescued early return (D3): keep = none, same
         reason. Arriving here for a rescued victim is the phantom's own
         signature; the reporting unit, if it is the phantom completer, is
         protected by its rescue_completed flag.
       victim_dead (D1): the former single-pair lookup is replaced by the
         helper with keep = none and the incident reason ("fire_casualty").

1.3  The drain (_process_pending_agent_removals, D7): a rescue absence is drawn
     only for the completion that turned the victim rescued in this drain (not
     rescued before it, not already completed by another unit in it, rescued
     after finalize). A co-completer, a unit exiting against a victim already
     carried out, or a corpse carrier is recycled in place with a "[Rescue
     Hand-over Skipped]" line and draws nothing from the absence RNG.

1.4  Not changed: the assign guard (apply_physical_rescue_command), the planner
     lookup, _blocked_replacement_attempted, the unassign action, the
     revalidation pass (_revalidate_route_blocked_firefighters), Feature 1's
     absence machinery apart from 1.3, Feature 2.

Unaffected runs stay byte-identical by construction: with no second claimant
and no victim death the helper finds nothing bound, issues no command, prints
nothing, writes nothing (proved on 9/13 runs, section 7).

3. REVIEW, AND WHAT IT CHANGED
================================================================================
Two adversarial multi-lens review workflows were run against the working tree
(six lenses: stranding/latch, ordering/re-entrancy, byte-identity, the
victim_dead widening, downstream consumers, test adequacy; three refuters per
finding). Both were cut short by session limits: run 1 completed one lens
(consumers), run 2 completed five (stranding, ordering, identity, consumers,
tests); the victim_dead lens never completed and no verifier completed. The
findings were therefore triaged by hand against the code; each was checked
before acting.

Acted on (all in the final source, all covered by tests):
  D4  keep rule (run 1, consumers; run 2, ordering). When the rescue_complete
      incident carries no firefighter id, _finalize_rescued_victim names
      _firefighter_id_for_victim = managed_victims[vid].firefighter_id, the
      LAST-assigned unit - in a double claim the loser. A keep-by-id then
      skipped the loser while rescue_completed skipped the carrier: nobody was
      released. Latent (the drain always names the completer) and closed: the
      name protects a unit only while it is exiting AND no bound unit has
      rescue_completed.
  D5  relabel misreport (stranding). If the knowledge sync inside the relabel
      raised, the unit was in fact released but reported "[Rescue Release
      Failed]" and not counted. The relabel now has its own guard.
  D6  gate latch (route_blocked gate, section 10). See below.
  D7  same-step co-completion (consumers, major). Two carriers of one victim
      reaching exits in the same step both drew an absence; the second is
      protected by rescue_completed by design, so the residual had to be closed
      at the drain (1.3). Not exercised by the sample (0 phantom completions on
      the fix arm), covered by a test.
  order (consumers): release before coverage activation, as section 4.2 of the
      design said; the helper now contains its own failures.
  tests (tests lens): the already-rescued test advanced the step counter so the
      same-step rescue_complete duplicate guard cannot make its assertion
      vacuous, and asserts exactly one finalize command; the drain test uses a
      victim cell that is closest to the released unit under both absence
      configurations; the ignition comment was corrected (ignition is random in
      [10,39]^2 and unseeded in tests; no assertion reads a position after a
      move); tests added for the dead-unit skip with three claimants, the
      relabel-failure path, the route_blocked release with and without live
      victims, the keep rule with a completer present, and the co-completer.
  D8  counter split by reason (consumers): the victim_dead path counts too.

Not acted on - pre-existing, unchanged by this fix, listed as follow-ups:
  * a unit released on the victim_dead path is in the pool but no dispatch
    sweep runs there (dispatch is incident-driven: drain recycles, revalidation
    recoveries, and the incident's own victim); a confirmed victim under a
    "delay" decision waits for the next trigger. The pre-fix recall left the
    unit in exactly the same state. One line would close it
    (_try_dispatch_unresolved_confirmed_victims after a victim_dead release);
    left out to keep this change to release semantics.
  * Firefighter.advance labels every safe idle cell "standby at edge".
  * the casualty sweep's own reset_victim_pending unassign relabels a
    same-sweep dead victim's marker "confirmed".
  * a re-dispatch path drawn inside the drain is wiped by the completer's
    _rescue_path_clear_requested (visual only).
  * the "victim_dead_recall" fallback reason string is unreachable (the
    incident always carries "fire_casualty").
  * the harness idle metric is keyed on the status label and is confounded by
    the D2 relabel; it is not quoted anywhere in this report.

7. WHY EXACTLY THESE FOUR RUNS DIFFER
================================================================================
  east/half 303 - the phantom episode. Baseline: ff_unit_1 stayed bound to
    victim_0 after ff_unit_0 carried it out at step 101, walked to the stale
    target (49,24), flipped exiting at 148 against empty ground, "completed" at
    149 (finalize returned early, rescued stayed 2), took a 3-step absence, and
    victim_1 was still a candidate at the horizon. Fix: "[Rescue Released]
    FF-ff_unit_1 released from victim_0" at step 101, in the dispatch pool the
    same step (pool_step=101), assigned to victim_1 at step 202 (in the
    baseline ff_unit_0 took that dispatch), completed at step 240: rescued
    2 -> 3, terminal_step None -> 240. Between 101 and 202 there were 0 steps
    in which ff_unit_1 was dispatchable while a confirmed victim waited
    unassigned - the freed capacity idled only because there was no work.
  south/half 303 - the dead-bound sibling (D1) and the gate case (D6).
    Baseline: ff_unit_0, blocked a second time on victim_3 at step 216 and so
    still assigned, was skipped by the recall when victim_3 died at 216, walked
    toward the corpse from 222 and was still bound at the horizon (24 steps).
    Fix: released at 216 ("reason=fire_casualty"); with every victim terminal
    at 216 there was no path to test, so D6 cleared its flag ("[Route Cleared]
    FF-ff_unit_0 released with no victim left to reach at (36, 23)"); it idles
    as available to the horizon. Eval identical (all victims terminal at 216
    in both arms); cells differ from step 217 because it no longer walks.
  east/half 202 and east/def 202 - the ordinary one-claimant victim_dead
    recall at step 27 (ff_unit_0, victim_0). The same unassign as before, plus
    the D2 relabel en_route -> available and one "[Rescue Released]" line.
    Cells, flags, victim rows and eval identical on every step; the identity
    lens traced every decision consumer of the raw status string (dispatch
    predicate, planner, revalidation, casualty sweep, executor, UAV and
    communication planners) and found each distinguishes only "dead" and
    "route_blocked", so this is guaranteed, not merely observed.
  The other 9 runs are byte-identical: eval, per-step firefighter rows, victim
  rows, fire digests, every recorded event list, stdout sha256.

10. ROUTE_BLOCKED GATE
================================================================================
The gate was run twice. The first run (prefix phfix, on the source after
review 1) PASSED "rescued does not decrease on any seed" and "recovery pass
still recovers units" but FAILED "no unit left latched as route_blocked at end

unit was in fact recoverable the step a victim appeared (test
test_route_blocked_release_with_a_live_victim_leaves_the_flag_to_the_pass) -
but the flag had no referent and the gate counts exactly that. D6 clears the
flag in the helper in that one case, unless the unit is fire-enclosed; the
revalidation pass is untouched.
Final run on the final source (prefix phfix3, outputs/_ph_rbgate_phfix3.txt):
all three items PASS. Seed sets match the baseline exactly (13 east, 5 south,

recoveries 3 -> 8, end-of-run units still blocked 0 -> 0. D/south: rescued

12. LIMITATIONS AND WHAT I WOULD NOT CLAIM
================================================================================
  * 13 seeds of one scenario; one phantom episode and one dead-bound case in
    the sample. The rescued +1 is one victim in one run. The mechanism claims
    rest on the code paths and the tests, the magnitude on this sample only.
  * D7 (co-completion) and the D4 fallback path are covered by tests but never
    exercised by the sample; their behavioural effect on other scenarios is
    unmeasured (they can only remove absences, never add one).
  * The D2 relabel changes the knowledge-model labels of every recalled unit
    (two runs here). Decision-invariance was traced through every consumer by
    the identity lens and holds on the sample; a future consumer that reads the
    raw status string for "en_route" would see the change.
  * Removing a phantom absence draw shifts the dedicated absence-RNG sequence
    for later completers in that run only; it cannot touch the fire map.
  * The review verification stage never ran (session limits); findings were
    triaged by hand. The victim_dead lens never reported.
