--------------------------------------------------------------------------------

  Root cause of the divergence: UAV SPAWN RELOCATION -> detection delay.
  Measured, isolated in 4.3.

--------------------------------------------------------------------------------
4.2  Why removing the early return alone would not fix it
--------------------------------------------------------------------------------
The brief and both prior reports treat `if not victim_cells: return`
(wildfire_model.py:2566) as the gap. It is the visible symptom, not a
sufficient description:

  delete that line and nothing changes. The per-unit loop at :2582-2586 tests
      any(_path_exists_avoiding_fire(cell, vcell, fire) for vcell in victim_cells)
  which over an empty victim_cells evaluates False, so every unit hits
  `continue` at :2587 and is still not cleared.

A fix must ADD a clearing branch for the empty-referent case, not remove a
guard. And the deeper statement is the one in section 0: a single unassign
disarms all three clears simultaneously. That is why this keeps reappearing on
a different seed every round - it is structural, not an ordering accident.

Corollary, and this is the sharpest structural point: a unit flagged on the
FIRST block of an (ff, victim) pair can never be a bound claimant while
flagged, because the flag and the unbinding happen inside the single statement
`self._mark_route_blocked()`. Clear 3 can therefore only ever reach a unit
flagged on a SECOND block of the same pair, where
`if attempt_key in self._blocked_replacement_attempted: return`
(wildfire_model.py:3333) returns before the unassign. Every first-block flag
whose victim then goes terminal falls through - deterministically.

4.4  The 30-step hazard-standoff oscillation  [NEW THIS ROUND]
--------------------------------------------------------------------------------
Neither prior report noticed this, and it changes what "too late" means.

  step  ff_unit_1 pos  target   Manhattan
  ----  -------------  -------  ---------
  189   [26, 8]        [22, 3]   9   <- closest approach
  190   [27, 8]        [22, 2]  11
  191   [27, 7]        [22, 2]  10
  192   [27, 8]        [22, 2]  11
  193   [27, 7]        [22, 2]  10
  194   [27, 8]        [22, 2]  11
  ...   (oscillation continues)
  205   [28, 6]        [22, 0]  12
  206   [28, 7]        [22, 0]  13
  207   [29, 7]        [22, 0]  14
  208   [28, 7]        [22, 0]  13
  209   [29, 7]        [22, 0]  14
  210   [29, 6]        [23, 0]  12
  211   [30, 6]        [23, 0]  13
  ...   [29,6]<->[30,6], then [30,6]<->[31,6]
  218   [31, 6]        [24, 0]  13
  219   route_blocked

Thirty consecutive steps, status en_route throughout, the route NOT blocked,
the unit simply unable to make progress. It arrived within 9 cells with 33
steps to spare and lost them to a two-cell oscillation.

Mechanism: _move_toward's tier system (agents.py:1774-1800) prefers cells that
are improving AND not adjacent-to-fire AND not smoky (tier 1), then maintaining
under the same constraints (tier 2), then any non-adjacent-non-smoky cell
(tier 3). When every improving neighbour is adjacent to fire, tier 3 selects a
non-improving cell, and the next step's tier 3 selects the cell it just left.
The unit is held at a standoff distance by the hazard tiers, not by an absent
route - the flag only fires 30 steps later.

IMPORTANT SCOPING NOTE: this is a movement-near-fire behaviour, which is
precisely the family that has measured WORSE in every round that touched it
(section 8.3). It is diagnosed here, not proposed for change.

--------------------------------------------------------------------------------
7.1  Why not the others
--------------------------------------------------------------------------------
  Not (A) NEW DEFECT. The complete f4e79d5 source diff touches no line in the
      route_blocked raise, clear, revalidation, unassign or replacement
      pathways. git blame dates every load-bearing line earlier: a4a01b4
      (2026-07-27) the replacement pathway, unassign and handler; f2827ed
      (08-28) and 70e1b33 (08-30) the trigger, the _move_toward clear and the
      whole revalidation pass including :2566; dd0a1b9 (09-05) the D6 clear at
      :3563. agents.py's added lines are entirely inside class UAV; a grep over
      the Firefighter class body (agents.py:970-1819) finds zero base_station
      references. The feature touches firefighters ONLY at construction time
      (berth spawn :660-668, berth reservation :582/:593) and has no per-step

  Not (C) UNRELATED. The effect is deterministic and reproducible, and the
      mechanism from spawn to detection to dispatch to flag is traced end to
      end. It is not coincidence that THIS seed latches at mode 3.

--------------------------------------------------------------------------------
7.2  Severity - and this is where the draft was too relaxed
--------------------------------------------------------------------------------
route_blocked is not an inert label. Both dispatch gates exclude it:
_firefighter_available_for_dispatch (wildfire_model.py:2971) returns False, and
the planner skips the entry (rescue_planner.py:591). A latched unit is
undispatchable for the rest of the run.

  On 808 east the consequence is nil, because every victim was already terminal
  when the flags stuck. Nothing in _build_evaluation reads firefighter state
  except `dead`.

  On 202 - MODE 0, the shipped default - it is NOT nil. ff_unit_1 was flagged
  at 237 and ff_unit_0 died the same step; victim_1 was then scored
  `unreachable` because no dispatchable firefighter remained. The flag is
  upstream of an evaluation-visible outcome.

So the correct disposition is: the latch is worth fixing on its own merits, at
mode 0, independently of whether the base station is ever armed. It is not a
blocker specific to arming the feature, and it should not be described as one.

--------------------------------------------------------------------------------
8.2  Does (i) risk reopening what 70e1b33 closed?
--------------------------------------------------------------------------------
It touches the same function and MUST keep that commit's trapped guard.

70e1b33 added the pass to break a circular dependency: the only in-run clear
needs target_pos, which needs a dispatch, which refuses route_blocked units.
Its own design caught a bug in itself before shipping - an early version
"recovered" a unit trapped in a corner, carrying a victim, because
_path_exists_avoiding_fire returns True at distance zero. The fix was the
trapped guard: at least one fire-free neighbour before any clear.

A no-referent clearing does not reopen that, provided it keeps the guard:
  - the corner case involved a unit CARRYING a victim (exiting); the pass
    already excludes exiting units at :2548-2549;
  - the distance-zero false positive came from testing reachability against a
    victim in the unit's own cell. On the no-referent path there is no
    reachability test at all, so that failure mode is structurally absent;
  - the enclosure test must still be applied. A unit standing in a ring of fire
    should stay flagged. (On every latch measured this round enclosed=False, so
    the guard would not have blocked any of them.)

Tests that would police the change:
  tests/test_phantom_rescue_release.py      (D6 / release-path clearing)
  tests/test_firefighter_dispatch_replacement.py  (the replacement pathway)
  tests/test_firefighter_fire_avoidance.py  (trigger and trapped guard)
  tests/test_rescue_planner_authority.py    (planner selection)
  tests/test_base_station.py                (23 tests, feature-side)
  tests/test_adaptation_manager_cycle.py    (the per-step call site)

8.3  Is (i) in the "changing firefighter behaviour near fire" family?
--------------------------------------------------------------------------------
The brief's warning is well founded. The record:
  c92e136  scorched-ground hazard term - measured HARMFUL at every magnitude
  fd743f5  lateral-when-pinned - best rule saves 2 and kills 4, declined
  e76c806  dimension fix's searcher hazard change - fresh-seed deaths 3 -> 8
  db57df6  fix12 hazard re-validation, measured BELOW fix8
  and the base station round itself, a canonical gain evaporating on wider seeds.

Candidate (i) is OUTSIDE that family, checkably:
  - it fires only when _any_victim_needs_rescue() is False, and that predicate
    is MONOTONE (a victim's status only moves into {dead, rescued, unreachable}
    and never out). So there is never another dispatch after it fires, and no
    movement decision can be affected;
  - route_blocked is read only by dispatch/pairing gates. Firefighter.advance,
    _check_fire_casualties and _update_unreachable_victims never read it;
  - the only firefighter field _build_evaluation reads is `dead`.
  => on runs where the last victim is already terminal, (i) changes the
     reported end status and nothing else. Zero outcome movement expected.

  HONEST CAVEAT: that argument is airtight only for the 808-shaped case. On a
  202-shaped run the whole POINT is that clearing the flag earlier could let
  the unit be re-dispatched and change `unreachable` - i.e. (i) is
  outcome-bearing exactly where it is most valuable. Whether that is an
  improvement must be MEASURED on a seed-matched wave, not assumed. Do not
  gate this fix as "bookkeeping only".

  Candidates (iv) and (v) ARE in the dangerous family. Say so out loud in any
  round that proposes them.
