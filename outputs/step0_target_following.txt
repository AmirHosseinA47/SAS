   any divergence observed here; it is a defect waiting for the corridor
   path to be revived.

   run              mean cov_w    max cov_w   cov_w >= 0.9  min_escape values
   D/north 101           0.948        0.960       239/240                5/20

   The causal chain, all verified in source:

     1. _coverage_mode_active (:724-739) returns True for EVERY input with
        unresolved > 0. Lines :731-738 test steps_since_detection, corridor
        failure, boost > 0.2 and post_rescue, each returning True - and then
        :739 returns True unconditionally anyway. Those four tests cannot
        change the result, so the function is simply 'unresolved > 0'.
     2. _coverage_priority (:959-962) therefore raises base to >= 0.9 whenever
        a victim is unresolved, then :963 returns base + boost. Measured:
        coverage_w >= 0.9 on 239 of 240 steps in every run.
     3. coverage_w >= 0.9 sets min_escape_dist = max(min_escape, 20.0) at
        :3147-3148. Measured min_escape_dist only ever takes the values above -

   the grid filtered out. The coverage bonus is being asked to steer inside a

SUGGESTION (not part of the diagnosis; recorded after both verdicts)
==============================================================================

The next change should be a GENERATOR change, and the target-diversity gap in
Q6 is the thing to attack: 12-14 distinct proposed cells in failing runs
versus 37 in the succeeding one. Three candidate root causes are visible in
the data and are worth separating before designing anything:
  1. The 30-step rolling window (:913, :917). A lifetime visited-cell or
     visited-coarse-bucket structure would let the exploration term see real
     gaps. This is a state-representation change, not a weight tweak.
  2. corridor_waypoint_calls == 0 in ALL FOUR RUNS. _generate_corridor_waypoints
     never executed; every target came from _pick_global_coverage_escape_target
     (185-209 steps) or a bare _finalize_coverage_target escape (30-54 steps).
     An entire intended target-generation path is dead at HEAD, which would
     explain why so few distinct cells are proposed. Worth confirming why
     before tuning anything that assumes the corridor path runs.
  3. NEW, and the strongest of the three: coverage_y_commit. It is a FILTER,
     not a weight (:3192-3199). Q8-B shows it removing 100% of every victim's
     observation-post set on 20 of 21 measured steps per run, in all four runs.
     Whatever is done to the scoring terms cannot reach a cell that was never
     scored. This should be settled before any term is re-weighted, and it is
     a different kind of change from either of the above.

Re-weighting _uncovered_region_bonus is NOT indicated, and Q8 sharpens why.
Its spread is already large, so scaling it changes the argmax without making
it track coverage; and it sits under a term with roughly 20x its range, so a
proportionate increase would have to be very large to matter. Both
double-counts (:1001 + :3235 for the coverage bonus, :999 + :3232 for
never_seen) should be resolved on their own merits regardless, since each
silently applies a term at twice its nominal weight.
