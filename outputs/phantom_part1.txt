3. IS DOUBLE-ASSIGNMENT EVER LEGITIMATE?  YES - AND IT IS LOAD-BEARING
--------------------------------------------------------------------------------
The replacement pathway is built on it. A unit blocked for the second time on
the same victim keeps its task (the handler deliberately does not unassign it a
second time) and resumes by itself when its route reopens (agents.py 1553-1556,
the only in-run clear). Meanwhile the victim shows no visible claimant and a
replacement is sent. Two live claimants is the intended state of that pathway;
whoever gets there first should rescue, and the other should be released.

Measured in the sample: in the one episode (303), the SECOND claimant did the
rescue (analyzer outcome second_rescued@101). ff_unit_1, the first claimant,
did not reach the target cell until step 148 - 47 steps later, with victim_0
fleeing fire in the meantime. Preventing the second claim would have made
victim_0's rescue depend on the blocked unit.

Both variants of fix (a) fail:
  (a1) make the executor guard use the same lookup as the planner
       -> a no-op in real runs (the planner already refuses on that lookup);
          it changes only direct executor callers such as the probe and tests.
  (a2) make the guard count route_blocked claimants too
       -> refuses the replacement while a blocked unit holds the victim: the
          replacement pathway stops working the second time a pair blocks.
          Rescued can only go down.
This is the same shape as the two load-bearing guards the campaign already
tripped over (#7 clearing site, last_cell exclusion). (a) is rejected.

DECISION: (b) RELEASE. Add a release on rescue_complete. The assign guard
(3807-3812), the planner lookup, and _blocked_replacement_attempted stay
exactly as they are.

4. FIX (b) - DESIGN
--------------------------------------------------------------------------------
4.1  One new model helper, wildfire_model.py, next to _find_active_firefighter_
     for_victim:

     _release_other_claimants(victim_id, victim_marker, keep_ff_id, reason) -> list[str]

     For every unit in firefighter_marker_agents:
       skip  ff_id == keep_ff_id                (the completing unit, section 4.3)
       skip  dead / status "dead"               (casualty path owns corpses; an
                                                 unassign would relabel a dead
                                                 unit's managed state "available")
       skip  rescue_completed True              (a unit that finished its own exit
                                                 this step; the drain recycles it)
       bound test: rescued_victim is victim_marker, or its id == victim_id.
             NOT gated on `assigned`, NOT gated on status: route_blocked
             claimants are the whole point (sections 2 and 6).
       release: executor unassign, metadata {} - deliberately NOT
             reset_victim_pending: that flag relabels the victim marker
             "confirmed" unconditionally, and the victim here is terminal.
       then: if status is "en_route" or "assigned" -> status = "available"
             (route_blocked is left for the revalidation pass; see 4.4), and
             re-sync that unit's operational knowledge, because the unassign
             action's own sync ran while status was still "en_route" and
             _derive_firefighter_operational_fields (3586) maps status
             "en_route" with assigned=False to availability "assigned" - a stale
             label the victim_dead recall leaves behind today.
       print "[Rescue Released] FF-x released from victim_y (reason)" and bump
             ff_claims_released_total. No new rescue-event type: the executor
             already records a physical_unassign event for the command.
     Returns the released ids. A run with no second claimant emits nothing, so
     unaffected runs stay byte-identical (Part 3 gate).

4.2  Call site: the rescue_complete branch (3151-3189).
       - after execute_physical_command(finalize_rescue), when result["success"]:
           self._release_other_claimants(vid, agent, ff_id, "released_after_rescue_complete")
       - in the already-rescued early return (3157-3158) as well, before
         returning: arriving here for a rescued victim IS the phantom's
         signature (the 149 completion in 303). It is idempotent - normally
         nothing is bound any more - and costs one loop over 2-3 units.
     Nothing else in the branch moves; coverage activation stays after the
     release. The reason string "released_after_rescue_complete" is what the
     analyzer keys on.

4.3  The completing unit is excluded and must not be touched here. In the
     drain (_process_pending_agent_removals, 2530-2600) the Firefighter entry
     calls _finalize_rescued_victim(vid, rescued_victim, firefighter_id=unit_id)
     and THEN removes/recycles the unit itself; the unassign action would clear
     its `exiting` mid-hand-over. Exclusion is by the incident's ff_id, with
     rescue_completed as the belt-and-braces (a completer always has it True
     by then, an en-route claimant never does). If the victim entry ever came
     first with no ff_id, _firefighter_id_for_victim would read
     managed_victims[vid].firefighter_id = the LAST assigned unit, which in a
     double claim can be the loser - the rescue_completed skip is what keeps
     the true carrier safe in that order too.

4.4  Released unit: made immediately available for dispatch, in place.
     Not recycled: _recycle_firefighter_after_exit is the boundary hand-over
     reset (it also clears rescue_completed and prints Recycled); a loser is
     mid-field with nothing to hand over, and walking it to an edge would be
     more wasted movement. Not left as-is either (the "en_route" label).
     State after release: assigned False, target_pos None, rescued_victim None,
     exiting False, exit_target None, rescue_completed unchanged (False),
     status "available" (or route_blocked, unchanged), pos unchanged.
     _firefighter_available_for_dispatch (2842-2853) checks dead / status in
     (dead, route_blocked) / assigned / exiting / rescue_completed / pos - so the
     unit is in the pool immediately. Firefighter.advance with no target and
     not exiting takes the idle branches (idle retreat from fire, standby,
     hold), the same path every recalled unit takes today.

4.5  Cannot strand a unit - the 70e1b33 shape checked explicitly:
     - non-blocked loser: dispatchable at once. The drain's own
       _try_dispatch_unresolved_confirmed_victims runs right after (recycled>0
       because the completer was just removed/recycled), so it can be
       re-dispatched in the same step.
     - route_blocked loser: assigned False, exiting False, pos not None ->
       exactly the set _revalidate_route_blocked_firefighters (2431-2508)
       scans every step from _sync_firefighter_marker_status; it flips the
       unit to "available" as soon as a fire-free path to ANY live victim
       exists and calls _try_dispatch_unresolved_confirmed_victims. The 70e1b33
       latch was a unit in this state with NO revalidation; the revalidation is
       what closed it and it applies unchanged here. If no live victim exists
       the unit stays route_blocked with no work to do, and recovers the step
       a new victim is confirmed (the pass runs every step).
     - the completer: untouched, handled by the drain as today.
     Part 3 asserts this on every released unit from the per-step
     ff_bind_steps observer (section 8): later in the dispatch pool, or later
     assigned, or dead/off-grid, or no confirmed victim left.

4.6  What does NOT change: the assign guard, the planner lookup,
     _blocked_replacement_attempted, the unassign action, Feature 1 and
     Feature 2 code, the Victim custody clause (a rescued victim is off-grid).

4.7  Feature interactions:
     - Feature 1: the phantom completer no longer completes, so no phantom
       absence is drawn. The absence RNG is a dedicated stream seeded once from
       SYSTEM_RANDOM.getstate(); one fewer draw from it changes nothing in the
       shared stream. Fire digests must stay identical on all 13 runs (gate).
       Feature 2 moved firefighter deaths 6 -> 8 by tying units up longer; this
       fix frees a unit ~48 steps earlier in 303 and removes a 3-step absence.
       Part 3 reports whether any of the +2 comes back.
     - Feature 2: _refresh_target_from_victim already stops on a terminal
       victim; the loser was walking to the last cell it saw. After the fix it
       has no target. No change to the flee rule or leash.

5. DISPATCH-POOL RE-ENTRY: THE STEP-ORDER ARGUMENT
--------------------------------------------------------------------------------
Within one step: schedule.step() (moves; a completer flips rescue_completed and
queues itself + victim) -> post-move cycle: _return_absent_firefighters at the
head of the drain, the drain (finalize -> release -> completer removed or
recycled -> re-dispatch pass), then _check_fire_casualties, then the
route_blocked revalidation in _sync_firefighter_marker_status (order as stated
in the _return_absent_firefighters docstring, 2323-2330). So a released unit is
visible to the re-dispatch pass in the same step, and a released route_blocked
unit is revalidated in the same step.

6. SIBLING GAP FOUND WHILE VERIFYING: THE victim_dead RECALL HAS THE SAME HOLE
--------------------------------------------------------------------------------
The victim_dead branch releases via _find_active_firefighter_for_victim, which
skips route_blocked units and returns one pair. D/south/half 303 (recorded):
  step 156  ff_unit_0 -> victim_3 (replacement_after_blocked)
  step 199  blocked -> unassigned -> delay; step 207 re-dispatched to victim_3
  step 216  blocked AGAIN (early return: stays assigned, route_blocked)
  step 216  victim_3 dies at (49,2). victim_dead recall: lookup skips the
            route_blocked unit -> nobody unassigned.
  step 222  route reopens -> status "assigned" -> ff_unit_0 walks toward the
            corpse's cell; still bound at the 240 horizon (DEAD-BOUND 24 steps).
Had the run been longer it would have arrived, flipped exiting against a dead
marker, dragged that marker to the boundary, and taken an absence; the drain
would then set the dead marker's status to "rescued" (2557-2560) - managed
state stays "dead", so counts are safe, but it is the same phantom shape.
No capacity was lost in this run (all victims were terminal at 216).

RECOMMENDATION: route the victim_dead branch through the same helper
(keep_ff_id="", reason unchanged "fire_casualty"/"victim_dead_recall"). For the
common case - one visible claimant - it issues the identical unassign command;
the only added effects are (i) route_blocked and second claimants are released
too, (ii) the status relabel of 4.1. This is one helper, two call sites, and
the analyzer reports the two paths separately (release reason vs dead-bound
count), so attribution in Part 3 stays clean. Alternative: rescue_complete only,
and file the dead-bound case as a follow-up.
