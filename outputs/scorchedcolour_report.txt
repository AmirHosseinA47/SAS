4.2  has_burned_cells IS NOT THE SCORCHED COUNT, AND SCORCHED CANNOT BE
     RECOVERED BY SUBTRACTION IN THE BROWSER.

    This is why 2.4 relabelled the tile but did NOT change its number.

    From agents.py:26, :105-106, :109-110 - has_burned is set the first
    spread-tick a cell is burning and is NEVER cleared, and burnt implies
    has_burned. So

        has_burned = burnt UNION scorched UNION (burning cells past one tick)

    It is a cumulative "ever ignited" figure that also counts cells the map
    paints orange and grey. "ever burned" is an honest label for it; "charred"
    was not, and after the split "charred" would have named a map colour that
    no longer exists as a single thing.

    The tempting cheap fix - derive scorched in the JS - is arithmetically
    unsound. FIRE_SPREAD_SPEED is 3 (common_fixed_variables.py:23). Ignition
    happens in advance() (agents.py:125), but has_burned = True is set in
    step() only when steps_counter % 3 == 0, so a freshly-ignited cell carries
    burning=True with has_burned=False for three steps - the entire leading
    ring of the fire front. Therefore

        has_burned_cells - burnt_cells - active_fire_cells
            = scorched - |burning AND NOT has_burned|

    which CAN GO NEGATIVE. A subtraction-derived tile would be wrong by the
    size of the fire newest ring and could render a negative count.

    A correct scorched tile needs one accumulator in the existing loop in
    dashboard_state_builder.py _build_fire_view, publishing "scorched_cells"
    and using the renderer split predicate VERBATIM so tile and map can never
    disagree. DEFERRED - that file was not in this round scope, and it is a
    data-model addition rather than a rendering change. It was checked and
    would be stdout-safe: get_dashboard_state output is never printed in a
    headless run (evaluate_scenarios.py:128 and evaluate_extended_metrics.py:61
    read only mission_status.all_victims_terminal, both inside
    redirect_stdout; wildfire_model.py:4641 only assigns it), fire_view is
    typed dict[str, Any] in contracts.py:84 so no contract change is needed,
    and _slim_panel passes fire_view through unfiltered so the JS would receive
    it with no plumbing.

4.3  "burnt" IS RENDERED IN AMBER IN BOTH STAT PANELS.

    serve_dashboard.py:681 and live_dashboard_panel.py:206 both style
    burnt_cells with the amber (caution) token, while the number that carries
    the danger is unstyled. Burnt is the SAFEST ground in the model - 0
    re-ignitions in 23,126 opportunities. This is the same class of
    operator-facing inversion as the colour merge just fixed, one layer up.
    Not changed: it is outside this round scope, and it deserves to be decided

  display; a hatch or stipple on scorched cells would be robust to every
  deficiency at once. Follow-up, not a blocker.
