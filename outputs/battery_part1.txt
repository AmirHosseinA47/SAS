   and never touched since.

   because UAVs move on 236.6 of 240 steps: 0.297/step measured, so the level
   at step 240 is 28.0-34.6 (mean 28.7). Consequences inside the canonical
   horizon: the 30% gate is crossed in the last 1-7 steps (47 of 52 UAV-runs,

   mean-battery "worsening" test is true on every step from 3 (3,094 of 3,094).
   The 15% gate is never reached (minimum 28.0; earliest possible step 284).

    def _update_battery_after_step(self, moved: bool) -> None:
        """Apply per-step and per-move drain; update status labels (no movement or planning effects)."""
        self.battery_level -= self.battery_drain_per_step
        if moved:
            self.battery_level -= self.battery_drain_per_move
        self.battery_level = max(0.0, min(100.0, float(self.battery_level)))
        if self.battery_level <= self.battery_critical_threshold:
            self.battery_status = "critical"
        elif self.battery_level <= self.battery_low_threshold:
            self.battery_status = "low"
        else:
            self.battery_status = "normal"

    def advance(self):
        move_x = [1, 0, -1, 0]
        move_y = [0, -1, 0, 1]
        current_time = float(self.model.evaluation_timesteps_counter)
        pos_before = self.pos
        intended_delta = (move_x[self.selected_dir], move_y[self.selected_dir])
        moved = self.move()
        self._update_battery_after_step(moved)
        if self.local_monitor is not None:
            self.local_monitor.finalize_step_after_move(
                self, pos_before, self.pos, intended_delta
            )
            self.latest_local_observation = self.local_monitor.collect_observation(
                self, current_time
            )
            buf = getattr(self.model, "monitoring_buffer", None)
            if buf is not None:
                buf.add_local_observation(str(self.unique_id), self.latest_local_observation)

move() (309-336) reads selected_dir and pos only. Its first branch (322-324)
is the movement contract that any return-to-base leg has to respect: when the
MAPE pipeline is active and no executor committed a direction this step, the
UAV does not move and stamps execution_action = "no_managed_direction_hold".
Nothing in move() or advance() reads battery_level or battery_status. The
class comment, the method docstring and the code agree: on the agent, the
battery is a counter that is decremented and labelled, and nothing more.

The arithmetic that the rest of this report keeps coming back to: with the
drain above, level(t) = 100 - 0.1*t - 0.2*m(t), m = moves so far. At the
canonical horizon t = 240 that is 76 - 0.2*m. The agent's "low" label (<=30)
needs m >= 230 moves in 240 steps; "critical" (<=15) needs m >= 305, i.e. is
UNREACHABLE inside a 240-step run by construction, whatever the UAV does; the
knowledge runway gate PRUT < 120 needs level < 36 on a step the UAV moved,
i.e. m > 200 by step 240; the global monitor's third branch (< 20) is likewise
unreachable. The measurements below confirm these bounds are not approached.

      next_action with "hold" (decision_dispatcher.py:495-496).
    executor: "hold" for a non-searcher reaches _execute_hold (uav_executor.py:
      523-529), which returns the CURRENT selected_dir with the label "hold"
      (or an escape direction when stuck). A hold does not hold: the UAV keeps
      its last heading. Measured: moves per UAV under emergency are unchanged
      (232-240 vs stock 229-240), stationary steps after onset 0-7; the fire-
      tracker actions fire_flank_relocate / fire_safe_standoff / fire_flank_
      hold vanish after onset and the trackers ride their heading to the grid
      edge and stay there ((0,6), (0,16), (0,49), (38,1), (48,0), (22,0) at
      step 240). Victim searchers mostly keep searching: the "hold" branch
      re-enters _resolve_direction_intent("victim_search_wind_aware") whenever
      the wind-search state asks for a retarget (140-399 such steps per run).
    the battery: reaches 0.0 between step 41 and 88 and stays there (the clamp
      at agents.py:275). Nothing notices: no dead, landed or grounded state
      exists; the UAV keeps flying at 0.0 for 150-200 steps, PRUT is 0,
      CRITICAL_BATTERY fires on, the mode stays emergency.
    the mission: identical rescue outcomes and identical fire on all six
      forced runs. The trackers' abandonment of the fire and the drift to the
      edges cost nothing in _build_evaluation's terms on these three seeds
      (the evaluation has no UAV or fire-tracking term; detection had already
      happened where it mattered).

So the one gate that can act, acts like this: it does not return anything
anywhere, it strands the fire trackers on a heading, and it leaves a UAV at
0% battery flying. The name "return_to_base" appears in the preferred-action
list, in the fallback catalogue and in the dispatcher's override token, and is
outranked by 0.01 in the only mode that could pick it; even if it were picked,
the dispatcher would drop the path (no producer emits a path containing
"return"/"base"/"home"/"rtb") and the UAV would take the managed hold at
agents.py:322-324 instead.

2.7  CLASSIFICATION AGAINST THE CAMPAIGN'S TAXONOMY (item 5)
--------------------------------------------------------------------------------
The battery is not one instance; its pieces fall into five of the classes the
campaign has already named, plus one new one. In the campaign's terms:

(a) DEAD-INPUT (reader of a permanently absent input) - the class of
    _DELAY_CANCEL_BONUS, the role string/dict mismatch, belief_gap_regions and
    the global utility vector (globalplanner_scope.txt 1.3). Three further
    sub-instances here, all measured:
      - constraint_filter._battery_reasons reads runtime_models["battery"] /
        ["battery_state"]; neither key is ever created (wildfire_model.py:
        1684-1696): None on 555,100 of 555,100 calls, 0 rejections.
      - utility feasibility reads params battery_level / projected_battery_
        after_option: present on 0 of 483,428 calls. (The weighted terms
        battery_cost / battery_pressure / energy_failure_risk are the seventh
        instance already counted; re-verified absent in every scope.)
      - the local analyzer's primary input, latest_local_observation
        ["battery_level"]: absent on 12,480 of 12,480 calls (buffer cleared
        before analysis). The knowledge fallback is the only live path. The
        unit test for this branch (test_local_analysis.py:89) feeds the dict
        by hand.
(a') DEAD-VALUE (input present, value constant and unable to raise a term) -
    the Cost_switch / role_switch_count=None variant of (a):
      - "battery" / "battery_state" params on every global and fail-safe
        option: always None.
      - uav_resource_model.py:185-190's own 20/50 status gates: computed
        12,480 times, overwritten 12,480 times by update_uav_state:119.
      - mission min_battery (0.15-0.35): a fraction compared to nothing.
(w) WRITE-ONLY (written every step, read by nothing) - the class of
    should_return_to_normal and sop.mission_mode:
      - UAVExtensionState.battery_level/status (12,480 writes; the only read
        is the getattr default on the writer line)
      - LocalObservationModel.local_battery_state (12,480 writes, 0 reads)
      - LocalUAVMonitor._resource_snapshot (12,480 computed, 0 used)
(u) UNREACHABLE GATE (a correct branch that arithmetic keeps closed) - the
    class of _move_toward tier 2:
      - every "critical" gate (agent 276, analyzers 142/703, monitor 349):
        needs step 284 at the 0.3 ceiling; horizon is 240. Minimum seen 28.0.
      - global_monitor.py:355 (0 < bl < 20): shadowed by 352.
      - global_analyzer.py:766 (>= 2 critical UAVs).
(t) ALWAYS-TRUE GATE - new, the mirror image of (u): TREND_WORSENING's
    mean_battery test (global_analyzer.py:1494) is true on 3,094 of 3,094
    steps because a monotone counter beats an absolute eps of 0.02 every step.
    Information-free by construction, and consumed by nothing by name.
(r) REACHABLE, PRODUCED, CONSUMED, INERT - the piece with no exact precedent:
    LOW (<= 30) and the runway gate (PRUT < 120) DO open late in the horizon
    and DO produce triggers that DO reach the generators and the fail-safe
    planner as text - and the seed-matched counterfactual shows zero effect.
    This is the dead-input class seen from the producer's side: the producer
    and the consumers are both live, the mapping between them (LOW_BATTERY ->
    no reason; trigger names -> substring flags already set by other triggers)
    is what is missing.

Which instance does it resemble most? Not any single one. What makes the
battery different from the seven dead-input instances is that the producer is
real and correct (the drain), the observation chain is real and correct
(agent -> LocalObservation -> knowledge -> analyzers -> dashboard), and the
disconnect is PARAMETRIC (gates placed where drain x horizon cannot reach) and
ACTION-LEVEL (the one reachable-by-forcing gate produces a heading-hold, not a
return). Its nearest relative is the _move_toward tier-2 gate: a branch that
is written, correct as far as it goes, and mathematically closed under the
evaluated conditions. The difference is that the battery's closed branch
would not do the right thing even if it opened.

3.1  VERDICT (item 6)
--------------------------------------------------------------------------------
(B) TRACKED BUT INERT.

A battery exists on the UAV agent, depletes every step, and is tracked
faithfully by monitoring, the knowledge model, the managed mirror and the
dashboard. Over the canonical 240-step horizon nothing acts on its value:
pinning it at 100 reproduces every UAV cell, every burn and every outcome of
all 13 stock runs exactly, while three battery-driven trigger streams
(LOW_BATTERY from step 235, RESOURCE_DEGRADING from step 215, TREND_WORSENING
on every step) come and go without touching a decision.

Two qualifications, both needed for scoping:

  - There is a sliver of (A) behind a gate the drain cannot reach in 240
    steps: CRITICAL_BATTERY (<= 15, earliest step 284). Forced open, it does
    act - but only with a co-occurring collision reason, only as EMERGENCY /
    safe_hold, and safe_hold keeps the current heading. Fire trackers ride
    to the grid edge, searchers keep searching, the battery reaches 0 and the
    UAV flies on. That is not a return, and a 300-step run (the
    evaluate_scenarios.py default) would reach it in its last ~16 steps.

  - Everything base-station-specific is (D) ABSENT: no base cell (the spawn
    cluster at the grid centre is not stored), no recharge path (battery_level
    only ever decreases), no return leg (return_to_base is a token whose only
    effect is to drop a path, and it is outranked by 0.01 in the one mode that
    could choose it), no landed / charging / dead state, no exclusion of a UAV
    from the lane and sector lists, and no pos-None tolerance in the UAV
    consumers.

What (B) would need wired, in one line each (the detail is 3.2):
  1. one threshold source (today five inconsistent copies; the agent's own
     30/15 are hardcoded and unreachable by apply_scenario_config);
  2. a gate that fires at the return threshold and reaches an action - either
     a managed-side check next to the drain, or a SafetyChecker mapping for
     LOW_BATTERY plus a fail-safe action that is not pre-empted by the
     information-recovery reasons present on 239 of 240 steps;
  3. a base cell, and a return leg built on the executor's existing
     _direction_toward primitive;
  4. a charging state with the role-loop exclusion (lanes, sectors) and the
     re-entry, on the feature 1 removal/return pattern;
  5. the recharge itself (the first code path that ever raises battery_level);
  6. pos-None guards on the seven UAV position consumers if the base is
     off-grid, and dashboard/metric fields that say "charging".

3.2  INTEGRATION POINTS A BATTERY-DRIVEN RETURN-TO-BASE WOULD NEED (item 7)
--------------------------------------------------------------------------------
Named, not designed. Each point is where the existing code already touches the
concept, what it does today, and what is missing. Where two homes are possible
both are named with the measured facts that bear on the choice.

(i) DEPLETION - exists. agents.py:270-281, called once per UAV per step from
    advance() (346), after move(). It is the only writer of battery_level and
    the only place the drain constants are read. What is missing:
      - a way UP. There is no code path anywhere that increases battery_level;
        a recharge branch would be the first. The clamp at 281 already caps at
        100, so a recharge that overshoots is harmless.
      - one source of truth for the constants. The drain (0.1/0.2) and the
        agent's 30/15 gates are hardcoded on the instance (237-242) and are
        not in common_fixed_variables, so apply_scenario_config cannot reach
        them and a per-run override is impossible today. The same two numbers
        exist as cfv LOW_BATTERY_THRESHOLD/BATTERY_CRITICAL_THRESHOLD (read by
        the analyzers and the alert manager), as 15/30/20 literals in
        global_monitor.py:349-356, as 20/50 in uav_resource_model.py:185-190
        (dead-value), and as 50/20 in the two dashboard colour maps. A return
        threshold is a FIFTH number unless the copies are collapsed. The
        precedent for reading cfv at call time from agents.py is
        victim_flee_trigger_distance (agents.py:359-371), written exactly so a
        per-run override is visible to the agent.

(ii) THE THRESHOLD CHECK - two candidate homes, neither exists today.
    (a) Managed side, next to the drain: a check in UAV.advance()/move()
        (agents.py:339-356 / 309-336) that flips the UAV into a returning
        state when battery_level <= the return threshold, the way features 1
        and 2 were built as managed-agent rules with no MAPE involvement.
        Nothing there reads the battery today; the movement contract at
        322-324 (no committed direction -> hold) is what the returning state
        would have to pre-empt.
    (b) Managing side, through the pipeline that already exists:
        LocalUAVAnalyzer/GlobalAnalyzer LOW_BATTERY/CRITICAL_BATTERY (E) ->
        SafetyChecker reason critical_battery -> ModeManager mode ->
        FailSafePlanner fail_safe_action -> DecisionDispatcher override ->
        UAVExecutor. Measured facts that bear on (b), from 2.6:
          - only CRITICAL_BATTERY produces a reason; LOW_BATTERY maps to
            nothing in safety_checker.py:18-28, so "return at 30%" through (b)
            needs a new mapping.
          - critical_battery alone classifies as DEGRADED, and is pre-empted by
            information-recovery / safety-first reasons that are present on
            most steps of every run; the planner then never chooses
            return_to_base (2.6 shows what it chose instead).
          - even when return_to_base IS the action, decision_dispatcher.py:
            483-516 has no path to give: it keeps the local path only if the
            path text contains "return/base/home/rtb", otherwise drops it and
            the UAV holds. There is no base cell, no path producer, and
            _dispatch_fail_safe (192-231) cannot address a UAV because the
            fail-safe options carry target_entity "uav", a literal.
          - the analyzers see the knowledge copy, one step stale (2.4), which
            is fine for a threshold but means the reaction lands one step
            after the crossing.
        Whichever home is chosen, the gate itself is one comparison; the work
        is everything in (iii).

(iii) TAKING A UAV OUT OF ITS ROLE LOOP AND PUTTING IT BACK
    The role loop, per step, pre-move (adaptation_manager.py:80-128):
      _run_analysis (per UAV with a resource-model entry, wildfire_model.py:
      1626-1643) -> local_adaptation_generator.generate per local_result
      (1699-1719) -> planning_coordinator local path planner per UAV ->
      decision_dispatcher._dispatch_local_paths -> UAVExecutor.execute ->
      _commit_execution_direction (uav_executor.py:140-145) -> agents.py
      move() at schedule.step().
    Existing precedence mechanisms a return leg could reuse:
      - the dispatcher's fail-safe override (decision_dispatcher.py:427-516):
        already knows the token "return_to_base"; today its only effect is to
        drop the path.
      - the executor's target-following primitives: _execute_search_mode
        (735) / _execute_role_preserving_search point a UAV at a target
        through _direction_toward(agent, target) (4566-4589), a greedy,
        bounds-checked one-step-toward. A return leg is "_direction_toward
        (agent, base_cell)" plus a way to say which UAVs are on it.
      - the managed-side hold contract (agents.py:322-324): a UAV with no
        committed direction stays put. A charging UAV that is on-grid could
        simply be given no direction.
    What has no mechanism today:
      - a base cell. The only base-like geometry is the spawn cluster,
        wildfire_model.py:142-160: four cells around (HEIGHT//2, WIDTH//2),
        centre of the grid, and it is not stored anywhere after placement.
      - a returning/charging state on the UAV, and its exclusion from the
        role loop. Roles live in managed_uav_states[uid].role
        (wildfire_model.py:657-689 _assign_uav_roles, mirrored into the
        knowledge model's current_role) and are read by
        resolve_victim_searcher_uav_ids (lanes) and _uav_assignment_role
        (sectors, 320-338). A UAV that keeps its role while returning keeps
        its lane/sector; a UAV whose role changes reshuffles everyone's (see
        (iv)).
      - taking a UAV OFF the grid, if the base is off-map: feature 1's
        removal/return pair is the template - _remove_firefighter_for_
        rescue_absence (2179-2230: grid.remove_agent, status "off_grid",
        absent_until_step, exit cell, log + counters) and the return at the
        head of the post-move cycle (2324-2392: place_agent at the exit cell,
        flags cleared, logged). Feature 1 could rely on every consumer
        already treating a firefighter's pos None as "not here"; for UAVs
        that is NOT true (see (iv) and 3.3).
      - putting it back: role restored (both copies), re-placed, re-entered
        into the lane/sector lists (automatic, since both are recomputed from
        the live role list), monitor re-attached if it was detached.

(iv) WHO NEEDS TO KNOW
    Searcher lanes - local_adaptation_generator.py:276-318 + 332-364.
      The lane list is the sorted ids of schedule UAVs whose role is a
      searcher role, rebuilt on every call with no memo
      (outputs/lane_partitioning_investigation.txt:175-177). Consequences:
        - a UAV that leaves the searcher role mid-run shrinks n; the survivors'
          lanes reshuffle immediately (investigation 306-331, measured), the
          partition stays disjoint/gapless (981-985, verdict (b)), and the
          per-searcher targeting state that is lane-blind survives the
          reshuffle and was measured to self-clear (333-358). So a role change
          is handled, with a coverage discontinuity, not a crash.
        - a UAV that KEEPS the role while away is still counted: n does not
          shrink, its lane is assigned to nobody who is there, and nothing
          detects that. This is the silent case.
        - the return reshuffles again. Two reshuffles per charging cycle, per
          UAV.
    Fire-tracker sectors - wildfire_model.py:428-522, recomputed at the head
      of EVERY step (5279) from the sorted role list, split n ways along the
      longer axis of the fire's bounding box. Identical two cases: role change
      -> flanks reshuffle every cycle; role kept -> one flank unattended.
    Coverage scoring - _estimate_coverage_ratio (3072-3097) is belief-based
      (mean fire-confidence), not UAV-count-based, so it does not notice a
      missing UAV directly. uav_team_summary.total_information_gain
      (global_monitor.py:232) and the avg_normalized_information_gain gate
      (classify_events 360-370, information_collapse / low_information_gain
      events) DO: a UAV that is holding or away contributes ~0 gain, which
      pushes the fleet toward the search-mode fail-safe path. The same path
      is already active on most steps (2.4), so the marginal effect is small
      but real.
    Dashboard - uav_status_view (dashboard_state_builder.py:207) already shows
      battery; alerts at 30% (alert_manager.py:236); colours at 50/20 (live
      panel 269-270, serve_dashboard.py:692). No field says "returning" or
      "charging". serve_dashboard.py:156 indexes every UAV's pos unguarded.
    Metrics - _build_evaluation (serve_dashboard.py:286-325) has no UAV term;
      a charging cycle changes rescue outcomes only through detection and
      coverage. evaluate_extended_metrics.py:38-92 (tracker smoke/fire
      exposure) already skips pos None (71-72). MR1/MR2 (wildfire_model.py:
      2775-2806) index every UAV's pos unguarded and would need to skip or
      zero an absent UAV; MR1's per-UAV reward list is positional, so
      skipping changes its shape.

3.3  INTERACTIONS WITH WORK ALREADY DONE (item 8)
--------------------------------------------------------------------------------
Feature 1 (off-grid firefighter, pos None).
  The removal/return pair is the template (above). The break class is the
  same and it is WIDER for UAVs, because no UAV has ever had pos None: the
  lane investigation notes (line 22) that UAVs are never removed from the
  schedule, so no consumer was ever made to cope. Consumers that index a
  UAV position unguarded today, i.e. the serve_dashboard.py break repeated:
    serve_dashboard.py:156           int(a.pos[0]) for every UAV in the
                                     schedule - the exact shape of the
                                     feature 1 break
    wildfire_model.py:975            _detect_victims_in_uav_radius:
                                     px, py = uav.pos
    wildfire_model.py:2796-2798      MR2 pairwise distances
    wildfire_model.py:2808-2823      state() -> UAV.surrounding_states (294-
                                     307) -> grid.get_neighborhood(None)
    agents.py:328,343-350            move()/advance(): pos_to_move and
                                     pos_before; collect_observation
                                     (local_uav_monitor.py:313) int(uav.pos[0])
    global_monitor.py:58,194         _uav_team_summary iterates self.uavs, the
                                     list captured at CONSTRUCTION - removing a
                                     UAV from the schedule does not remove it
                                     here - and indexes pos unguarded
    uav_executor.py:369-371 (+3444,  boundary/pocket helpers int(agent.pos[0])
      3467, 4136, 4155, 4261)
  Already guarded: dashboard_state_builder (_coords, 38-41), stuck counts
  (2720), managed-state sync (727), _direction_toward (4569), the extended
  metrics (71-72), local_adaptation_generator (reads the knowledge
  current_position, 3349-3366, which would be stale rather than None).
  A charging UAV that stays ON the grid (charges in place on a base cell)
  avoids all of this and only needs the role-loop exclusion.

Searcher lane partitioning (outputs/lane_partitioning_investigation.txt).
  Confirmed against the source at fd743f5: resolve_victim_searcher_uav_ids
  is still role-based, sorted, recomputed on every call, no memo, no
  discontinuity handling. Handled: a shrink or grow of the ACTIVE list gives a
  well-formed partition immediately (the investigation's verdict (b)). Not
  handled, and new with a recharge mechanic: (1) the role-kept-while-away
  case, which the partition cannot see; (2) two reshuffles per cycle per UAV,
  each of which the investigation measured as a coverage discontinuity with
  stale targeting state that self-clears rather than being reset. Whether
  that cost matters depends on how often UAVs cycle, which depends on the
  return threshold and the charge time - numbers the brief does not fix.
  The tracker-sector split is the same problem with the same properties.

Feature 2 / phantom-rescue release.
  No interaction: victims and firefighters do not read UAV state. The one
  shared path is victim DETECTION (_detect_victims_in_uav_radius, run twice
  per step in both cycles): a UAV away from its lane detects nothing there,
  so a victim that spawned in that lane is found later or never.

Seed-matched harness discipline.
  The battery is deterministic (no RNG anywhere in (A)-(H)). A recharge
  mechanic stays seed-matched as long as it draws nothing from SYSTEM_RANDOM;
  if a charge duration is ever randomised, the feature 1 pattern
  (_make_ff_absence_rng, wildfire_model.py:2137-2177, a dedicated RNG seeded
  from the run seed) is what keeps _ffr_harness-style A/B comparisons valid.
