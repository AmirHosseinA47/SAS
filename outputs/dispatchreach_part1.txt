1.3  IS FIRE STATE REACHABLE AT THE CALL SITE?  NO - AND THIS IS STRUCTURAL
-----------------------------------------------------------------------------
  IN THE PLANNER: NO.  rescue_planner.py imports TriggerBatch,
  RescueDecision, planner_selection, mission_goal_integration and
  utility_evaluation - and nothing else.  No mesa, no grid, no wildfire_model,
  no agents.  select_rescue_assignment receives one argument that carries
  state, `snapshot: dict`, and that dict contains only step, victims,
  firefighters and incidents (built at wildfire_model.py:2578-2582).  There is
  no fire field, no grid handle and no model reference.

  A live BFS is therefore IMPOSSIBLE inside select_rescue_assignment without
  handing the planner a model reference, which is the managed/managing
  separation this codebase documents in docs/02_managed_vs_managing.md and
  which ffdeath_investigation.txt section 8 explicitly said not to break.

  IN THE MODEL: YES, and the precedent is already in the file.
  _revalidate_route_blocked_firefighters (wildfire_model.py:2139-2213, added
  in 70e1b33) does exactly this, on the model side, by borrowing the marker
  agent's helpers:

      fire_cells = ff_marker._fire_cells()                       # agents.py:617
      ff_marker._path_exists_avoiding_fire(cell, vcell, fire_cells)   # agents.py:1030

  So model-side code calling the marker's BFS is established practice in this
  exact file, added by this exact chain, and needs no change to agents.py.

  WHERE THE DATA WOULD HAVE TO BE COMPUTED, THEN:
    * COMPUTED in wildfire_model.get_rescue_operational_snapshot (:2497), in
      the firefighter loop at :2544-2568 - the same loop that already calls
      _firefighter_available_for_dispatch, so the availability set is already
      in hand there;
    * CARRIED as a new per-firefighter snapshot field, alongside "available"
      and "route_blocked";
    * CONSUMED in rescue_planner.select_rescue_assignment at the sort, :624.

  ONE WRINKLE THAT SHAPES THE FIELD: reachability is per (firefighter,
  victim) PAIR, but the snapshot is built before the planner picks a victim.
  A scalar per firefighter cannot express it.  The field would have to be the
  set of victim IDs that firefighter can currently reach - which one
  flood-fill per available unit produces for all victims at once.  This is the
  same objection ffdeath_investigation.txt section 8 raised against putting
  reachability on "available", and it survives: "available" is a fleet-status
  concept consumed by the dashboard, the knowledge model and
  adaptation_manager, and it is not per-victim.

  COST OF PUTTING IT IN THE SNAPSHOT: the snapshot is built on EVERY step, not
  only at dispatch - _build_mission_goal_runtime_context calls it at :2583.
  So a snapshot-resident field is a per-step cost, not a per-dispatch cost.
  Section 3 measures both.

2.6  THE OBVIOUS CHALLENGE TO A NULL RESULT - AND IT LANDS
------------------------------------------------------------
  The challenge is "your reachability test was too permissive".  The test is
  the production one - _path_exists_avoiding_fire, the predicate 70e1b33 uses
  to release a route_blocked unit - so an appeal to provenance was available.
  It was not taken, because the objection deserves a measurement.  The
  near-continuous version of the same question was instrumented on the same
  91 dispatches: BFS SHORTEST PATH LENGTH, and detour = bfs - manhattan.

  THE OBJECTION IS CORRECT, AND THIS ROUND HAD DRAFTED THE OPPOSITE.  An
  earlier draft of this section asserted that every route was geodesically
  straight.  The measurement refuted it:

      candidate evaluations with a path length ......... 129 / 129
      ... with detour (bfs - manhattan) > 0 ............  13
      detour histogram: 2->3  4->2  6->3  12->2  20->1  28->1  32->1
      ... with no path at all ..........................   0

      multi-candidate dispatches whose two candidates
        DIFFER in detour ...............................   3 / 38
      ... of those, where the ORDERING actually flips ..   1 / 38

  SO THE BINARY TEST AND THE GRADED TEST GIVE DIFFERENT ANSWERS.  Binary
  reachability separates nothing, 0 of 38.  Route LENGTH separates the
  candidates on 3 of 38 and actually reverses the choice on 1 of 38.  That one
  is section 2.8, and it is the reason this round did not stop at "correct but
  inert".

  WHY THE BINARY TEST IS THE ONE THAT COMES BACK EMPTY - the mechanism, so
  the zeros in 2.1/2.3 are understood rather than merely observed.  The fire
  is a wind-driven front, not an enclosure.  A moving band across a 50x50 open
  grid disconnects almost nothing: to make a unit unreachable the band must
  close a full cut between it and the victim, which on this geometry
  essentially only happens when the unit is locally enclosed - and a locally
  enclosed unit is ALREADY excluded from the pool, by route_blocked
  (agents.py:961, all four neighbours burning), which the availability filter
  reads at rescue_planner.py:589.

      THE POOL IS ALREADY PRE-FILTERED BY THE ONE CONDITION THAT WOULD MAKE
      THE BFS SAY NO.  A hard reachability filter is very nearly a second copy
      of route_blocked, applied to a pool route_blocked has already cleaned.

  That is a structural argument, not a sample-size one: it says the zeros in
  2.1 and 2.3 should be expected to hold, not merely that they held here.
  What the band DOES do is bend routes around itself - which is why the graded
  test finds signal where the binary one cannot.

3.1  THE SAME COST AS A MICROBENCHMARK, INCLUDING THE TRUE WORST CASE
----------------------------------------------------------------------
The aggregate above divides total BFS time by total wall clock, which hides
what a single call costs at a single moment.  outputs/_dr_cost.py times the
three pieces directly at eight points through a D/east 505 run, 200
repetitions each.  Milliseconds:

    step  fires   model.step()  _fire_cells()   BFS open   BFS full-flood
      30    119      2875.4         0.209         0.99          1.71
      60    403      2424.9         0.243         0.005         0.005
      90    263      1853.7         0.229         1.02          1.63
     120    197      1818.6         0.209         1.21          1.68
     150    154      2342.8         0.203         1.22          1.67
     180     49      2152.8         0.193         1.48          1.78
     210     31       933.3         0.182         1.77          1.76
     240     27      1011.1         0.184         1.53          1.75

  "BFS full-flood" is the TRUE worst case - a destination the search can never
  match, so it exhausts the entire reachable component instead of
  short-circuiting on arrival.  (An earlier version of this benchmark walled
  off the SOURCE's four neighbours to force a False; that drains the queue on
  the first iteration and measures the FASTEST case, not the slowest.  The
  number it produced, 0.001 ms, was wrong by three orders of magnitude and is
  not used anywhere in this report.)

  READ AGAINST THE ONLY DENOMINATOR THAT MATTERS: one model.step() costs
  0.9 to 2.9 SECONDS.  A worst-case full-flood BFS costs 1.8 MILLISECONDS -
  between 0.06% and 0.19% of a single step, incurred about four times in a
  240-step run.

  The step-60 row reads 0.005 ms on both BFS columns because at peak fire
  (403 burning cells) the sampled unit is enclosed and the flood drains
  immediately.  It is not a measurement error; it is the enclosed case, which
  is also the case route_blocked already catches (2.6).

  WHAT THIS MEANS FOR THE TWO PLACEMENTS OF THE FIELD:
    * dispatch-only (the 5.4 design): ~4 dispatches per run x up to 2 units x
      up to 4 needy victims = at most ~32 BFS per run, under 60 ms against a
      569-second run.  Free.
    * snapshot-resident on every step (the naive placement): up to 8 BFS plus
      one _fire_cells() per step, ~14 ms against a ~1800 ms step, so under 1%.
      Still small - but it is ~240x the dispatch-only figure, and quoting the
      dispatch-only number for it would be wrong.  This is why 5.4 opts the
      per-step caller out rather than paying it.

4. THE ARMS, BUILT AND RUN
================================================================================
Every arm is a runtime monkeypatch; NOTHING was written to source for this
section.  All four are applied the same way, and the way matters: the arm
SHRINKS THE CANDIDATE POOL AND RE-CALLS THE REAL PLANNER.  No arm reimplements

same payload, same decision_id, and, for the hard filter, the planner's own
no-firefighter branch rather than a probe's imitation of it.

5. THE DECISION
================================================================================
5.1  WHAT THE EVIDENCE RULES OUT
---------------------------------
  ARM A, THE HARD FILTER: REJECTED.  Three reasons, in descending order of
  force.

    (i)  IT IS VERY NEARLY A SECOND COPY OF route_blocked.  Section 2.6's
         mechanism argument: the only realistic way this geometry makes a unit
         BFS-unreachable is local enclosure, and locally enclosed units are
         already struck from the pool by route_blocked, which the availability
         filter reads at rescue_planner.py:589.  The filter would re-derive,
         with a BFS, a condition the pool has already been cleaned of.
    (ii) ITS ONE MEASURED FIRING BUYS NOTHING.  In 108 dispatches it has
         exactly one candidate to remove (east/half 333 step 44); the pool
         there is size 1, so removing it converts a futile assign into a
         futile delay - and the victim dies the next step either way, at
         Manhattan 53 from the only unit alive.  See 2.7.
    (iii) IT CARRIES A DOWNSIDE THE OTHERS DO NOT.  Emptying the pool routes
         into the planner's no-firefighter branch, which returns "delay" for
         initial and blocked reasons but "mark_unreachable" otherwise - and
         mark_unreachable is PERMANENT: the executor applies it
         (rescue_executor.py:349-372) and the planner's needy filter then
         skips that victim for the rest of the run (rescue_planner.py:556).
         Turning a transient route closure into a permanent write-off is a
         strictly worse failure mode than dispatching a unit that may still
         arrive.  This is exactly the risk ffdeath_investigation.txt section 8
         predicted, and nothing measured this round reduces it.

  ARM B, THE SOFT TIEBREAK ON BINARY REACHABILITY: REJECTED AS VACUOUS.  It is
  harmless - it cannot regress, because it only reorders when one candidate is
  unroutable and another is not.  But that population is EMPTY: 0 of 38
  multi-candidate dispatches on the standard sample, 0 of 7 on the extension.
  It would add a snapshot field, a planner branch and a BFS to express a
  preference that never once fires.  The brief calls this the honest fix on
  the assumption that 2(a) is near-zero.  2(a) IS near-zero - and the honest
  reading of that is that this particular fix has nothing to do.  SHIPPING IT
  WOULD BE ADDING MACHINERY TO DECIDE SOMETHING THAT IS NEVER IN DOUBT.

  ARM D, ROUTE LENGTH AS PRIMARY KEY: REJECTED.  Bit-identical to arm C on all
  23 runs (4.2), so it is a strictly larger change with a measured-identical
  effect.  The brief's own rule decides it: prefer the smaller change.

5.2  THE RECOMMENDATION
------------------------
  RECOMMENDED: ARM C - ROUTE LENGTH AS THE TIEBREAK, key (manhattan,
  bfs_length, id).

  THIS IS NOT AN OUTCOME ARGUMENT, AND IT WOULD BE DISHONEST TO DRESS IT AS
  ONE.  Arm C changed one dispatch in 108 and moved no seed's rescued,
  victims-dead or firefighter-deaths count.  ON OUTCOMES IT IS INERT - the
  same result the _DELAY_CANCEL_BONUS round reported, and it should be
  described in the same terms.

  The argument is that of the four designs it is the only one that is both
  correct and non-vacuous, and it is the smallest such change:

    * IT REPLACES AN ARBITRARY TIEBREAK WITH AN INFORMED ONE.  Where Manhattan
      ties, the stock code decides by (ff_s < str(best_ff)) - the firefighter's
      NAME.  That is not a policy, it is a deterministic coin flip, and
      section 2.8 catches it picking a 71-cell route over a 39-cell one.
      Replacing a coin flip with the route length the BFS already computed is
      an unambiguous improvement in decision quality, whatever the outcome.
    * IT CANNOT REGRESS THE PRIMARY KEY.  Manhattan stays first, so arm C is
      inactive except where the existing code has already declared the two
      units equally good.  Measured blast radius: 2 exact ties in 91
      dispatches.  It fired on one and left the other unchanged.
    * IT SUBSUMES ARM B AT NO EXTRA COST.  An unreachable candidate has BFS
      length None, which sorts last - so arm C already prefers the routable
      unit on a tie.  It delivers arm B's stated benefit and adds the graded
      case arm B is blind to.
    * ITS SIGNAL IS REAL WHERE ARM B'S IS EMPTY.  13 of 129 candidate
      evaluations have a nonzero detour and 3 of 38 multi-candidate dispatches
      differ on it.  Binary reachability: 0 and 0.

  WHAT IT DOES NOT DO, SAID BEFORE ANYONE ASKS:
    * IT DOES NOT RECOVER THE D/EAST 505 RESCUE.  That dispatch has margin 1,
      not 0, so arm C never consults route length there; and both routes were
      open AND geodesic, so nothing in the reachability family touches it.
      The gate item c4d5a25 failed stays failed by this change.
    * IT DOES NOT REDUCE FIREFIGHTER DEATHS.  14 in every arm.
    * IT DOES NOT ADDRESS THE DOMINANT FAILURE MODE.  Section 2.4: 40 of 91
      dispatches never complete; 29 of those had a pool of size 1 and no
      decision available to be wrong; and in all 11 that did have an
      alternative, the alternative was equally routable at every followed
      step.  What kills these dispatches is transit length and fire arriving
      during transit - not which unit was picked.

5.3  IF THE ANSWER IS "SHIP NOTHING", THAT IS DEFENSIBLE TOO
-------------------------------------------------------------
  Arm C is worth one dispatch in 108 and zero outcome deltas.  A reasonable
  reading is that this round's FINDING is the deliverable - "the reachability
  constraint is almost never violated at commitment, and the real failure mode
  is corridors closing mid-transit" - and that the code should be left alone.
  The measurement stands either way.  The recommendation above is what to
  build IF something is built; the choice is the user's, which is what the
  Part 2 stop is for.

5.4  IMPLEMENTATION SHAPE FOR ARM C, IF PART 3 IS AUTHORISED
--------------------------------------------------------------
  TWO FILES: wildfire_model.py and src_extension/planning/rescue_planner.py.
  agents.py is NOT touched - its BFS helpers are CALLED, exactly as
  _revalidate_route_blocked_firefighters already calls them.

  (1) wildfire_model.get_rescue_operational_snapshot (:2497) gains a keyword,
      include_route_lengths: bool = True.  In the firefighter loop
      (:2544-2568), for each unit passing _firefighter_available_for_dispatch,
      emit route lengths to every victim that needs rescue:

          "route_lengths": {victim_id: int | None}

      computed with the marker's own BFS over one _fire_cells() taken per
      snapshot.  Keyed per (firefighter, victim) because reachability IS per
      pair - a scalar on the firefighter cannot express it.  This is also why
      it does NOT go on "available": that key is a fleet-status concept read
      by the dashboard, the knowledge model and adaptation_manager, and
      ffdeath_investigation.txt section 8's objection to overloading it
      stands.

  (2) THE PER-STEP COST IS OPTED OUT, NOT PAID.  The snapshot is built once
      per step by _build_mission_goal_runtime_context (:2583, reached from the
      MAPE-K cycle at :1884) and only ~4 times per run for dispatch.  So
      :2583 passes include_route_lengths=False and keeps today's cost, while
      the dispatch sites (:2832, :2915, :3952 and rescue_executor.py:186) get
      the data by taking the default.  The default is True and the single
      per-step caller opts out, which puts one edit at one cheap call site
      instead of four edits across two files.

  (3) rescue_planner.select_rescue_assignment (:624-630): the sort gains the
      middle key.  ABSENCE OF THE FIELD MUST SORT AS A TIE, so that any
      snapshot built without route lengths - the per-step one, and any
      hand-built one in a test - reproduces today's behaviour exactly.

  RISK REGISTER, SUCH AS IT IS:
    * "available" is unchanged, so the dashboard, knowledge model and
      adaptation_manager see nothing new;
    * the no-firefighter branch is unchanged, so delay / mark_unreachable
      behaviour is untouched and the arm-A downside in 5.1(iii) is not
      incurred;
    * no new constant and no threshold, so there is nothing to tune;
    * 2 exact ties in 91 dispatches is the entire blast radius on this sample.
