SUMMARY OF THE ANSWER
------------------------------------------------------------------------------
The emitter is _gradual_escape_target (:1372-1399), reached from its ONLY call
site :3873 inside _compute_wind_aware_search_target.  It is a pure geometric
fallback that walks the searcher 12 cells toward ((x_min+x_max)//2,
(y_min+y_max)//2) = (24, 24) and lands EXACTLY on that cell whenever the
searcher is already within Manhattan 12 of it.  It is not lane-filtered and it
has no candidate set to filter - the grid centre is baked into the arithmetic.

It is NOT the _pick_global_coverage_escape_target centre fallback (:3548-3563).
That one was measured and it does not fire: 136 emissions on C_east seed 101,
0 out-of-lane, 0 at the centre cell.  It is also structurally unreachable on
this route (proof in Q1.4).

Chosen fix: hand _gradual_escape_target the SEARCHER'S OWN LANE BOUNDS instead
of the global grid bounds at :3873.  Reasoning in Q4.

Q1.3  WHY THE CELL IS EXACTLY THE CENTRE, NOT MERELY NEAR IT
------------------------------------------------------------------------------
Two ways to land exactly on (24, 24):

  (a) dist = |24-ax| + |24-ay| <= 12   ->  scale = min(1.0, 12/dist) = 1.0
      ->  tx = round(ax + (24-ax)*1.0) = 24, ty = 24.  The "gradual" step is
      not gradual at all inside a radius of 12; it snaps to the centre.
  (b) dist <= 1.0  ->  early return (cx, cy) at :1388.

And once the searcher has been dragged onto the centre ROW, it is stuck there:
dy = 24 - ay = 0, so ty = round(ay + 0*scale) = ay = 24 for every subsequent
call regardless of scale.  This is visible in the C_east trace below, where the
x coordinate wanders (21, 23, 24, 25) while y is pinned at 24.0 for all 35
violations.

Q1.4  WHICH FUNCTION RETURNS IT, AND UNDER WHAT CONDITION IT FIRES INSTEAD OF
      THE COVERAGE-MODE CANDIDATE LOOP
------------------------------------------------------------------------------
Structural proof that this branch, not the candidate loop, is taken:

  * _coverage_mode_active (:751-767) has exactly ONE False exit:
        unresolved = int(wind_state.get("unresolved_victim_count", 0) or 0)
        if unresolved <= 0:
            return False
    every other path falls through to `return True`.  So
        cov_active == False   <==>   unresolved_victim_count == 0
    i.e. every managed victim is in a terminal state (rescued / dead /
    unreachable).  Nothing else can turn coverage mode off.

  * force_coverage_escape is STICKY.  _apply_unresolved_coverage_mode (:1215)
    sets it True while coverage is active but has no path that clears it when
    unresolved later drops to 0 - it simply returns False early.  So after the
    last victim resolves, the flag survives and the outer gate at :3865 keeps
    firing.

  * Inside :3865, the inner condition at :3866-3872 is
        not cov_active AND (pocket >= 20 OR force_coverage_escape)
    whose second conjunct is IDENTICAL to the outer gate.  Therefore whenever
    the outer gate is open and cov_active is False, the inner branch is
    ALWAYS taken.

  * _gradual_escape_target never returns None (:1388, :1398, :1399 all return
    a tuple), so `if opp is not None` at :3876 is always true, and :3884
    RETURNS.  Control never reaches self._pick_global_coverage_escape_target
    at :3888.

  => When cov_active is False, _pick_global_coverage_escape_target is
     unreachable from this site.  Its other call site (:3765) is guarded by
     `if coverage_mode and _corridor_diversity_failure(...)`, which requires
     coverage_mode True.  So the :3548 centre fallback CANNOT produce a
     cov_active=False emission at all.  The brief's residual signature
     (cov_active=False) therefore identifies _gradual_escape_target uniquely.

  * The coverage-mode candidate loops at :3466 and :3640 are not merely
    outranked here - they are not consulted.  :3884 returns before
    _generate_corridor_waypoints (:3930 onward) is ever reached, and
    _pick_global_coverage_escape_target is skipped as shown.  This is why
    _lane_allows_cell never gets a chance to act: there is no candidate set.

Q2.  WHY C_east SPECIFICALLY?
==============================================================================
Three separable effects.  Two are real, one is not what it looks like.

Q2.1  WHAT MAKES COVERAGE MODE INACTIVE - AND IT IS A SCENARIO-SIZE EFFECT
------------------------------------------------------------------------------
cov_active == False is exactly unresolved_victim_count == 0 (Q1.4).  It is not
a mode the searcher chooses; it is "there is no unresolved victim left".  So
the size of the cov-inactive tail is set by how fast the scenario finishes its
victims:

      scenario   victims   firefighters   UAV split
      C              3           3        5 = 3 trackers + 2 searchers
      D              4           2        4 = 2 trackers + 2 searchers

C has FEWER victims and MORE firefighters than D.  It resolves its whole victim
set earlier, so a larger share of a fixed 240-step run is spent with
unresolved == 0 - which is precisely the regime in which the defective branch
is the only branch.  This is the scenario-size effect the brief hypothesised,
and it is confirmed by the cov_active=False share per combo in the table below.

Q2.2  WHY THE UPPER LANE AND NOT THE LOWER ONE - THE AXIS EFFECT
------------------------------------------------------------------------------
_searcher_crosswind_lane splits a 50-cell span into [0..24] and [25..49].  The
centre cell 24 lies INSIDE lane index 0 and OUTSIDE lane index 1, on either
axis.  So the identical bug is invisible on the searcher that owns the lower
lane and maximally visible on the one that owns the upper lane.  That
asymmetry is exactly what the committed post-clamp-fix matrix shows
(outputs/lane_matrix, 5 seeds per combo):

Q2.3  IT IS NOT A WIND-SPECIFIC EFFECT IN THE PHYSICS SENSE
------------------------------------------------------------------------------
Nothing in _gradual_escape_target reads the wind.  Wind matters only because it
selects the lane AXIS in _searcher_crosswind_lane (:350-357): east/west -> "y"
lanes, north/south -> "x" lanes.  The centre anchor pins the coordinate on
whichever axis it is; it becomes a lane violation only when that axis is the
partitioned one AND the lane is the upper one.  East/west therefore shows it as
a y violation, which is the axis the lane owns.

Q2.4  WHY C_east AND NOT C_west, WHICH HAS THE SAME STRUCTURE
------------------------------------------------------------------------------
It is not that C_east is uniquely broken - C_west has the same signature
(0.9508 / 0.5125).  C_east is singled out because it is the one combo whose
compliance FELL relative to its pre-clamp-fix baseline: it began at 0.822, the
highest of the eight, and the clamp fix removed a y-commit that had happened to
push the upper-lane searcher north, i.e. away from y=24 and back into its own
lane.  Removing the wrong mechanism exposed the centre anchor underneath it.
C_west started at 0.633 and still improved to 0.732 despite carrying the same
defect.  So C_east is the visible case, not a separate cause.

Q2.6  SO IS IT SCENARIO SIZE, WIND, OR STRUCTURE?  ALL THREE, RANKED
------------------------------------------------------------------------------
  STRUCTURAL (dominant).  cov_active=False is the enabling condition and it is
  purely "no unresolved victim remains".  Every combo spends 33-77% of its
  emissions in that state, and the defect is the only target source there.
  This is not specific to C or to east at all - it is 100% of the out-of-lane
  emissions in all eight combos.

  SCENARIO SIZE (real, secondary).  C reaches the all-terminal state earlier
  than D on three of four winds (66 vs 165 on east, 90 vs 141 on south,
  126 vs 166 on north; west is the exception, 144 vs 94).  On east - the combo
  in question - C is all-terminal at step 66 against D's 165, so C_east spends
  77.1% of its emissions in the broken regime, the highest of the eight, versus
  32.8% for D_east, the lowest.  That is the scenario-size effect, and C_east
  is its extreme.

  WIND (real, but only as axis selection).  Wind picks the lane axis, and the
  anchor pins the coordinate on whichever axis it is.  It becomes a lane
  violation when the searcher owns the upper lane.  The visible consequence is
  the east/west compliance split in Q2.2.

Q3.  DOES THIS PATH HAVE ACCESS TO LANE BOUNDS WHERE IT COMPUTES ITS TARGET?
==============================================================================
_gradual_escape_target itself: NO.  Its whole input is (ax, ay), the four grid
bounds, the two hazard sets and a step size.  It has no uav_id, no simulation
and no wind, so it cannot derive a lane.

Its CALL SITE: YES, completely, with nothing to thread through.  At :3873 the
enclosing _compute_wind_aware_search_target already holds every input
_searcher_crosswind_lane needs, and has already called it once in this same
invocation:

  :3740   x_min, x_max, y_min, y_max = self._grid_bounds(runtime_models)
  :3744   simulation = _simulation_from_runtime(runtime_models)
  :3747   _set_active_lane_axis(
  :3748       wind_state,
  :3749       _searcher_crosswind_lane(
  :3750           simulation, uav_id,
  :3751           normalize_wind_direction(wind_direction),
  :3752-55        x_min, x_max, y_min, y_max,
  :3756       ),
  :3757   )
  :3819   wind_norm = normalize_wind_direction(wind_direction)

The lane tuple ("y", 25, 49) is therefore computed at :3749 and then THROWN
AWAY - _set_active_lane_axis (:821-824) keeps only lane[0], the axis letter,
because that is all the previous round needed.  The bounds are discarded one
statement before the code that needs them.

This is the opposite of the situation the lane-clamp round faced with
_finalize_coverage_target.  That one is a module-level function with three
call sites and no access to simulation or uav_id, which is why the axis had to
be carried through wind_state.  Here nothing needs threading: no new parameter,
no new wind_state key, no signature change.  Two options, both local:

  (i)  bind the :3749 expression to a local and reuse it at :3873;
  (ii) call _searcher_crosswind_lane again at :3873 using wind_norm (:3819).

(ii) is preferred and is what will be implemented, for one reason: it does not
edit a single line the lane-clamp round wrote, which the brief forbids.  The
cost is one extra call to a pure function on a branch that only runs when
coverage is inactive.  _searcher_crosswind_lane -> resolve_victim_searcher_uav_
ids (:276-316) only reads model attributes; it mutates nothing and draws no
randomness, so re-calling it is free of side effects.

Q4.  IS A LANE-AWARE FIX THE RIGHT SHAPE, OR IS THERE A SIMPLER ONE?
==============================================================================
DECISION, taken before any code was written and before any post-fix run:

  Re-anchor the fallback on the searcher's own lane by passing the LANE's
  bounds to _gradual_escape_target at :3873 instead of the global grid bounds.
  Do NOT turn the fallback into a filtered candidate search.

That is the brief's option "constrain the fallback point to the searcher's own
lane midpoint ... no filtering logic needed".  Five reasons from Q1-Q3:

1.  THERE IS NOTHING TO FILTER.  _lane_allows_cell is a candidate filter and
    this path has no candidates.  It is 17 lines of arithmetic with a single
    outcome.  Applying a filter would mean first inventing a candidate set,
    i.e. writing a second _pick_global_coverage_escape_target.

2.  THE ANCHOR IS THE WHOLE BUG, AND BOUNDS ARE THE ANCHOR.  cx/cy at
    :1383-1384 are literally the midpoint of the bounds handed in.  Passing
    ("y", 25, 49) makes cy = (25+49)//2 = 37, and the output clamp at :1393
    becomes ty = max(26, min(48, ty)), which is inside the lane by
    construction.  The correction lands at the source of the coordinate, not
    on its way out.

3.  THIS IS NOT THE MISTAKE THE LAST ROUND REJECTED.  Last round option (A)
    ("clamp the clamp") was rejected because clipping the emitted y left the
    candidate loop's own commit / y_force_min filters unsatisfiable, so the
    candidate set stayed empty and the searcher stayed on a degenerate
    fallback: the metric would move while the failure path stayed intact.
    That objection is about TWO REPRESENTATIONS DISAGREEING - a latched state
    read in one place and clipped in another.  _gradual_escape_target has no
    latch and no state at all: it is a pure function of (ax, ay, bounds).
    Change the bounds and the entire computation changes, clamp included.
    There is no second representation left to disagree.

4.  THE ALTERNATIVE IS FORBIDDEN AND UNNECESSARY.  The lane-filtered candidate
    search already exists as _pick_global_coverage_escape_target, which the
    brief puts out of scope - and measurement says it is not the defect
    anyway: 136 emissions on C_east seed 101, 0 out-of-lane, 0 at the centre.
    Duplicating a correct function to replace a broken one is worse than
    fixing the broken one.

5.  IT ALSO REMOVES THE DUPLICATE-TARGET CONVERGENCE.  Today every searcher
    computes the same global centre, so two searchers on the same step hold
    the identical target (7 / 119 steps in the lane-clamp round's east probe,
    all of them (24,24)).  Lane bounds give each searcher a different anchor,
    which is the point of the partitioning.

SUFFICIENCY - what this fix does and does not claim:
  It fixes 100% of the measured C_east out-of-lane emissions, because 35/35
  trace to _gradual_escape_target (17 direct + 18 replays of a stored gradual
  target, Q1.5).  It does NOT claim to fix lane compliance to 1.0: compliance
  is POSITION-based, and victim-pursuit targets and other non-search movement
  are outside this path entirely - the same limit the previous round recorded.

WHAT WILL NOT BE TOUCHED (brief's constraints):
  _lane_allows_cell, the candidate loops at :3466 and :3640, and every line the
  lane-clamp round wrote (_update_coverage_y_commit's y-lane gate,
  _finalize_coverage_target's x-lane gate, _active_lane_axis /
  _set_active_lane_axis and their call sites at :3460, :3634, :3747).  Also not
  touched: the fix14 x-clamp reachability change and the target-hold mechanism.
  The :3548 _pick_global centre fallback is left alone deliberately - it was
  measured (0 firings) and Q1.4 shows it cannot produce the reported signature.

THE n <= 1 CASE - HOW IT IS KEPT PROVABLY INERT:
  _searcher_crosswind_lane returns a literal None when len(ids) <= 1 (:344-345)
  and on ValueError (:348-349).  The new code is guarded on `lane is not None`,
  so at n <= 1 the arguments passed to _gradual_escape_target are byte-for-byte
  the ones passed today and control flow is identical.  The only added work is
  one call to a read-only function that consumes no randomness.  This is
  argued semantically here and will be proven empirically in Part 3 item 6 by
  a bit-identical 16-combo default matrix.
