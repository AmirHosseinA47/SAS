HOW TARGETS ARE CHOSEN IN THE SHIPPED CONFIG
1. Coverage mode is effectively always on. _coverage_mode_active (local_adaptation_generator.py:811-826) returns True whenever unresolved_victim_count > 0; every branch after that ends in `return True`. managed_victims holds every victim from init (wildfire_model.py:920-946), so the count is > 0 until every victim is resolved.
2. Each _compute_wind_aware_search_target call applies _apply_unresolved_coverage_mode (:4028, :1360-1370). That sets force_coverage_escape, force_interior_retarget and coverage_priority 0.9, and clears force_sweep.
3. The target is then _pick_global_coverage_escape_target (:4030-4059 or :4164-4198), passed through _finalize_coverage_target and the COMMIT HOLD (_apply_target_hold, :1130-1194).
   - The hold returns the same held target T on every call and step until one of four releases fires (:1095-1127): arrival (Euclidean distance <= 2), unsafe (T itself burning or in smoke), stalled (12 steps with no new best distance; COMMIT_PROGRESS_WINDOW = WIND_FIRE_FRONT_MIN_DISTANCE, :92) or timeout (held steps > 2 x the initial distance).
   - _corridor_diversity_failure (:792-808) is true whenever the last 20 x-positions span 18 cells or less (CORRIDOR_NARROW_X_SPAN = 18), which is nearly always. So branch :4030 usually runs and also writes wind_state.escape_target = held T (:4052).
4. The planner (local_uav_path_planner.py:138-213) always sets needs_new_wind_target when coverage is active, so the executor ignores the decision target (:1367-1372, :1413, :4267).
5. The executor then routes as follows:
   - If escape_target is set, it steers there first (uav_executor.py:1374-1405, via _attempt_pathfinding_toward_target with the BFS label).
   - Otherwise force_coverage is true (:1439-1457). It recomputes _wind_aware_victim_search_target (:1458; the generator's second call this step returns the same held T) and routes through _apply_retarget_with_pathfinding_fallback (:1466-1469).
   - Both routed paths reach _route_within_fire_field, whose latch is keyed on the rounded goal (:2186, :2193-2215).

IS THE TARGET THE SAME ON CONSECUTIVE STEPS?
Mostly yes, so a latch keyed on the target would hold in the main regime. The exceptions:
- the one-call release gap (a released hold returns that call's freshly computed target, :1180-1181);
- a switch between a stale escape_target and the held target;
- flapping between two roughly equidistant known victims (_nearest_target, :4757-4772);
- a route that ends within Manhattan distance 2 of its goal (:2212-2214). The fallback there is the memoryless path: _choose_best_direction plus the hazard gate.

WHICH STEPS ARE STILL MEMORYLESS (NOT ROUTED)
The route is reached from only two call sites: :1389 and :2313 (via :1467 and :1492). Every other searcher branch uses _choose_best_direction plus _apply_victim_searcher_hazard_gate, and then execute() may gate the result a second time (:452-460):
- the planner wind target (:1418-1437);
- the non-forced executor wind target (:1470-1477);
- the lawnmower sweep (:1591-1602);
- the escape and retarget fallbacks (:1397-1405, :2321-2325);
- the known-victim branch (:1071-1333; no gate inside it, only the post-gate in execute());
- hold_escape (:373-426 then :452-460).
The fail-safe role-preserving search (:501-537) uses _apply_final_direction_safety (:1955-1965) instead of the searcher gate. It is a separate memoryless override that can also rewrite a routed step's label. For example, a fire-wait with '_hazard_escape' appended no longer matches FIRE_WAIT_LABEL, so the stay at :168-171 is lost.
Separately, execute() decides a step was routed from self._last_escape_method (:453-456). That attribute persists on the cached executor (decision_dispatcher.py:216-223) and is not reset when the route returns None at :2212-2214. A fallback step can therefore be exempted from the post-gate on a stale value. It has already been gated once inside the fallback.

MINIMAL DETERMINISTIC GIVE-UP, PER TARGET SOURCE

(1) Coverage held target (the dominant source)
- Blacklisting alone is not enough, because the hold ignores saturation. Releasing alone is not enough either: the release returns a fresh argmax, T can win again (the recent-target penalty is only 5, or 2.75 within 3 cells, :666-677), and the next call re-arms the hold on it.
- Even release plus blacklist can hand back T. _finalize_coverage_target moves the argmax afterwards (:1225-1285): the x-clamp, the west/east sweep pull to safe_x_min + 6 or safe_x_max - 6, and the y-commit clamp. The moved cell is checked only against fire and smoke (:1286-1291), never against saturation. The function's own docstring (:1017-1022) records 58 target breaks collapsing onto 2 distinct cells.
- The all-excluded fallback, the grid midpoint (:3799-3814), is not checked against saturation either.
- A robust give-up therefore needs four steps: _clear_target_hold; blacklist T; clear escape_target if it equals T; and a check on the finalized or armed target against the given-up T (at :1182-1184 or in the executor before routing).
- A near-existing bound: in the main regime a no-progress wait should already end in about 12 steps. The same-target streak blacklists T at about 11 steps (:4068) and the stall release fires at 12 (:1120).

(2) escape_target
- Must be set to None explicitly. It is cleared only by:
  - distance <= 2 in the executor (:1383-1387);
  - distance <= 3 in the generator (:4094, :4110);
  - leaving the pocket's 5x5 box (:1473-1476);
  - pocket < 5 and more than 6 cells from the anchor (:1505-1512);
  - a role change (wildfire_model.py:478-481).
- A stationary waiting searcher keeps it indefinitely unless the diversity-failure branch rewrites it (:4052).
- Outside coverage mode, _gradual_escape_target is a pure function of position (:1528-1544). From the same cell it returns the same T immediately (:4149-4153).

(3) Planner wind target: a blacklist on T is enough for the executor to drop it (:1413-1417). But the recomputed target is the held T unless the hold is also released.

(4) Corridor target (used only when no victim is unresolved): the existing _reset_corridor_on_same_target_streak pattern (blacklist, corridor cleared, force_interior) is enough. The regenerated corridor excludes T for 15 steps.

(5) Sweep target (no blacklist consumer): advance the state the way the at-target branch does (:1570-1579), or change lane at the lane end (:1549-1569). T recurs if it is the clamped lane end (:1578, :4585, band clamp :4526-4527). Also, before step 20 (LAUNCH_GRACE_STEPS) the sector bounds are None: y_end is 0 or W-1 (:1541) but the sweep is clamped to the band [4, W-5], so the lane-end test can never pass and the target sits at the lane end. This is inferred from the code, not measured.

(6) Known victim: no exclusion exists. The nearest unhandled victim (:1047, :1780-1806) is re-picked every step until its status changes (:1697-1778). A give-up needs a new per-UAV exclusion with an expiry. Abandoning a victim trades against detection and rescue.

The retarget flags (force_interior_retarget, force_coverage_escape, needs_new_wind_target, force_wind_retarget) never produce a different target on their own. They only choose the routed branch, discard the decision target, or trigger corridor regeneration (a different target only outside coverage mode). blocked_backtrack_cells changes the path, not the target, and the route's BFS explicitly ignores it.

PLANNER SIDE
- The generator re-issues the held T every step (:2267-2277, :4371).
- It re-issues live-victim targets every step (:2245-2266).
- The planner derives its flags only from the wind_state snapshot (wildfire_model.py:1956-1978, copied at adaptation_manager.py:106 before generation at :111). fire_route_target is written and read only in uav_executor.py (:2194-2215). No planner code sees the route's no-path state.
